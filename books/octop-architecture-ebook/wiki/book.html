前言：看懂一个 Agent 宿主如何拼起来

调通一个大模型 SDK 往往只需要几十行 Python，但把它做成一个家庭或小团队长期跑在自己机器上的多用户助手，真正消耗工程量的事情几乎全在模型循环之外。谁能看哪位专家的对话、浏览器关掉后长任务怎么继续跑、工具调进死循环怎么刹住、切到 PostgreSQL 多副本之后定时任务和飞书通道怎么避免跑两遍、托管外部编程 Agent 时怎么把知识库和插件递给它，这些才是决定平台能不能稳住的骨架。

TencentCloud/Octop 的价值正在这层宿主设计。它把四套独立发布的运行库（octop-harness、octop-gateway、octop-memory、octop-browser）和一个 React 前端，装进同一个 Python 包里。读它的源码时，与其按目录从头翻到尾，不如追着真实故障和边界问题看：谁持有状态、哪条边界真拦得住越权、哪项能力在单机和集群模式下表现完全不同。

阅读之前先避开三个常见误判#

阅读 README_CN.md 时，容易看到早期留下的概念印象，对照 docs/architecture.md 和 src/octop/infra/server.py 后有三个事实必须先对齐。

第一，AgentManager、Gateway、CronManager 都是进程级单例，按数据行字段区分用户和专家，早就不再为每个用户维护一套独立的管理器对象。

第二，聊天主通道已经从旧版 SSE 迁到双向 WebSocket（/api/agents/{agent_id}/chat/ws），哪怕前端个别辅助文件仍保留历史命名，也只有 HITL 恢复路由 POST /api/agents/{agent_id}/chat/hitl/resume 还在用 SSE 推送续跑流。

第三，选择 SQLite 还是 PostgreSQL 不再只是换一张连接表。随着 ADR 003 与同行租约落地，PostgreSQL 模式下技能包源、知识库原文和 pgvector 向量、专家记忆以及通道和定时任务租约都迁进了共享库，但每台实例的本机工作区和飞书去重表仍留在各自磁盘上，需要按数据类别分别盘点。

需求推导：脱离模型 SDK 之后要守住什么

把大模型接进产品时，第一周通常顺风顺水：上传一份文档、拼好系统提示词、流式吐字，原型就能演示。麻烦往往在第二周同时冒出来。同事问能不能共用你调好的那位研究专家，但又不能互相看见私有聊天记录；长工具调用跑了三分钟，用户切了个标签页或者合上笔记本，后台任务该不该直接掐断；Agent 准备调用外发或删文件工具时，审批按钮点快了两次会不会发出两份；好不容易配好的一套系统，换台机器或者加个副本后配置全散了。

这些问题没有一个能靠换更强的模型解决。它们决定了 Octop 必须长成什么样的宿主架构，也决定了每一条代码边界到底在防什么。

产品定位与信任边界#

Octop 面向的典型场景是个人、家庭和小团队的自托管 AI 助手。这个定位划出了很清楚的能力边界：它需要支持多用户、角色权限、用户组资源可见性和企业 LDAP/OIDC 登录，但它的默认假设仍是可信小团队内的自托管环境，不等同于面向陌生公网租户的强隔离多租户 SaaS。

在权限设计上，系统里至少存在四类行为主体，各自需要什么权力、不该顺带拿到什么权力，在源码里分得非常明确：

主体角色 核心操作需求 必须拦住的越权动作
普通成员 聊天、上传附件、管理自己的专家与连接器 读取他人的私有线程，或修改他人共享出来的专家配置
专家所有者 配置模型、技能、知识库、后端及分享范围 分享专家后把自己的历史私有会话一并暴露给他人
管理员 完成首次初始化、管理用户组、限制允许的存储后端 无审计地混用个人云凭证，或绕过容器宿主挂载约束
外部协作者 通过 IM 通道或跨实例 Bridge 调用授权专家 用本机用户编号冒充对端身份，或借隧道打穿管理接口

源码里管理员在多处路由拥有 bypass 逻辑（例如 api/common/agent.py 和 api/deps.py 中的权限检查），这是为了降低小团队运维成本做的刻意取舍。部署到跨部门场景时，要把哪些能力留给管理员、哪些云账号凭证按用户隔离（如 v1.0.3b6 起腾讯云 CVM 登录严格按用户隔离），当成架构前提来评估。

八条核心需求如何推导出系统骨架#

从真实使用中的失败模式往回推，Octop 现在的模块分布几乎都能找到对应的工程动因：

面对的工程问题 Octop 采取的架构方案 源码落点

这张对照表在日常改需求时非常顺手。比如要接入一个新的 IM 平台，变动应该停在通道适配和 octop-gateway，不该去改 AgentManager；如果要调整共享专家的会话可见性，变动就必须落在服务端鉴权和线程表模型上，只改前端列表过滤毫无意义。

用可核对的行为取代空泛指标#

给一个 Agent 平台写验收标准，一上来就拍脑袋写一个并发 QPS 数字往往没什么用。模型耗时动辄几秒到几十秒，真正让人在生产里踩坑的是状态和边界失真。对照 Octop 的核心路径，至少有七条行为验收线必须盯死：

  1. 用户上传的附件先进入受控工作区 inbound/，模型与工具只读取工作区引用，不拿浏览器预览地址当文件权威。
  2. 浏览器断开 WebSocket 后，宿主里的在途回合继续执行；重新订阅后能接上后续流，历史刷新不会把屏幕上正在生成的回复冲掉。
  3. 共享专家允许授权成员开启自己的对话，但拿着他人的 thread_id 请求历史或订阅时，除非该线程被显式标记为共享对话，否则服务端必须拒绝。
  4. 危险工具触发人工审批暂停后，审批决定必须绑定具体的 pending_id 和参数快照，用户连点两次批准不会把外部动作投递两遍。
  5. 模型陷入死循环反复调用同一个工具、传同一组参数时，宿主按连续相同次数熔断并结束回合，但不能误杀正常换参数探索的多步任务。
  6. 模型或工具中途报错时，历史与界面明确记录失败回合，不能把一段报错文本混成普通成功回复。
  7. 服务重启或切换数据库维护后，已提交的对话历史仍可读；清理孤儿 checkpoint 时绝不能误伤共享库里其他智能体的活跃对话。

这七条线几乎每一条都对应着 Octop 在 v1.0.3b1 到 v1.0.3b7 之间真实修过的线上问题。后面每一章拆源码时，我们都会拿具体代码去对照这些边界到底是怎么落地的。

非功能指标必须拆成可定位的段#

在 Agent 平台里笼统说系统慢或不稳定，几乎没法排障。延迟至少要拆成四段来看：WebSocket 建连与首帧确认、模型首 token 等待、单次工具执行耗时、回合结束后的历史与轨迹落盘耗时。稳定性同样要拆成具体故障点：弱网断线重连、上游模型超时与自动切换、本地磁盘空间不足时的 SQLite 压缩跳过、进程优雅退出时租约释放、以及知识库索引或重排序超时降级。

记录一次线上问题时，把用户 ID、agent_id、session_key、thread_id、选中的模型引用和实际落盘结果一起抓出来，排障就能直接定位到某一层，而不用对着一张回复空白的截图猜半天。

总体架构：单进程宿主与四套可复用运行库

很多团队一启动多 Agent 平台项目，图纸上先画出一排框：API 网关、任务队列、Worker 集群、记忆服务、文件服务、通道服务，光把本地开发环境拉起来就要折腾半天 Docker Compose。Octop 反其道而行之，在 docs/adr/001-single-process-model.md 里定下一条铁律：核心平台必须是一个 Python 进程、一个安装包，装完只配模型密钥就能跑，不强制依赖 Redis、RabbitMQ 或独立 Worker。

单进程不等于代码揉成一团。相反，为了既保住单机安装极简，又能把底层能力复用给其他项目，Octop 把整个架构切成了五层，而且在仓库根目录的 AGENTS.md 里写死了模块之间的依赖禁令。

这张分层图把 Octop 的边界划得很直白：所有依赖严格向内流动，传输层调领域层，领域层绝不反向依赖 HTTP 路由或 CLI。整座仓库里只有 src/octop/launch.py 这一个模块允许同时引入 infra/server 和 api/app，用来把后端领域对象树和 FastAPI 装配到 uvicorn 里。

为什么拆成宿主加四套运行库#

看 pyproject.toml 的依赖清单，能清楚看到 Octop 把重型垂直能力抽成了四个独立发版的库：

  • octop-harness（>=1.0.11）承担基于 LangGraph 的 Agent 循环、工具调用、技能加载、存储后端抽象与中间件机制，以及记忆和浏览器工具在回合内的接线。
  • octop-gateway（>=1.0.4）负责飞书、钉钉、企微、微信、Telegram、Discord 等 IM 平台的协议适配、媒体上传与群聊唤醒规则。
  • octop-memory（>=1.0.5）管长期记忆的提取、召回、排序、数据库表结构与压缩维护。
  • octop-browser（>=1.0.0）管 Chrome CDP 连接、浏览器 Profile、DOM 操作与 browser_tool。

Octop 宿主仓库自己只干一件事：把这四个库包装成多用户产品。用户认证、角色与用户组、专家注册表、线程管理、连接器凭证加密、知识库检索、定时任务、跨实例 Bridge 和 React Dashboard 全部留在 src/octop/ 和 dashboard/ 里。AGENTS.md 明确要求，遇到属于这四个库的行为缺陷，必须去对应运行库里修并升级 pyproject.toml 的版本下限，禁止把实现复制粘贴进宿主仓库。

这种拆法把演进节奏解开了：运行库可以独立跑单测、独立升级模型协议或 IM 适配，宿主则专注产品权限、控制面数据和工作台体验。

读懂 infra/ 目录里的硬边界#

初看 src/octop/infra/，容易因为目录名把它当成传统 DDD 里的纯基础设施层。其实 Octop 的核心业务编排几乎都在 infra/ 里：AgentManager 管进程内全部专家的生命周期与装配，Gateway 管通道连接和 WebSocket Hub，GlobalProcessor 管所有入口汇入后的统一回合处理，CronManager 管定时调度，SharedServices 把各张表的仓储对象打包注入上层。

为了让这个大目录不退化成网状互相引用，仓库定下了几条刚性红线：

  • infra/ 绝不能引入 api/、cli/ 或 launch.py。
  • infra/db/repos/ 只写 SQL，只能依赖 infra/db/_base 和 infra/utils/，不能反向引入 agents/ 或 gateway/。
  • infra/utils/ 只放无领域依赖的纯辅助函数（路径、ULID、SSRF 校验、宿主机目录规则等）。
  • api/routers/ 保持薄层，只做 HTTP 参数校验、权限提取、调 infra/ 和映射 OctopError，不藏业务规则。
  • dashboard/ 前端 SPA 只通过 /api HTTP 和 WebSocket 与后端通信，绝不直接读 SQLite 文件，构建后的静态资源打包进 src/octop/dashboard/ 随 wheel 一并分发。

Click CLI 也按同样思路分层，不复制业务逻辑。纯配置增删（如 user、provider、cron 列表）走离线仓储直读写本地库；需要真实运行时能力的命令（如 chats send、chats repl、cron run-now、acp）则在进程内拉起一个短生命周期的嵌入式 OctopServer；涉及操作系统或扫码绑定的操作直接走外部子进程。

单进程如何平滑过渡到多副本集群#

早期 v1.0.3b1 时期，ADR 002 虽然支持把控制面换到 PostgreSQL，但单进程内存假设导致它明确不承诺多实例同写：两个进程各自拉起 APScheduler，同一条定时任务就会跑两次；两个进程各自连飞书长连接，消息会乱抢。

到了 v1.0.3b3 至 v1.0.3b6，Octop 并没有为了多副本推翻单进程模型去上 Redis 和 Celery，而是顺着共享 PostgreSQL 补齐了三块拼图：

  1. 内容平面入库（ADR 003），PostgreSQL 模式下技能包源、知识库原文和 pgvector 向量不再绑在单机磁盘上，全部进共享库，每台实例看到同一份资产。
  2. 同行租约（infra/db/lease.py），定时任务和 IM 通道在数据库行上抢占 90 秒租约，持有者每 30 秒续约、退出时主动释放，其他实例每 25 秒巡检接管过期行，保证后台任务和长连接单活。
  3. 入口按 Cookie 粘滞（docs/cluster_CN.md），浏览器发起的一轮流式对话由接入的那台实例在内存里持有并推送实时帧，前置反向代理或 Kubernetes Ingress 用 Cookie 把同一浏览器固定到同一副本。

这套组合很有工程节制感：单机用户依然零外部依赖、开箱即用；小团队需要滚动升级或横向扩展对话吞吐时，换上共享 PostgreSQL、配好对象存储或 PG 工作区、套上官方 Helm Chart 就能跑多副本，不需要把单体拆成十几个微服务。代价也很坦诚：单台副本挂掉时正在进行的实时流会断一次，刷新后由新副本从共享库恢复历史，它换来的是部署简洁，而不是无感透明的进程内状态迁移。

启动与退出：装配顺序、延迟绑库与有序收尾

服务刚启动时最容易出隐蔽故障：数据库还没选定，路由已经放进来读写请求；旧版本残留的历史归档还没迁完，新对话已经把 checkpoint 祖先剪掉了；进程收到 SIGTERM 后直接强杀，定时任务刚好触发一半，通道租约没释放，另一台副本只能干等 90 秒超时。

Octop 把整套启动和退出拆成了两个清晰的装配入口：src/octop/launch.py 负责外部进程与 Web 服务器接线，src/octop/infra/server.py 里的 OctopServer 负责领域对象的依赖排序、延迟绑库、启动迁移和逆序关闭。

为什么把 launch.py 和 server.py 拆开#

执行 octop run 时，CLI 并不直接构造 FastAPI，而是调用 launch.run_foreground_blocking。launch.py 先启动 OctopServer，再把构建好的领域服务树交给 api/app.py 的 build_app()，最后挂载到 uvicorn 事件循环。

把这两个文件分开有两个实在的好处。第一，像 octop chats repl、octop cron run-now、octop acp 这类嵌入式 CLI 命令，可以直接实例化 OctopServer 跑完就退，不用绑定 TCP 端口，也不用引入任何 FastAPI 路由代码。第二，HTTP 层与领域层的依赖方向被物理切断，哪怕未来换一套 Web 框架，核心启动树也不用动。

从空目录到可接请求的装配链#

进入 OctopServer.start() 后，对象树严格按依赖顺序逐层拉起：

  1. 解析 PathLayout.from_env() 和 load_config(config.json)，叠加环境变量覆盖，确定数据目录、密钥目录与数据库配置。
  2. 判断是否需要延迟打开控制面数据库（should_defer_control_plane_db）。首次安装且尚未指定数据库时，服务先以未绑定状态启动，只放行安装向导与健康检查路由。
  3. 控制面就绪后，调用 open_database() 打开 SqlitePool 或 PostgresPool，顺序执行 infra/db/migrations/ 下的带编号迁移脚本（SQLite 与 PostgreSQL 成对维护，截至 v1.0.3b7 已到 025_user_mfa）。
  4. 装配 SharedServices（所有仓储与公共服务）、WizardTokenStore（5 分钟有效的向导令牌）、ExpertCatalog、SubagentCatalog，以及 PluginManager.seed_bundled() 与 load_installed()（内置插件默认关闭）。
  5. 构造进程级 AgentManager，并在任何专家写新对话之前执行一次性 migrate_history_v2()（见下文）。
  6. 拉起 Gateway（包含按需建立的 ChannelManager 与 WebSocketHub）、CronManager（APScheduler）和 UserManager，把四个核心单例收进 AppRuntime 暴露给 API 路由。

这套顺序里藏着一条关键区分：进程存活不等于业务就绪。如果健康检查只看 TCP 端口通不通，首次安装进入向导锁定态，或者某个专家的远程后端失联时，排障很容易误判。区分宿主未绑库、用户未初始化、单个专家构建超时和单次模型调用失败，能省掉大量查日志的时间。

首次安装的延迟绑库与空库重绑#

自托管用户第一次打开页面，往往是在浏览器向导里决定用 SQLite 还是填一套外部 PostgreSQL 地址。如果 OctopServer.start() 强行在启动瞬间建好默认 SQLite 并初始化所有服务，用户选 PostgreSQL 时就会出现两套库互相打架的局面。

infra/db/factory.py 中的 should_defer_control_plane_db 专门处理这个空白期：未完成初始选库时，服务先启动 HTTP 界面并由 setup_lockdown 中间件拦截非向导请求；用户提交数据库选择并测试连通后，服务端调用 bind_control_plane() 正式打开目标库、跑完迁移并启动 _boot_runtime()。

对于已经绑定了空库、还没有创建任何用户（user_count == 0）的向导场景，infra/db/rebind.py 还允许切换一次控制面，并调用各运行时组件的 replace_repos() 等重绑方法同步新连接池，避免直接改私有字段留下一半旧引用。一旦管理员账号建好、系统进入正常使用，这条热重绑通道就关上了，不存在运行中把存量 SQLite 数据在线切到 PostgreSQL 的魔法。

v1.0.3b5 的启动关口：下线 history_v2 的一次性迁移#

在 v1.0.3b1 时，Octop 曾试验过一套名为 history_v2 的本地分段归档库（history_v2.sqlite）。到了 v1.0.3b5，团队决定正式下线这套仅支持 SQLite 的平行历史库，统一回到控制面的 thread_messages 投影表。

处理这种历史包袱时，最危险的做法是在后台异步慢慢搬数据，或者允许新对话边写边迁。看 src/octop/infra/server.py 的 _boot_runtime()，团队把 migrate_history_v2() 放到了一个非常卡死的位置：数据库迁移完成之后、任何 Agent 开始写新历史或裁剪 checkpoint 祖先之前。

src/octop/infra/history/retire_v2.py 的实现很克制：

  • 检测到 ~/.octop/history_v2.sqlite 或 history_v2.required 存在时才触发；如果只有标记文件却缺归档文件，或者当前控制面已经不是 SQLite，直接抛错中止启动，绝不静默丢历史。
  • 以只读模式（mode=ro + PRAGMA query_only = ON）打开旧归档，校验 archive_meta.version == 1。
  • 按 thread_id 逐条开控制面事务迁回 thread_messages，并在同一事务里向 history_v2_retirement 表写入归档片段的 SHA-256 摘要。哪怕迁移到一半进程崩溃，重启后已迁完的线程靠摘要幂等跳过，未迁完的继续补齐；如果有人换了一份不同内容的旧归档顶包，摘要不匹配会立刻报错拦下。
  • 全部线程落稳后，再把旧归档和标记文件归档移走，之后整套系统才正式接流。

这个启动关口示范了什么叫负责任的架构退场：不留双写尾巴，不靠运维手工倒库，把幂等和崩溃恢复做在启动链路里。

退出为什么必须按逆序来#

收到退出信号后，OctopServer.stop() 不会直接让进程一死了之，而是反着依赖树拆掉：先停主动关怀调度器和 CronManager，再停 Gateway 和外部通道连接，随后停止 AgentManager 中的活跃专家与连接器会话，最后关闭历史资源和数据库连接池。

先停调度器和入口，再停执行器，道理很朴素：如果先关了数据库或 Agent 注册表，而 APScheduler 刚好唤醒一条定时任务，或者 IM 通道正好收进一条群消息，就会撞上一连串半销毁状态。在多副本 PostgreSQL 部署里，有序退出还多了一层价值：CronManager 和通道管理器退出时会主动释放自己持有的数据库租约行，另一台副本在下一轮 25 秒巡检里就能立刻接管，不用干等 90 秒租约自然过期。

Agent 装配：原生专家、托管专家与中间件顺序

用户在界面里改了一位专家的默认模型，或者关掉了一个技能，数据库里那行 agents 记录马上就变了。但此时内存里可能正跑着一个三分钟的回合，或者连接池里还挂着旧的 MCP 客户端。数据库里的配置行，和真正执行推理的运行时对象，在 Octop 里是两回事。负责把静态配置行装配成活的运行时、又管住并发重载边界的，是 src/octop/infra/agents/manager.py 里的 AgentManager。

从 v1.0.3b6 和 v1.0.3b7 开始，这套装配体系还多了一类一等公民：托管专家（kind="managed"）。它把本地的 OpenCode、Claude Code、Codex、CodeBuddy 等外部 ACP 编程 Agent 接进同一张专家列表，同时把 Octop 的工具、知识库和插件递给这些外部进程。

从 agents 表行到 HarnessAgentConfig#

对原生专家来说，AgentManager._build_harness_config() 是能力拼装的总开关。它把六份分散的来源合成一份 HarnessAgentConfig，再交给 octop-harness 构造 LangGraph 运行时：

信息来源 装配进运行时的产物 工程上容易踩的坑
agents 行与 config_json 身份、提示词、默认模型、运行时限制开关 保存进库不等于已生效，要区分热同步与重建
工作区后端解析 workspace_dir、BackendWorkspace spec 文件内容后端与 shell 执行环境不是一回事
Provider 解析 模型引用、候选故障转移列表、本地 Magpie/Ollama AUTO 路由在原模型失效后需自动换可用兜底
技能、插件与连接器 工具集合、MCP server 列表、技能目录 已安装但未启用的插件绝不能默认注入
安全策略 SecurityPolicy.merge(global, agent)、interrupt_on 专家级覆盖不得绕过全局底线
Memory 配置 记忆后端 DSN/路径、独立辅助抽取模型 聊天模型正常不代表记忆提炼模型也可用

manager.py 体积很大，既管生命周期锁，又管各类能力组装。读它时别从第 1 行硬啃，沿着 _build_harness_config() 和 stream() 两条主干看，先抓输入来源和输出配置，再按需下钻到 infra/agents/settings/ 下的子模块。

中间件顺序为什么不能随便调#

原生专家装配时，宿主会往运行图里挂一串有序中间件。看 manager.py 里的装配片段，能直观感受到它们各自卡在什么位置：

  • TokenQuotaMiddleware 和 ReasoningRequestMiddleware 在外层管配额与推理强度参数透传。
  • KnowledgeSearchHintMiddleware 与 BrowserProfileMiddleware 负责把知识库目录和浏览器配置提示带入上下文。
  • BinaryReadGuardMiddleware 挡住模型直接把二进制大文件当文本读爆上下文。
  • WorkspaceImageMaterializeMiddleware 把工作区图片路径转换成模型可见的多模态输入；ThreadArtifactsMiddleware 则在输出侧把新生成的工作区文件登记到当前线程。
  • OctopUiOffloadMiddleware 必须留在特定内层，把插件返回的超大 octop_ui 富界面载荷卸出模型上下文，同时让外层其他中间件看到一致的瘦身结果。
  • 最外层再根据配置挂上 SafeModelFailoverMiddleware 以及 runtime_limits.py 组装的调用护栏中间件。

这里最值得留意的是 v1.0.3b7 新增的 ConsecutiveToolCallMiddleware（位于 src/octop/infra/agents/middleware/consecutive_tool_call.py）。

连续相同工具调用熔断：既杀死循环，又不误伤长任务#

早期版本如果简单限制一轮对话的总工具调用次数，很快就会撞墙：一个认真的代码审计或批量文档处理任务，合法调用五六十次不同的 read_file 或 grep 再正常不过，总次数一刀切会把正常长任务直接掐死；可如果不设防，模型卡在某个报错参数上原地空转几十轮，既烧光 token 又卡死页面。

v1.0.3b7 给出的解法非常精准：runtime_limits.py 默认开启 ConsecutiveToolCallMiddleware(limit=40)，只统计连续相同的 (tool_name, sorted_json_args) 调用。看它的核心判定逻辑：

class ConsecutiveToolCallState(AgentState[Any]):
    # UntrackedValue 确保计数器只在单次 run 内存活，下一轮用户发言自动清零
    tool_call_streak: NotRequired[Annotated[dict[str, Any], UntrackedValue, PrivateStateAttr]]

每当模型产出一条带 tool_calls 的 AIMessage，after_model 钩子逐个计算 tool_call_signature(call)（工具名加排序后的 JSON 参数）：

  • 签名和上一条完全一致，count 加 1；只要换了工具名、改了参数，或者模型吐出了一条不带工具调用的纯文本回复，count 立刻归零。
  • 一旦 count > limit，中间件不会再放行这次执行，而是给被拦截的调用以及同一批次里尚未执行的后续调用都补上 status="error" 的 ToolMessage，再追加一条带 [tool_call_repeat] 标记的 AIMessage，直接返回 "jump_to": "end" 结束本轮图执行。

把状态类型声明成 LangGraph 的 UntrackedValue 很讲究：它不污染长期 checkpoint，也不需要手动写清理代码，用户下一轮发言自然重新起算。配套的 ToolRetryMiddleware（默认重试 5 次）和模型重试预算（默认 2 次）也一并收在 runtime_limits.py 里统一解析，参数配置收口得很干净。

托管专家：把外部 ACP Runner 装进同一套专家模型#

v1.0.3b6 引入、v1.0.3b7 补全的托管专家（src/octop/infra/agents/managed.py），解决的是另一类常见诉求：开发者本机已经装好了 OpenCode、Claude Code、Codex、CodeBuddy、Cursor CLI 或 Kimi Code，想直接在 Octop 的 Web 工作台、IM 通道或定时任务里驱动它们，而不是再套一层原生 LangGraph 循环。

托管专家在控制面依然是一行 agents 记录，区别在于 kind == "managed"，配置里记录 managed_runner、workspace_dir、可选的 managed_session_mode 和 managed_permission_mode。宿主在装配它时做了四件很务实的事：

  1. 剥离不匹配的原生开关，pin_managed_runtime() 去掉 Octop 原生的 conversation_mode，默认关闭记忆提取与注入（除非显式开启），并将存储后端钉死在本地根目录以便用户自选项目目录。
  2. 按 Runner 习惯映射技能目录，link_managed_skill_packages() 根据不同工具的原生约定目录（如 .claude/skills、.opencode/skills、.codex/skills、.codebuddy/skills、.cursor/skills），把用户选中的技能包以符号链接或 Windows Junction 的方式挂进去，并在 .octop/managed-skill-links.json 里记录自己创建的链接清单。切换 Runner 时，只清理清单里由 Octop 创建的链接，绝不误删项目原本的真实目录。
  3. 会话模式与审批门联动，src/octop/infra/agents/acp/session_modes.py 维护了各 Runner 支持的 session/set_mode 枚举表（例如 CodeBuddy/Claude Code 的 default、acceptEdits、plan、auto、bypassPermissions，Codex 的 auto、read-only、full-access，OpenCode 的 build、plan）。解析时故意忽略 Octop 自己的 ask 和 craft，保留通用的 plan；只要命中的模式 ID 含 yolo、bypass、full-access 等无人值守标记，approval_for_session() 就返回 yolo 跳过审批，反之如果该 Runner 发布过无人值守模式但当前没选它，就强制走 ask。
  4. 通过 6 个回环 MCP 把宿主能力递给外部进程，外部 Runner 跑在独立子进程里，看不见 Octop 进程内的 Python 工具。src/octop/infra/agents/acp/turn.py 在回合启动时，把用户授权的外部连接器加上 octop-knowledge、octop-agents、octop-files、octop-cron、octop-memory、octop-plugins 最多 6 个本地 HTTP 回环 MCP 服务拼成 mcp_servers 传给 session/new 或 session/load。我们在第 10 章和第 14 章会展开这套回环的细节。

进程内锁与重载策略#

AgentManager 内部同时维护了几种不同粒度的 asyncio.Lock：按 agent_id 的生命周期锁保护启动、停止和重建不撞车；按 (agent_id, thread_id) 的执行锁保证同一条线程的普通流式对话和 HITL 恢复不并发写 checkpoint；此外还有在途调用计数和记忆维护时的回收保护。

并非所有配置改动都要推倒重建运行时。像技能启用过滤集合这类轻量变更支持热同步，而更换 Provider、改底层后端或增减插件则会触发运行时重建，并在并发重载时加上有界限制避免瞬间打满内存。需要注意的是，这些锁全部存在于当前 Python 进程内；到了多副本部署场景，跨实例的并发保护不再靠它们，而是交给数据库事务和租约来处理。

身份与会话：四种标识与共享专家的线程隔离

共享一个调教好的专家给团队同事，是自托管助手最高频的需求，也是最容易漏权的地方。假如后端只校验当前用户有没有登录、能不能访问这位专家，一旦有人把浏览器地址栏或接口里的 thread_id 换成同事的编号，整段私人聊天记录就会直接串台。

Octop 用四个彼此正交的标识把人和对话彻底拆开：user_id、agent_id、session_key 和 thread_id。混用其中任意两个，权限和会话生命周期都会缠在一起。

四种标识各自管什么#

标识 回答的问题 生命周期特征
user_id 当前操作主体是谁 来自 JWT / 认证中间件，绝不信任请求体里的明文声明
agent_id 调用哪位专家 资源维度，可私有、可按用户组可见、可公开分享
session_key 某个入口当前绑在哪条对话上 可随时改绑，如 <aid>:dashboard:<uid>:dm 或 IM 群键
thread_id 哪一段持续对话和 LangGraph 图状态 稳定身份，切新对话后旧线程保留在历史里

不拿 session_key 直接充当 thread_id，原因很实在：同一个浏览器窗口或飞书私聊入口，用户随时会点新建对话。如果入口键和对话 ID 合二为一，新建对话就只能覆盖或删掉旧上下文；把它们拆成一张绑定表（ThreadRegistry），入口可以自由指向新线程，旧线程依然能按 thread_id 回看、归档甚至被定时任务固定引用。

先查专家权限，再查线程可见性#

请求进入聊天或工作区路由时，鉴权分成严格的两关。

第一关在 src/octop/api/common/agent.py。代码把读用权限和管理权限明确拆成两个辅助函数：require_agent_row() 允许专家所有者、管理员以及满足分享或用户组可见策略（expert_visible_to）的成员使用专家；修改模型、提示词、技能或删除专家则走 require_agent_owner_row()，把普通共享使用者挡在外面。

第二关在 src/octop/api/routers/chat/turn.py 的 resolve_thread_id()，以及 src/octop/infra/gateway/threads.py 的 thread_visible_to()。看 v1.0.3b7 的真实检查逻辑：

row = thread_registry.get_thread(thread_id)
if row is None or row.agent_id != agent_id:
    raise OctopError(ErrorCode.AGENT_NOT_FOUND, f"thread {thread_id!r} not found")
if not thread_visible_to(row, user_id):
    raise OctopError(ErrorCode.FORBIDDEN, "thread not owned by user")

而 thread_visible_to(row, user_id) 的判定只有一行：

def thread_visible_to(row: ThreadRow, user_id: int) -> bool:
    return row.user_id == user_id or bool(getattr(row, "contributed", False))

这行代码藏着 v1.0.3b5 才加入的产品语义：共享专家上的主动共享对话。默认情况下，哪怕专家已经分享给全组，每个人在上面创建的对话 contributed 都是关闭的，只有 row.user_id == user_id 才能打开。只有当线程所有者在共享专家下主动把某一条对话分享出去（置位 contributed），同一专家的其他可见成员才能阅读这条对话。早于该字段的老数据行默认视为私有，不会因为升级突然泄密。

同时，第一行 row.agent_id != agent_id 挡住了另一种越权：禁止拿着 A 专家合法的 thread_id 去请求 B 专家的聊天接口，防止上下文和工具权限跨专家污染。

session_key 是路由输入，不是凭证#

不同入口生成的 session_key 格式各自独立：

  • Web 工作台：<agent_id>:dashboard:<user_id>:dm
  • CLI 终端：<agent_id>:cli:<user_id>:dm
  • IM 通道：<agent_id>:<channel_kind>:<platform_session>:<dm|group>
  • 定时任务：默认回落到任务所有者的 dashboard 会话键，v1.0.3b6 起还可以写成 latest（跟随最新对话）或 thread:<thread_id>（钉死某一条历史对话，见 infra/cron/session_target.py）。

thread_id 本身不编码渠道来源，来源类型作为独立列存在线程表里。任何从客户端传入的 session_key 都只能当路由参数，服务端必须拿 JWT 解析出来的 user_id 重新校验专家与线程归属，绝不能因为字符串里拼了某个数字就放行。tests/integration/test_boundary_authz.py 专门把所有者、共享使用者、无权用户和管理员四种主体排成矩阵，测试专家读取、配置写入、线程订阅与取消的边界。

预建 LDAP 账号与用户组可见性#

企业内部署时，管理员往往希望在员工第一次登录前就把专家、知识库和技能包分好权限。v1.0.3b1 引入了按用户组限制技能包、知识库、连接器、模型、存储和专家的可见性；v1.0.3b3 又补上了预建 LDAP 账号能力，管理员可以提前建好账号并拉进对应用户组，员工首次用公司 LDAP 密码登录时直接继承预设分组和资源可见范围，不用等登录完再手工补权。

删除线程和删除专家，先清 checkpoint 再删表行#

沿着标识往下看，删除操作比创建更考验顺序。对话正文和图状态存在 Agent 的 checkpoint 存储里（本地 memory.sqlite 或 PostgreSQL 共享表），跟控制面的 threads 和 agents 表没有数据库级外键级联。

看 src/octop/infra/agents/memory/thread_cleanup.py 的顶部注释和执行顺序，Octop 定下了一条反直觉但非常稳的规则：先删 checkpoint，成功之后才删 threads 行。原因很简单：如果先删了 threads 表行，接着删 checkpoint 失败，这条对话在界面上消失了，磁盘或数据库里却永远留下一堆查不到的孤儿状态，用户想重试删除都没入口；反过来先删 checkpoint，失败了直接报错，对话还留在列表里，用户或管理员随时可以重试。

删除整个专家也照此办理：先遍历清理该专家所有线程的 checkpoint，再清除它的长期记忆命名空间（SQLite 删前缀表，PostgreSQL 在 octop_memory 等共享 schema 中按 namespace 删行），最后才删 agents 行和本机数据目录。此外，从 v1.0.3b1 起，如果某条对话正在流式回复中，接口会直接拒绝删除该对话，避免前台删表、后台还在写历史和 checkpoint 撞成脏数据。

存储与历史：六类数据平面、下线归档与安全清理

刷新页面后少了一段回复，或者删完一位旧专家磁盘空间一点没降，排查这类问题时最怕顺手找一个所谓的唯一数据库。在 Octop 里，数据按读写模式和一致性需求拆成了六个平面，而且在单机 SQLite 模式和集群 PostgreSQL 模式下的落盘位置差异很大。

为什么必须把图状态和展示历史拆开#

初学者常把 LangGraph 的 checkpoint 直接当成聊天记录库，跑两周就会踩进两个坑。第一个坑是上下文压缩：长对话触发 /compact 或自动裁剪后，checkpoint 里保留的是压缩摘要和后续图状态，如果前端直接读 checkpoint，用户会发现昨天的原始问答凭空蒸发了。第二个坑是查询形态：前端需要稳定分页、说话人标记、工具调用折叠卡片、本轮改过的文件增删行数（v1.0.3b6 新增）、错误状态和耗时轨迹，而 checkpoint 保存的是面向图恢复的序列化快照。

所以 Octop 把这两件事拆得清清楚楚：checkpoint 只管运行图恢复和 HITL 断点续跑；控制面里的 thread_messages 和 trajectory_events 表负责面向前端和审计的展示投影（由 infra/history/projection.py 维护）；长期提炼出的用户画像和事实记忆归 octop-memory；上传的文档切片和向量归知识库索引；SOUL.md、技能和生成产物归 BackendWorkspace。

SqlitePool 与 PostgresPool 的克制封装#

控制面的连接池封装在 src/octop/infra/db/pool.py。两个实现共用同一套 DatabasePool 协议（connect、transaction、close）和成对编号的迁移脚本（NNN_*.sql 与 NNN_*.pg.sql），但底层各有各的工程细节。

SqlitePool 用一把 threading.RLock 保护进程内唯一连接，建库时开启 PRAGMA foreign_keys = ON 和 PRAGMA journal_mode = WAL，POSIX 下把数据库文件权限设成 0600。这里有两处非常真实的生产踩坑记录直接写在了代码里：

  1. 事务固定用 BEGIN IMMEDIATE 而非延迟 BEGIN，如果用默认的延迟事务，先读后写时才去抢写锁，一旦另一条连接（比如 CLI 命令或多个 worker）在中间提交了事务，SQLite 会立刻抛 SQLITE_BUSY_SNAPSHOT，连 5 秒的 busy_timeout 都救不了。提前拿写锁让竞争者乖乖排队，把快照冲突扼杀在入口。
  2. Windows 下改为 PRAGMA synchronous = NORMAL（v1.0.3b3 修复），WAL 配合默认的 FULL 会在每条自动提交语句上调用 Windows 的 FlushFileBuffers，把应用和测试拖成龟速。只在 os.name == "nt" 时降为 SQLite 官方推荐的 WAL 设置 NORMAL，应用崩溃不损坏库文件，其他平台继续保持 FULL。

PostgresPool 则包了一层 _PgConnectionProxy，暴露与 SQLite 相似的 execute、executemany（v1.0.3b3 补齐适配）和 _CompatRow（同时支持列名和下标取值），并用简单的 qmark_to_pyformat() 把 ? 占位符替换成 %s。源码明确注明它不解析 SQL 字符串字面量，只服务于受控的仓储 SQL，不伪装成通用方言翻译器。

ADR 003：PostgreSQL 接管技能包与知识库#

在 v1.0.3b1 时期，哪怕你配了 PostgreSQL 控制面，技能包源文件和知识库索引依然死绑在 ~/.octop/skill-packages/ 和本地 index.sqlite 上。v1.0.3b3 落地 docs/adr/003-skill-package-kb-pg-storage.md 后，局面彻底变了：控制面驱动选定后，内容平面自动绑定，不再提供控制面用 PG 但知识库留本地的分叉配置。

控制面驱动 技能包源文件 知识库原文 知识库向量
sqlite 本地 skill-packages/ 本地 knowledge/<id>/docs/ 本地 index.sqlite
postgresql PG 表 skill_package_files PG 表 knowledge_files 同库 pgvector（knowledge_chunks）

ADR 003 做了一个很克制的选择：不造新的二进制打包协议，直接复用 octop-harness 的 PostgresBackend 形态（路径一行一文件、path + JSONB 内容），但分表与专家工作区隔离；技能包绑定到专家时，依然保持从 Store 复制进专家工作区的既有行为，不强迫专家改成复杂的 composite 挂载。另外，按 ADR 002 的约定，Octop 建表迁移绝不私自执行 CREATE EXTENSION vector，pgvector 扩展由部署时的初始化脚本或 DBA 提前装好。

为什么下线 history_v2#

上一版架构书曾花大篇幅介绍过默认关闭的分段历史库 history_v2.sqlite。它的本意是通过写入前提交保证流式历史不丢，但在产品演进中暴露出两个硬伤：它只支持 SQLite 控制面，和 PostgreSQL 多副本路线天然冲突；同时多出一套独立 SQLite 文件，让备份、在线恢复、跨库一致性和历史分页变得格外沉重。

因此在 v1.0.3b5 中，Octop 果断下线了 history_v2，删除了旧的 history/service.py 和 history/recorder.py，只留下 projection.py（消息投影）和 retire_v2.py（启动时单次迁回 thread_messages）。敢于把一个已经上线的复杂实验特性彻底收口退场，比硬撑着维护两套历史引擎健康得多。

v1.0.3b7 关键修复：PostgreSQL 孤儿 checkpoint 绝不误删#

控制面 threads 行和 checkpoint 处于不同存储层，异常崩溃或老版本缺陷可能留下没有对应 threads 行的孤儿 checkpoint。命令行 octop chats gc-orphans 就是干这件清理活的。

但在 PostgreSQL 模式下，这里藏过一个极其凶险的边界：octop_memory 的 PostgreSQL checkpoint 表是同 DSN 下所有智能体、甚至可能包含多台宿主实例共享的一张大表，而 LangGraph 原生 checkpoint 表结构本身并不带强归属外键（Octop 只能靠写入 checkpoint metadata->>'agent_id' 去反推归属）。如果某条记录缺标签、或者同库里别的智能体正挂着某个 thread_id，按单个专家的线程表一刀切去删，就会把其他智能体的正常对话直接清空。

v1.0.3b7 的 src/octop/infra/agents/memory/thread_cleanup.py（PR #2960）把这条风险焊死了：

if backend == "postgres":
    if dsn != control_dsn:
        skipped.append(SkippedCheckpoints(row.agent_id, "external_database", None, 0))
        continue
    if live_threads is None:
        live_threads = _all_live_threads(services)
    usage = _postgres_thread_bytes(dsn, row.agent_id)
    kept = [nbytes for tid, nbytes in usage.items() if tid not in live_threads]
    if kept:
        skipped.append(
            SkippedCheckpoints(row.agent_id, "postgres_report_only", len(kept), sum(kept))
        )
    continue

读懂这十几行就能抓住它的三条防护逻辑：

  • 如果该专家的记忆 DSN 和当前控制面不是同一个库，归为 external_database 直接跳过不扫描。
  • 即使在同一个控制面 PostgreSQL 上，先汇总全库所有专家的活跃线程集合 _all_live_threads()，绝不只拿单个专家的线程表做差集。
  • 最关键的是，就算传入了 --yes（apply=True），PostgreSQL 分支也永远只把统计出的孤儿线程数和字节数记入 skipped（原因 postgres_report_only），绝不执行 DELETE；只有独占文件的 SQLite 孤儿才会在 apply=True 时走 delete_stored_thread() 清理，并在空间充足时触发有界增量 vacuum（_DELETE_VACUUM_PAGES = 2000，整库 VACUUM 前还会检查磁盘剩余空间至少比库文件大 64MB）。

同时，针对 PostgreSQL 记忆表的日常瘦身，src/octop/infra/agents/memory/postgres_storage.py 走的是另一条安全路径：用 pg_try_advisory_xact_lock 按命名空间互斥，用 FOR UPDATE OF t SKIP LOCKED 每次最多锁 500 行超过 30 天的已拒绝候选或超过 14 天的流水线日志，先把精确的待删行刷盘备份成 0600 权限的 JSONL 并 fsync，再在同一事务里按 namespace + id 精准删除，绝不对共享表执行 VACUUM FULL 或触碰 checkpoint 与活跃记忆。

内容文件与系统运行材料两条路#

工作区目录里住着两类生命周期截然不同的文件：

  • 内容文件走 BackendWorkspace，调用方统一传工作区相对路径（如 SOUL.md、skills/foo/SKILL.md），目录列举默认用 "."，HTTP 路由收到前端传来的前导斜杠路径时先经 workspace_api_path() 归一化。用户上传聊天附件时，文件经 api/common/attachments.py 和 api/routers/uploads.py 落到 {workspace}/inbound/，后续聊天准备阶段只认受控的工作区路径引用，不拿浏览器临时预览 URL 当文件权威。
  • 系统运行材料放在 {workspace}/.octop/ 下（老专家的认证文件兼容 {workspace}/.octop-auth），包括 harness 托管的本地状态、sessions/*.jsonl 回退文件以及托管专家的链接清单。这个 system_files_path 对用户不可配置，在工作区首次初始化时自动建出。

即使内容平面已经切到远程对象存储，本机上的 workspace_dir 有时仍作为系统运行锚点存在。看到磁盘上有同名文件夹，不能想当然以为里面的文件就是权威副本。

多后端适配与 v1.0.3b3~b6 的新边界#

src/octop/infra/backend/adapter.py 和 resolver.py 把控制面里保存的存储后端配置行，翻译成 octop-harness 识别的 backend spec。截至 v1.0.3b7，Octop 支持的后端覆盖本地文件系统、local_shell、PostgreSQL 文件后端、S3、腾讯云 COS、火山引擎 TOS（v1.0.3b3 新增 tos_backend.py，可选依赖 tos>=2.9,<3）、Docker 沙箱、OpenSandbox（v1.0.3b3 补齐了文件操作桥接 opensandbox_mkdir.py）以及把多个后端按路径前缀拼起来的 composite 组合后端。

这里最容易混淆的一点，是把远程文件存储和远程代码执行混为一谈。把文件存进 COS 或 TOS 解决的是持久化位置和跨副本共享，并不能隔离 shell 命令执行；而 Docker 和 OpenSandbox 才涉及容器进程、资源配额（memory、cpus、pids_limit、allow_network）和执行边界。

另外从 v1.0.3b6 起，管理员可以在全局配置里限制创建专家时允许选择的存储后端，并且 v1.0.3b3 修复了创建专家时强制校验允许的存储根路径。在多副本 Kubernetes 集群里，这个开关非常实用：管理员可以直接禁掉容易随 Pod 销毁丢数据的本机临时盘，强制新建专家落在 PostgreSQL、S3/COS/TOS 或 OpenSandbox 上。

容器挂载的两次修正：为什么 b6 一刀切，b7 又放开了条件#

v1.0.3b6 到 v1.0.3b7 在 Docker 专家挂载宿主机目录这件事上经历了一次极具代表性的安全取舍，值得直接翻 src/octop/infra/backend/docker_spec.py 细看。

问题的起点很直白：如果 Octop 直接装在宿主机上（比如开发者的 Linux/macOS 机器或一台共享虚机），而 Docker 专家的配置允许传任意 volumes 给宿主机 Docker daemon，那普通用户只要在配置里把 / 或 /etc 挂进容器，就能借沙箱读穿整台宿主机，沙箱隔离形同虚设。因此 v1.0.3b6 直接把 Docker 专家的宿主机目录挂载全拦掉了。

但一刀切马上伤及了另一类正当部署：用户把 Octop 自己就跑在 Docker 容器里（通过 -v /host/projects:/workspace 提前由运维选定了允许暴露的宿主机目录），再把 Docker socket 挂进去跑 Docker 专家。在这种场景下，如果不把 volumes 透传给 Docker daemon，容器里的 Docker 专家压根碰不到运维已经明确授权的那几个项目目录。

于是 v1.0.3b7 在 docker_spec.py 的 omit_docker_volumes() 里改成了按部署环境区分：

def omit_docker_volumes(spec: Any) -> Any:
    if running_in_container():
        return spec
    if not isinstance(spec, dict):
        return spec
    kind = str(spec.get("type") or "").strip().lower()
    if kind == "docker":
        if "volumes" not in spec:
            return spec
        logger.warning("ignoring docker backend volumes; host mounts are not allowed")
        out = dict(spec)
        out.pop("volumes", None)
        return out
    if kind == "composite":
        # 递归剔除 default 和 routes 下每个子后端里的 volumes
        ...

逻辑非常干净：volumes 键可以原样留在存储配置里，但在真正装配给 harness 或做健康探测（enrich_docker_backend_spec）时，只有当 running_in_container() 为真（即 Octop 自身运行在 Docker/Podman 容器中，宿主机可见目录已由运维在容器编排层把关）才保留挂载；只要是裸机宿主安装，无论顶层是 docker 还是 composite 里的子路由，一律剥掉 volumes 并打告警日志。

同时，docker_spec.py 还控制着后台存储浏览页面的可见性（docker_spec_previewable()）：非 Docker 后端默认可浏览，Docker 后端只有在 sandbox_scope == "fixed" 或显式设了 previewable=True 时，才允许管理员的 /admin/backend 树浏览其文件，而专家自己的工作区预览不受此限。

别把 root_dir 当成真正的操作系统沙箱#

最后看一眼 src/octop/infra/utils/host_dirs.py 里一个极诚实的判断函数 host_jail_enforced()：

def host_jail_enforced() -> bool:
    if os.name != "posix":
        return False
    return _bwrap_on_path()

这段注释说得非常透彻：只有在 Linux 且系统 PATH 里存在 bwrap（bubblewrap）时，非根目录的 root_dir 才具备真正的操作系统级隔离。在 Windows、macOS 或没装 bwrap 的 Linux 上，配置一个受限的 root_dir 只能约束 Agent 自身文件工具的路径参数（同时 POSIX 下拒绝 /proc、/sys、/dev、/etc、/root 等敏感前缀），但子进程依然跑在 Octop 服务用户的真实操作系统权限下，UI 绝不能把它包装成安全沙箱。分清路径参数检查和内核级沙箱的差别，才不会在安全评审时给团队留下虚假安全感。

一次对话：从 WebSocket 入队到工具熔断与推送

用户按下回车却迟迟不见回字，新手往往直接去换模型或查 API Key，老手则会沿着一条请求穿过的六道关卡逐段排查：WebSocket 建连鉴权过了没有、线程订阅有没有赶在首个 chunk 发出前注册好、消息入队后走的是新回合还是在途追加（steer）、路由解析出的模型是不是已经失效、工具调用有没有触发熔断或审批暂停、最后历史记录和帧推送有没有落到正确的线程上。

下面沿着 /api/agents/{agent_id}/chat/ws 把一次完整回合拆开来看。

先把传输连接和任务执行拆开#

浏览器连上 /api/agents/{agent_id}/chat/ws 后，服务端在 src/octop/api/routers/chat/ws.py 里独立完成 JWT 校验和专家访问权核查，再把连接登记进 WebSocketHub。这条连接只管收发控制帧（user_turn、订阅、取消、审批响应）和接收下行推送，不亲自持有模型循环。

当收到一个 user_turn，src/octop/api/routers/chat/turn.py 的 prepare_dashboard_turn() 先把网页表单校验并归一化：调用 resolve_thread_id() 确认线程归属和会话绑定，验证本轮勾选的 MCP 和 Skill 列表，提取乐观渲染用的前端消息 ID（client_message_id_from_turn），把工作区附件转成结构化块，最后打包成 octop-gateway 定义的统一 InboundMessage，送进 ChannelManager.enqueue()。

这里的入队是进程内异步队列，用来让 Web、CLI、飞书、钉钉、Telegram 和 Cron 共用同一套消费管线，不依赖外部消息中间件。对于 IM 入口，下行 chunk 会经 src/octop/infra/gateway/process/stream_project.py 投影成各平台能发的 MessageEvent；对于 Web 工作台，则由 GlobalProcessor.iter_turn_chunks() 保持细粒度原生帧直接推送。

一个靠时序踩出来的修复：先订阅，再让出控制权#

ws.py 里藏着一条 v1.0.3b1 修过的经典异步竞态。从 v1.0.2 开始，Octop 支持对话进行中插话补一句（steer），不用等当前回合彻底结束。处理 user_turn 时，服务端要异步等待 steer 接纳判断。

如果代码写成先 await 接纳判断、再调用 hub.subscribe() 把当前 socket 加进线程房间，事件循环在 await 那一瞬间交出控制权，后台正在跑的回合恰好吐出前几个 chunk 往房间里广播，刚发消息的这个连接就会把开头几帧全漏掉。所以 ws.py 严格保证：线程 ID 确定之后，立刻同步执行 hub.subscribe()，然后再去 await 后续 steer 接纳或入队。这是纯事件循环调度问题，和模型响应快慢毫无关系。

GlobalProcessor 里的前置拦截与模型路由#

消息出队进入 src/octop/infra/gateway/process/processor.py 的 GlobalProcessor 后，并不是所有输入都会直奔 LLM：

  • 如果输入是斜杠命令（如 /compact、切换模型等），或者正好匹配当前线程挂起的 IM 文本审批口令（ApprovalUtterance），宿主会在进入模型循环前直接截流处理，走专门的 slash 或 HITL 恢复路径。
  • 如果本轮带了超长视觉图片，v1.0.3b3 起网关会在发给模型前先缩放长图，避免触发供应商尺寸限制报错。
  • 接着进入 _resolve_harness_model_route() 决定这轮到底调哪个模型。它的优先级是一条清晰瀑布：本轮显式覆盖或线程记录模型 → 校验是否仍可用且在当前用户组权限内（失效或被停用的旧模型自动丢弃，防止死卡在已删模型上） → 专家显式默认模型 → 用户偏好模型 → 系统兜底模型 → 仍无则交给 harness 自动路由（AUTO）。如果本轮含多模态图片而选中模型不支持视觉，自动升级到具备视觉能力的候选模型。v1.0.3b5 还统一了 IM 通道的推理强度覆盖（_resolve_reasoning_overrides），让飞书和 Telegram 对话与网页端行为一致。

如果是托管专家（kind="managed"），此时还会调用 managed_mcp_specs() 组装外部连接器和 6 个本地回环 MCP 地址，并根据 acp/session_modes.py 算出本轮要下发的 session/set_mode 和审批模式。

执行循环里的三道护栏：熔断、故障转移与记录#

进入 AgentManager.stream() 后，回合在 octop-harness 的运行图里向前推进，宿主靠几层中间件和观察器把现场托住：

  • 连续相同调用熔断：第 4 章读过的 ConsecutiveToolCallMiddleware 在每次模型返回 tool_calls 后检查签名连击数。同一工具同一参数连撞超过上限（默认 40 次），直接写错误 ToolMessage 与 [tool_call_repeat] 结束标记并 jump_to="end"，避免无限空转；只要换了工具、改了参数或回了纯文本，计数立刻归零。
  • 受控模型故障转移：SafeModelFailoverMiddleware 只在自动路由且命中可恢复异常类型时，按健康状态（providers/health.py 的半开探测与隔离机制）、多模态要求和上下文窗口容量挑选下一个健康候选模型，不会在用户显式锁死模型或发生业务逻辑错误时胡乱切模型重跑。
  • 边流边记与产物去重：流式循环中，UsageTracker 累计包含缓存 token 在内的用量，TurnHistoryTracker 收集消息增量并在回合节点写回 thread_messages，同时记录包含模型实际收到系统提示词在内的 trajectory_events（v1.0.3b2 新增）。工具执行产出新工作区文件时，会被转换成附件帧并去重，同时 v1.0.3b6 起汇总本轮改过的文件路径、所在目录和增删行数展示给对话界面，而且确保更早回合生成的文件不会在新回合里被重复发送一遍。

断线、取消与失败各自什么语义#

把这三种非正常结束混成一件事，系统状态就会彻底糊掉：

  • WebSocket 断开：ws.py 的清理块明确只注销当前连接订阅，绝不取消正在运行的后台回合。用户合上浏览器一分钟后再回来，任务可能已经跑完并落入历史，或者仍在运行等待重新订阅接上后续帧。
  • 显式取消（cancel）：校验线程归属后，标记 steer 取消、丢弃排队内容，并向 AgentManager 发送取消信号终止当前计算。但取消挡不住已经发出去的外部副作用：已经发出的邮件、已经删掉的云盘文件不会因为点停止按钮自动撤回。
  • 上游异常失败：processor.py 靠 stream_ok 标志和 finally 收尾区分完成与异常。出错时往客户端推送错误事件、在历史里按未完成或失败形态落账，不会把一句异常提示伪装成一条正常的 AI 回答。

记忆与知识库：命名空间维护、图谱扩展与重排序

用户上周在对话里交代过一句“以后周报默认用中文表格”，团队又往系统里上传了三十份产品规范 PDF。两者都会在回答问题时被召回进上下文，但工程上绝不能塞进同一张表：前者是随对话演化的个人偏好与事实提炼，允许用户手工编辑用户档案和强记忆、遇到冲突弹窗确认；后者是有明确文件夹层级、版本号和用户组可见权限的文档证据，需要解析、切片、建索引并带出处引用。

Octop 把这两条检索路径彻底分开：长期记忆交给独立运行库 octop-memory（>=1.0.5），文档知识库留在宿主 src/octop/infra/knowledge/ 下，并在 v1.0.3b3 到 v1.0.3b6 连续补齐了 pgvector 存储、二阶段重排序和实体图谱检索。

Memory 后端解析与 PostgreSQL 命名空间瘦身#

src/octop/infra/agents/memory/backend.py 的 open_memory_kwargs() 负责把专家配置翻译成 octop-memory 需要的 (namespace, backend, backend_config)。默认策略紧跟控制面驱动：

  • SQLite 控制面下，每个专家把记忆和 checkpoint 放在自己系统目录下的 memory.sqlite，命名空间按 agent_<agent_id> 规整化。
  • PostgreSQL 控制面下，除非该专家显式覆盖为本地 SQLite，否则默认复用同一条 PostgreSQL DSN，所有专家共享 octop_memory schema 下的 11 张表（raw_events、candidates、atoms、entities、aliases、entity_pages、memory_nodes、thread_active_entities、journal、episodes、digests），严格靠 namespace 列隔离。

有两点很容易在运维时踩坑。第一，记忆提炼使用的辅助抽取模型可以与日常聊天模型分开配置，因此聊天正常但长期记忆停止生长时，要单查抽取模型的可用性与运行开关（v1.0.3b5 专门修了捕获和召回运行开关被覆盖的问题，v1.0.3b3 升级 octop-memory 后长会话改为分批提炼且重启不重跑）。第二，前端快速切换专家查记忆时，旧请求可能比新请求晚返回，v1.0.3b7 在界面侧加上了过期响应丢弃，防止旧专家的记忆列表把当前页面盖掉。

共享 PostgreSQL 上做记忆空间整理最怕锁死整张表。第 6 章提到的 infra/agents/memory/postgres_storage.py 设计了一套边界极严的在线维护协议：

  1. 巡检阶段开 REPEATABLE READ, READ ONLY 事务，设 15 秒语句超时与 1 秒锁超时，按命名空间精确统计 11 张表的行数和列字节大小。
  2. 清理阶段先抢占按命名空间哈希的事务级咨询锁 pg_try_advisory_xact_lock，把并发触发的维护任务折叠掉。
  3. 每次只挑最多 500 行超过 30 天且无原子引用的已拒绝候选，以及超过 14 天的 6 类流水线日志，加 FOR UPDATE OF t SKIP LOCKED 避开在途写入，排除衍生全文检索列 fts_tsv，写完备份 JSONL 并 fsync 之后才执行精准 DELETE，全程不动活跃记忆、决策日志、checkpoint，也绝不跑锁表的 VACUUM FULL。

知识库的双存储平面：SQLite Sidecar 与 PGVector#

src/octop/infra/knowledge/plane.py 根据控制面驱动动态决定打开哪一套索引实现：

  • SQLite 模式（index.py）：每个知识库对应一个本地 index.sqlite sidecar，文档切片文本、元数据和二进制 embedding 存在 chunks 表中，replace_doc_chunks() 在单库事务里先删旧片再插新片，查询时在进程内扫描计算余弦相似度。这种设计零外部依赖，适合个人和小团队，数据量扩大时需要盯着内存与扫描延迟。
  • PostgreSQL 模式（pg_index.py，ADR 003）：知识库原文进 PG 文件表，切片和向量进 pgvector 支撑的 knowledge_chunks 表，支持多副本同时读写和共享。文档解析本身支持本地 OCR（完整镜像内置 rapidocr + pymupdf）、firecrawl-anydoc 转换、以及本地 ONNX 嵌入（fastembed）或远程供应商嵌入模型（v1.0.3b3 修复了远程批量 embedding 返回乱序的缺陷）。此外，v1.0.3b5 支持在知识库文件夹之间移动文档和子目录。

v1.0.3b6 的三段检索管线：向量召回、二阶段重排序与实体图谱#

翻开 src/octop/infra/knowledge/retrieve.py 的 _retrieve_context_sync()，能看到 v1.0.3b7 的知识库检索已经进化成一条带权限前置和双路增强的清晰管线：

校验知识能力与 query → 生成 query embedding
  → 取当前主体可见知识库集合（管理员全量，普通用户走 list_visible）
  → 与本轮选中的 knowledge_base_ids 取交集
  → 仅在 status == "ready" 且非目录的文档范围内检索：
      1. 向量召回：开重排序时扩召 candidate_count(k)（4*k，夹在 20~50），否则取 k=8
      2. 实体图谱扩展（可选）：open_knowledge_graph() 查关联实体事实与相关片段
  → 按相似度初排；若启用重排序，调供应商 /rerank 接口精排
  → _with_graph_passages() 按配额混入图谱关联段落（最多占 k/4）
  → 在 char_budget=6000 字符预算内格式化正文、图谱事实（最多占预算 1/5）与引用标记

这里有三个设计细节非常值得拆出来看：

  1. 权限过滤一定在召回之前：先算 visible_by_id 再查对应知识库的索引，绝不把所有知识库混搜一遍再指望提示词让模型别引用无权文档；同时只认 status == "ready" 的文档，避免解析失败或索引半成品污染回答。
  2. 重排序（rerank.py）的候选扩张与优雅降级：向量检索偏召回，容易把字面相似但答非所问的段落排前面。开启重排序后，系统先按 max(k, min(max(k * 4, 20), 50)) 多捞一批候选，再发往配置好的供应商 /rerank 接口（兼容 Jina、Cohere、SiliconFlow、vLLM、Xinference 和 TEI 格式）让精排模型同时看问题和段落打分。如果重排序供应商超时或报错，调用方记日志并直接退回向量原序，不拖垮整轮对话。
  3. 实体图谱（graph.py、graph_extract.py、graph_store.py）作为增量通道：图谱查询包在独立的 _expand() 捕获块里，挂了就退化为纯向量检索；成功时用固定比例（段落不超过 k/4，事实文本不超过字符预算的 1/5）把跨文档实体关联补进上下文，防止图谱事实把原始证据挤出窗口。

最后要留意一个有意为之的取舍：外层的 retrieve_context() 把整个同步检索丢进线程池执行，遇到任何未捕获异常都会记一条警告日志并返回空字符串。这样做的好处是嵌入模型欠费或网络抖动时，聊天不会直接崩溃；代价是模型会失去私有知识证据，退化成靠通用训练数据作答。如果你的业务场景要求严禁脱稿回答，需要在产品侧把检索失败显式透出，而不是默认 fail-open。

工具与扩展：Skill、Plugin、Connector 与 MCP OAuth

想让专家按公司模板写周报、想给对话界面加一个富交互卡片、想连上公司内部文档或自建 MCP 服务器，这三件事如果全都笼统叫成装插件，权限边界和故障面很快就会失控。Octop 把扩展能力分成了四层，每一层的执行位置、信任级别和授权粒度都不一样。

扩展机制 核心作用 典型载体 风险边界
Skill（技能与技能包） 给 Agent 提供按需读取的操作规程与脚本文档 SKILL.md 与配套文件树 属于提示词和工作区文件，不能代替服务端鉴权
Plugin（插件） 往宿主或运行库注入 Python 代码扩展 工具、中间件、IM 通道、富 UI 载荷 运行在宿主进程权限下，内置插件默认关闭
Connector（连接器） 把某用户的外部服务账户封装为受控能力 加密凭证、实例配置、工具白名单 按用户和共享范围隔离，共享连接器仅创建者可改
MCP 标准化的工具发现与调用协议 streamable_http / stdio server 配置 只管传输协议，不自带最小权限模型

技能包与插件：分发、隔离与大载荷卸载#

技能包（Skill Package）在 v1.0.3b1 到 v1.0.3b6 之间补齐了完整链路：支持按用户组共享、在工作台直接用文件树编辑、打包导出 ZIP 跨机迁移（还可由创建者关闭打包下载权限）。按 ADR 003，PostgreSQL 模式下技能包源文件存入 skill_package_files 表，绑定给原生专家时复制到专家的 BackendWorkspace；绑定给托管专家时，则通过 managed.py 的 link_managed_skill_packages() 在 Runner 自己的目录（如 .claude/skills 或 .opencode/skills）下建符号链接或 Windows Junction，并用清单追踪归属。

插件（src/octop/infra/agents/plugins/manager.py）的信任级别完全不同，代码直接跑在 Octop 进程里。PluginManager 启动时播种内置插件（默认关闭，需要显式启用），从 v1.0.3b3 起专家与插件市场目录彻底从安装包剥离、改为按需从远程市场加载，上传和 ZIP 解压有严格的体积上限防炸弹攻击。在 PostgreSQL 多副本模式下，已安装的插件和头像也同步进共享存储，避免各副本能力不一致。

插件常会返回体积庞大的 octop_ui 富界面数据（如表格、图表或交互面板）。如果原样塞进模型上下文，几轮对话就会把 token 预算吃干；如果直接丢掉，前端又画不出来。OctopUiOffloadMiddleware（设计说明见 docs/octop-ui-payload-offload.md）专门拦截这类特定信封，把大载荷卸到 UI 侧消费，只留精简摘要给模型和外层中间件。它服务于明确的插件信封协议，不是对任意工具结果做无差别压缩。

连接器的四种运行模式与 RAGFlow 接入#

内置连接器目录定义在 src/octop/infra/connectors/catalog.json（包含腾讯文档、企查查、语雀、Obsidian、Agent Mail、钉钉 CLI 以及 v1.0.3b2 新增的 RAGFlow 知识库连接器），按执行位置分成四种模式：

  • remote：运行库直接连向供应商托管的远程 MCP 地址。
  • gateway：使用 Octop 进程内的 Python 适配器执行，无需拉起外部进程。
  • internal：由 Octop 自己在 /api/internal/mcp 托管一个本地 HTTP MCP 入口，供运行库接入。
  • stdio：在 Octop 所在宿主机上拉起子进程，通过标准输入输出通信。

同样叫连接器，网络超时、凭据传递、代理配置和子进程回收完全不同。装配时还要严格区分三层集合：系统安装了哪些连接器、当前用户授权了哪些实例、这位专家在本轮允许调用哪些工具。v1.0.3b3 和 v1.0.3b4 连续修了两个高频边界：共享连接器只允许创建者编辑，防止使用者改坏公共凭证；共享专家使用查看者自己的自定义 MCP 时，会通过 shared_mcp_server_name() 正确映射到 harness，不串名也不越权。

自定义 MCP 的 OAuth 授权与 RFC 8414 路径发现#

越来越多远程 MCP 服务不再只收静态 API Key，而是走 OAuth 2.0 授权。Octop 在 src/octop/infra/connectors/custom_mcp.py 和 oauth/ 下实现了完整的自定义 MCP 接入链，并在 v1.0.3b5 与 v1.0.3b7 补齐了两个企业内网和 SaaS 常见的痛点。

第一，面向不支持动态注册的服务商提供手动 OAuth 应用凭证（v1.0.3b5）。标准 MCP 授权依赖动态客户端注册（DCR），但不少 OAuth 服务商要求提前在开发者后台建好应用拿到 client_id 和 client_secret。oauth/mcp.py 的 manual_client_metadata() 允许用户填写手工授权地址与令牌地址，同时用 validate_https_url_resolved() 做 DNS 解析后的 SSRF 拦截；公网远程 MCP 强制 HTTPS，本地回环和内网局域网 MCP 则放宽允许 http:// 方便内网自建工具联调。

第二，带路径的 MCP OAuth 按 RFC 8414 规范发现元数据（v1.0.3b7，PR #3004）。当一个 OAuth Issuer 带了子路径（例如 https://auth.example.com/realms/tenant），旧写法简单在末尾拼 /.well-known/oauth-authorization-server 会直接吃 404。src/octop/infra/connectors/oauth/mcp.py 的 fetch_authorization_metadata() 按 RFC 8414 第 3.1 节把 .well-known 插在域名与路径之间：

parsed = urlparse(issuer)
issuer_path = parsed.path.rstrip("/")
metadata_url = (
    f"{parsed.scheme}://{parsed.netloc}/.well-known/oauth-authorization-server{issuer_path}"
)

配合 oauth/discovery.py 里按 RFC 9728 顺序探测 /.well-known/oauth-protected-resource{path}、根路径以及 401 WWW-Authenticate 响应头里的 resource_metadata，无论是 Keycloak/Auth0 这类带租户路径的身份提供商，还是标准根域名 MCP 服务，都能自动发现授权端点，而且所有元数据里声明的 authorization_endpoint、token_endpoint 和 registration_endpoint 都必须通过 host_allowed_for_issuer() 与 SSRF 检查，防止恶意服务器借元数据重定向打向内网地址。

v1.0.3b7：托管专家如何通过 6 个回环 MCP 消费宿主能力#

原生专家跑在 Python 进程内，可以直接调用知识库、定时任务和插件函数；可托管专家（OpenCode、Claude Code、Codex 等）跑在独立的外部进程里，怎么才能共享同一套 Octop 能力？

v1.0.3b7 在 src/octop/infra/agents/acp/turn.py 和 mcp_tools.py 给出的方案非常巧妙：不改外部 Runner 源码，而是把 Octop 内部工具包装成最多 6 个按回合授权的本地 HTTP 回环 MCP 服务，在 session/new 和 session/load 时作为 mcp_servers 下发给外部 Runner：

  1. octop-knowledge：携带一次性或按作用域复用的随机 token（KnowledgeScope 绑定 user_id、is_admin、勾选的 knowledge_base_ids 和 locale），让外部 Runner 按同样权限检索知识库。
  2. octop-agents：把 ask_agent 等专家回调工具暴露出去，让托管专家也能呼叫 Octop 里的其他专家协作。
  3. octop-files：暴露 send_file_to_user，让外部 Runner 把工作区里生成的文件直接推回给网页或 IM 用户。
  4. octop-cron：暴露 cronjob_create/list/update/delete，并在回合提示词里明确叮嘱 Runner 别用它自带的会话内临时定时工具（那些任务不会出现在 Octop 的任务列表里）。
  5. octop-memory：仅在该托管专家显式打开记忆开关时挂载。
  6. octop-plugins：把当前专家已启用的插件工具自动转成标准 MCP JSON Schema，通过 var_child_runnable_config 注入上下文后供外部 Runner 调用。

此外，在 ask 或 plan 只读对话模式下，_connectors_allowed() 会自动跳过外部连接器，并针对 ACP 协议自身不支持按工具名过滤的限制，用 _tool_limit_note() 在回合提示中明确告知 Runner 每个连接器仅允许调用的白名单工具。

多 Agent 团队：共享展示时间线，隔离执行状态

把调研、法务审核和文档汇总交给三位专家一起干，最偷懒的做法是让三个模型轮流往同一条消息列表和同一份 checkpoint 里写内容。不出三轮就会乱套：谁的工具结果归谁、A 专家的私有工作区和记忆会不会漏给 B 专家、点停止按钮到底停哪一个、成员刚回复完结果该回推给网页还是飞书群。

Octop 在 docs/expert-teams.md 里定下了一条很清醒的架构原则：用户看见的是一条共享房间时间线，底层每个专家各自维护独立的 checkpoint、工作区与长期记忆。

主持人是特殊专家，不是一套平行表结构#

在数据模型上，专家团队并没有另起一套复杂的独立实体系统。团队主持人本身就是 agents 表里 kind = "team" 的一条专家记录，团队编制（成员列表、分工说明等）存在主持人工作区的 .octop/manifest.json 里，复用同一套 AgentManager 生命周期、分享权限和会话体系。

区别只在能力边界：主持人的职责是拆解任务、通过 TeamDispatchBriefingMiddleware 向成员下发改写后的任务简报并收尾总结，不直接挂载完整的文件修改、浏览器控制和外部 MCP 执行工具；被编入团队的成员依然是独立的一等专家，同一位专家可以同时加入多个团队。

一个房间，多份独立 checkpoint#

当用户在团队房间（会话 ID 即主持人的 thread_id）里发言，平台为房间内的不同角色分配各自隔离的图状态键：

房间展示时间线 = 主持人 conversation_id
  ├── 主持人 checkpoint：conversation_id
  ├── 成员 A checkpoint：conversation_id~member_a
  └── 成员 B checkpoint：conversation_id~member_b

成员各自使用自己的 BackendWorkspace 与 octop-memory 命名空间
成员流式输出经房间转播，附带明确的说话人（agent）标识，同步到 Web 与 IM

展示共享与状态隔离分开之后，好处立竿见影：

  • 成员加入团队，不会自动获得读取同事私有工作区或私有长期记忆的权限；团队级准则和汇总记忆留在主持人这一侧。
  • 主持人把群聊背景和本次交付目标整理成明确派工简报发给成员，成员干完活只把结果交回房间，不把中间几十步探索工具调用全倒进主持人的上下文窗口。

异步派工、成员并行与回叫串行#

团队协作有两种调用节奏：普通专家之间互相调用（ask_agent）以同步等待返回为主，托管专家也可以通过第 10 章的 octop-agents 回环 MCP 发起同样的专家回调；而团队主持人向成员派工则是异步的，主持人派完活立刻释放当前流，等成员跑完后由平台自动回叫主持人做下一轮汇总。

异步回调靠 TeamManager 和 GlobalProcessor（实现 TeamProcessor 协议）串联。每条派工任务都会带上 source_agent_id、source_thread_id、目标成员和 job_id，确保几分钟后成员交付结果时，平台准确知道该写回哪个房间 checkpoint，并通过 on_reply 把消息推回网页或对应的 IM 群聊。

并发调度遵循两套串行粒度：inbox 按被调用者（callee）协调，同一个成员收到的多条任务串行执行，不同成员之间可以并行跑；成员完成后回叫主持人时，则按源 thread_id 串行排队，避免两位成员同一秒完成把主持人总结流写花。成员在干活时可以同步询问另一位同事，但不允许异步再往群里拉新成员，防止无限套娃。

TeamJobTracker：按 job_id 做幂等在途记账#

团队正有成员在后台跑任务时，如果管理员突然把该成员移出团队或直接删掉这位专家，在途回调回来就会找不到目标。src/octop/infra/agents/teams/jobs.py 里的 TeamJobTracker 专门记录活跃任务计数，挡住这类破坏性操作。

看它的 begin() 实现：

def begin(
    self,
    team_agent_id: str,
    member_agent_id: str,
    job_id: str | None = None,
) -> None:
    key = (team_agent_id, member_agent_id)
    with self._lock:
        if job_id:
            if job_id in self._jobs:
                return
            self._jobs[job_id] = key
            return
        self._counts[key] = self._counts.get(key, 0) + 1

以 job_id 为键做去重比简单加减整数稳得多：同一条任务因为重试或状态重放重复触发 begin 时不会把计数加两遍，结束时按 job_id 摘除也不会减成负数。同时源码注释也坦诚写明了它的边界：TeamJobTracker 是进程内字典加线程锁，进程重启就归零，它不提供跨进程或跨重启的任务 fencing。

点停止按钮，究竟停掉了谁#

这是多 Agent 界面里最容易让用户困惑的一条边界，也是 docs/expert-teams.md 明确写死的行为：用户在 Dashboard 点取消，只取消主持人当前的流；已经排队或正在运行的成员任务不会被一并强杀，成员跑完后依然可能把结果回传并唤醒主持人。

如果业务方要求一键急停整个任务树并且禁止任何后续外发，光在前端隐藏成员气泡没用，必须在服务端引入整棵任务树的取消传播、回调抑制和工具侧拦截。了解当前的真实停止语义，比把既有行为误解成页面漏消息重要得多。

团队与 Subagent 别混着用#

仓库里同时存在 infra/agents/subagents/（子 Agent）和 infra/agents/teams/（专家团队）。两者定位不同：子 Agent 是单个专家运行时内部临时派生出的子任务执行体，适合短平快的局部拆解；专家团队编排的是拥有独立账号归属、工作区、知识库、连接器权限和长期记忆的一等专家。能用单个专家加子 Agent 解决的流程，没必要硬建三四个长期专家来维护编制。

安全边界：MFA、权限分离、审批串行与云凭证隔离

给 Agent 接上 shell、浏览器、外部连接器和云主机 API 之后，安全问题不再停留在登录页面。一个真实请求至少会撞上五道不同的门：身份认证、资源与用户组授权、工具审批（HITL）、执行与网络边界、以及静态凭证保护。这五道门互相补位，任何一道都不能替代另一道。

第一道门：JWT、Setup 锁定与 TOTP / Passkey MFA#

所有 HTTP /api/ 请求首先经过两层中间件：setup_lockdown.py 在系统尚未创建任何用户时锁死除安装向导和健康检查外的一切接口，返回 setup_required；系统初始化完成后，jwt_auth.py 对非豁免路径校验 JWT 并将已认证用户挂到 request.state（错误文案按 Accept-Language 本地化）。WebSocket 路由不会自动继承普通 HTTP 中间件的保护，因此在 ws.py 建连阶段会独立完成一次完整的 token 校验与资源鉴权。

从 v1.0.3b2 开始，Octop 在 src/octop/api/routers/auth_mfa.py 和迁移 025_user_mfa 中正式落地了多因素认证与会话加固：

  • TOTP 与 WebAuthn Passkey：支持一次性动态口令、硬件或系统通行密钥二次验证以及一次性恢复码；同时支持无密码 Passkey 登录，但该开关默认关闭，需管理员在应用设置中显式开启。
  • 高危配置二次认证（Reauth）：增删 TOTP 或注册 Passkey 前，必须先调用 /api/auth/mfa/reauth 再次验证密码（兼容本地账号和 LDAP 绑定限流）换取短效 reauth_token。
  • 会话续期与强制登出：记住登录支持自动续期，而修改密码会立即让其他设备的旧会话失效；老数据库升级时若缺少 MFA 表会自动补齐，防止升级中断登录。

第二道门：可见、可用、可改三权分离#

登录成功只说明系统认识你是谁，不代表能碰别人的资源。Octop 把资源权限细分成三层：

  1. 页面与功能级权限：v1.0.3b1 起权限按工作台 Tab 拆分并支持按组折叠，例如云主机页的路由 api/routers/cloud.py 直接挂载了 Depends(require_permission("cloud"))。
  2. 用户组资源可见性：技能包、知识库、连接器、模型、存储后端和专家都可以按用户组限定可见范围；共享连接器只有创建者能修改配置。
  3. 专家与线程两级校验：第 5 章拆解过，require_agent_row 放行所有者、管理员和分享对象，require_agent_owner_row 锁死配置写入权，resolve_thread_id 和 thread_visible_to 把私人线程与显式共享对话区分开。

第三道门：HITL 审批与重叠 ACP 权限串行化#

危险工具需要人工确认时，运行图在中断点挂起。src/octop/infra/gateway/hitl/coordinator.py 和 infra/agents/security/hitl_session.py 把待审批动作绑定到具体的 pending_id、用户、专家和线程，协调网页弹窗（恢复走 SSE）、CLI 提示和 IM 文本回复三种入口，同时受线程级执行锁保护，避免同一个中断点被并发恢复。

审批设计里有一条铁律：批准必须绑定已保存的参数快照，而不是只绑工具名。假如界面展示给用户确认的是“发邮件给 A”，如果恢复接口允许重新塞入一个收件人 B，审批就成了摆设。同样，审批管的是放行未来的执行，取消管的是终止当前计算，已经发出去的外部写操作无法靠事后点取消自动撤回。

到了 v1.0.3b6，在对接托管编程 Agent 时冒出了一个非常隐蔽的并发审批 Bug（PR #2994）：Cursor CLI 可以在同一回合里连续抛出两个重叠的权限请求（比如同时发起两次 WebSearch）。底层的 ACPHostedClient 内部只保存单个 future 和单个待处理权限，第二个 request_permission 进来直接覆盖了第一个 future，等用户点同意后，只有第二个被唤醒，第一个永远挂死，整轮对话卡在开场白再也走不完。

src/octop/infra/agents/acp/permissions.py 用不到 30 行代码干净利落地修掉了这个问题：给每个 ACPHostedClient 实例动态挂一把 asyncio.Lock（_octop_permission_lock），包装 request_permission，强迫同一客户端上重叠到达的权限请求排队挨个等用户确认。

第四道门：容器挂载、SSRF 与静态加密#

在执行和网络层面，Octop 叠了四块互不替代的防护板：

  • Docker 宿主机挂载策略（v1.0.3b6~`b7`）：如第 7 章所析，裸机安装时 omit_docker_volumes() 强制剥离所有 docker 和 composite 配置里的 volumes，堵死普通用户把宿主机敏感目录挂进沙箱的路；只有当 Octop 自己跑在容器内、暴露目录已由运维在宿主机容器层收敛时，才允许向 Docker 专家透传挂载。
  • 出站 SSRF 防护（infra/utils/ssrf_guard.py）：自定义 MCP、OAuth 发现、元数据端点和回调全部校验公网 HTTPS 与 DNS 解析后的真实 IP，阻断私网与链路本地地址探测（仅显式允许本地/局域网自建 MCP 跳过私网禁令）。
  • 静态密钥加密与日志脱敏：从 v1.0.3b1 起，控制面保存的各类连接器与供应商密钥改为 Fernet 加密落盘，同时兼容平滑读取旧明文；server.py 在常规日志级别压低 httpx/httpcore 输出，避免带查询参数密钥的完整 URL 刷进日志文件。
  • 工作区边界与插件信任：记住 host_jail_enforced() 的结论，无 bwrap 的非 Linux 环境不具备内核级文件系统隔离；插件代码运行在宿主进程内，只应安装可信来源的插件。

第五道门：腾讯云 CVM 凭证按用户隔离与 Bridge 隧道白名单#

v1.0.3b4 上线了工作台云主机页（src/octop/api/routers/cloud.py），让用户授权腾讯云账号后在界面里查看 CVM 实例监控并交给常驻运维专家巡检。在多用户和多副本部署下，云账号凭证如果混用或落在本地单机文件，会产生严重的越权与串号风险。

v1.0.3b4 和 v1.0.3b6 连续把这两条口子补齐：多副本部署时腾讯云授权改存共享控制面（open_cloud_credential_store 走 secret_repo），单机仍兼容本地文件；同时登录态与本地 tccli 镜像凭证严格按用户 ID 隔离（tccli_credential_path_for_user），绝不让 A 用户的云操作凭据被 B 用户或 B 用户的专家顺走。

而在跨实例协同场景下，src/octop/infra/bridge/tunnel_policy.py 对 Bridge HTTP 隧道实施默认拒绝策略：只放行白名单里明确定义的专家对话、只读 composer 和浏览器视图等路径与方法，所有未知管理路径一律拦下。并且隧道对端严格以对端连接账号的身份执行鉴权，本机的 user_id=7 绝不会直接当成远端的 user_id=7。

前端状态机：离线订阅、五道恢复门与历史竞态

写一个简单聊天页只要维护一个 messages 数组，收到 token 就往最后一条拼字，收到 done 就解锁输入框。但放到 Octop 的真实对话里，这套玩具写法几分钟就会崩：用户切去设置页再切回来，在途流状态全丢了；工具执行 40 秒没吐字，前端误以为断线把气泡封死了；团队房间里成员 A 刚吐完 done，主持人还在汇总，输入框就被错误解锁了；下拉刷新历史请求慢半拍回来，把屏幕上刚生成的新回答一把冲掉。

Octop 的 React 18 + TypeScript 前端（dashboard/）之所以把聊天核心做成一台独立的外部状态机，就是为了把这些并发时序锁死。

为什么把 chatStore 搬出 React 组件树#

打开 dashboard/src/pages/Chat/hooks/chatStore.ts，最核心的设计决策写在开头：WebSocket 实例、流式累计消息、在途说话人集合和订阅状态全部放在模块级 store 里，React 页面组件只通过快照订阅读取状态。

这样一来，用户在工作台里从对话页切到知识库、云主机或设置页，聊天组件被 React 卸载，底层 WebSocket 和累计缓冲区纹丝不动；切回聊天页时组件直接接上最新快照，屏幕不闪烁也不丢字。同时要分清边界：这个模块级 store 只跨越单页应用内部的路由切换，页面真正刷新或关掉浏览器后，仍然要靠服务端历史接口和 turn_active 标志重新接轨。

另外从 v1.0.3b5 起，服务重启升级后前端会主动清理 Service Worker 缓存再重载（PR #2901），避免旧版静态 JS 与新版后端协议字段错位；Monaco 编辑器资源也改为从同源提供（v1.0.3b3），不依赖外网 CDN。

帧归属与多说话人合并#

服务端推送下来的原始帧，经过 dashboard/src/utils/parseHarnessChunk.ts 统一翻译成前端事件，再由 frameThread.ts 决定它该落进哪条线程的缓冲区。这里有三个容易踩坑的边界：

  • 同一条 WebSocket 上不止一位说话人：团队房间里，主持人和多位成员的流通过同一条房间订阅推下来，前端必须严格按帧里的说话人标识分别归并气泡，成员的 done 事件只能封口该成员的气泡，不能把仍在活跃状态的主持人或整条房间流误判为结束。
  • 本轮改动文件清单：v1.0.3b6 起，对话流会把本轮编辑过的文件路径、所在目录与增删行数汇总展示在聊天区，让开发者不用切终端就能核对原生或托管专家到底动了哪些文件。
  • 多方同时共享会话防重叠：v1.0.3b5 修复了共享对话场景下并发回复重叠和消息顺序错乱的问题，结合前端乐观渲染生成的 client_message_id（后端在 turn.py 原样校验并沿用），保证用户提问和模型回复顺序对齐，也避免已经结束的一轮在历史加载后再重复追加一次（v1.0.3b2 修复）。

wsResumeGate.ts 里的五道恢复门#

dashboard/src/pages/Chat/hooks/wsResumeGate.ts 是整套前端里含金量最高的小模块，全文件只有一百多行，把弱流式恢复拆成了五个纯函数门禁，每个门禁都直接对应一种线上事故：

门禁函数 解决什么问题 关键常量与判断条件
shouldResumeStreamAfterClose 意外断线后要不要自动重订阅 非主动关闭、正在流式、线程有效、未超 MAX_STREAM_RESUME_ATTEMPTS = 8、且当前标签处于聚焦状态（后台标签不疯狂重连）
shouldProbeActiveTurn 打开历史页时要不要探测在途任务 仅在本地 isStreaming 或服务端历史返回 turn_active === true 时探测，绝不靠猜最后一条消息像不像没说完
shouldBlockHistoryRefresh 下拉刷新历史把在途新回复冲掉 仅当 socket 仍存活且存在正在生成的流、活跃说话人或 streaming 气泡时拦截；断线状态放行恢复路径
shouldForceSealStream 断线太久连不上，气泡永远转圈 仅在无活 socket、聚焦状态且距上次活动满 STREAM_STALE_WITHOUT_SOCKET_MS = 20_000 毫秒才强制封口；活 socket 豁免，绝不误杀长工具调用
shouldEmitStreamResumeNotice 重连成功后的提示控制 仅在非首次重连（resumeAttempt > 0）且服务端确认 turnActive 时弹一次提示

把这五个判断从巨大的 React 组件和 store 里抽成纯函数，有两个立竿见影的收益：第一，不会再有人提议“20 秒没收到 token 就把加载关掉”这种会误杀 60 秒工具调用的拍脑袋逻辑；第二，每个边界都能用极快的单元测试把边界条件全铺满。

历史回填与实时增量的竞态治理#

在弱网或慢查询下，历史加载经常和实时流撞车：比如前端先发了一个拉取历史的 HTTP 请求，等它返回前 WebSocket 又推来了三段新文本和一条工具结果。如果直接粗暴地用历史响应覆盖当前列表，新字瞬间消失；如果无脑拼接，同一条工具结果又会出现两遍。

除了上面提到的 shouldBlockHistoryRefresh，chatStore.history.test.ts 里专门用事件序列测试锁死了各类合并边界：审批暂停时刷新历史、成员结束但主持人未结束、历史请求失败保留本地内容、取消后收到迟到帧，以及老版本里出现过的过期缓存把历史顺序倒置的问题（v1.0.3b3 修复）。类似的竞态也出现在记忆管理页：连续切换不同专家加载记忆列表时，慢返回的旧响应不能覆盖新专家的列表，这也是 v1.0.3b7 专门补齐的一处防过期响应守卫。

跨端协作：托管 ACP 回环与 Bridge 实例隧道

单台 Octop 跑稳之后，自然会冒出两类跨边界诉求。第一类是开发者手头已经有顺手的本地编程 Agent（Claude Code、OpenCode、Codex、CodeBuddy 等），或者想在 Zed 这类 IDE 里反过来调用 Octop，这走的是 ACP（Agent Client Protocol）。第二类是两台独立部署的 Octop（比如办公室台式机和云服务器）想互相借用对方的专家和工作区，这走的是 Bridge（云端协同桥接）。

这两种能力都叫跨端协作，但执行位置、数据权威和身份边界截然不同，绝不能混成一回事。

ACP 的三种用法：入站、出站工具与托管专家#

看 docs/acp.md 以及 v1.0.3b6~`b7新加的src/octop/api/routers/managed.py和infra/agents/managed.py`，Octop 对 ACP 的支持已经形成三条清晰路径：

形态 谁发起，谁执行 通信方式 核心注意点
入站 ACP（octop acp） Zed 等外部 IDE 调 Octop stdio JSON-RPC 启动独立的嵌入式 OctopServer，与正在跑的 octop run 不共享进程内锁
出站 acp_runner 工具 原生专家把子任务派给外部 CLI stdio JSON-RPC 在运行 Octop 的宿主机找 PATH 与凭证，不是在浏览器机器执行
托管专家（kind="managed"） 外部编程 Agent 直接作为 Octop 一等专家 ACP + 6 个回环 HTTP MCP 直接接管对话回合，可选会话模式，共享 Octop 连接器、知识库、专家回调与插件

v1.0.3b6 到 v1.0.3b7 把托管专家做成了非常顺手的工程抽象。创建托管专家时，managed.py 会往目标项目目录放入种子 AGENTS.md（仅当目录里原本没有时写入，避免覆盖项目自有规范），将选中的技能包按 Runner 习惯链接进 .claude/skills、.opencode/skills 等目录，并在每轮对话里通过 acp/session_modes.py 与 acp/turn.py 完成两件关键桥接：

  1. 模式与审批映射：解析本轮显式模式、线程保存模式或专家固定模式，自动过滤掉 Octop 自有的 ask/craft 却保留跨协议通用的 plan，经 session/set_mode 下发给底层 Runner；同时按 approval_for_session() 判定本轮是走逐次审批（ask）还是无人值守（yolo），并由第 12 章提到的 acp/permissions.py 给重叠权限请求加锁排队。
  2. 反向能力回环：通过 octop-knowledge、octop-agents、octop-files、octop-cron、octop-memory、octop-plugins 六个本地回环 MCP 端点，把原本只有原生专家才碰得到的知识库、其他专家、文件回传、全局定时任务和已启用插件，原封不动递给外部进程。这样一来，你在飞书里给 OpenCode 或 Claude Code 发一条消息，它既能改本机代码库，又能查 Octop 知识库、把改完的文件发回飞书，还能建一条真正的 Octop 定时任务。

Bridge 云端协同：转发请求，绝不复制权威#

再看另一种场景：台式机上的 Octop 挂着私有代码库和本地 GPU，云服务器上的 Octop 对外连着飞书和公网浏览器。Bridge 要做的不是把两台数据库做双向主从同步，而是通过一条机机长连接，让本机能够安全调用远端那位专家。

在本地视角里，远端专家的标识符形如 bridge:{connection_id}:{remote_agent_id}，并在头像上打上云端标记，列表卡片默认对对端地址和账号打码（v1.0.3b1）。浏览器依然只请求本机的 /api 与 WebSocket，由 src/octop/infra/bridge/ 下的 manager.py、transport.py、http_tunnel.py 和 peer_turn.py 识别远端引用后转发到对端。

这里守着三条硬边界：

  1. 权威永远留在专家所在侧：远端专家的模型循环、线程历史、工作区文件和附件落盘全部发生在远端实例。本机只存桥接连接配置和临时视图，绝不在桥断开后悄悄拉起一个本地同名专家顶替续写，因为两边的工作区、凭证、记忆和执行环境根本不是同一个主体。
  2. 两种 WebSocket 彻底分开：浏览器连本机用的是 WebSocketHub，本机连远端用的是独立的机机长连接通道（v1.0.3b5 修复了心跳超时反复断开的问题），浏览器永远不需要也不能直接越过本机去直连远端内网地址。
  3. 身份不按整数等价，路径默认拒绝：本机的 user_id = 7 和远端的 user_id = 7 毫无关系，远端执行请求时严格按照对端绑定账号的身份做资源可见性判断；而且 tunnel_policy.py 把可穿透的 HTTP 方法和路径收得很窄，未在白名单内的管理接口一律拒绝，连接所有者与共享使用者的权限同样分开管控。

跨桥调用还必须正视网络不确定性：HTTP 隧道或流式推送在半路超时，并不等于远端没有执行某个外部工具，反过来传输返回成功也不等于远端工具具有天然幂等。在跨实例链路里，任何有外部副作用的动作依然需要依赖动作标识与对端查询来确认结果。

部署与运维：Electron 壳、镜像分层与多副本租约

自托管软件最容易在“装得上”和“扛得住”之间劈叉：给个人用的桌面安装包要做到点两下就能跑，给小团队用的容器集群又要做到不停服滚动升级、不丢数据、飞书和定时任务不双活乱撞。到了 v1.0.3b7，Octop 在打包形态和集群运维上已经把这两条线收口得非常清楚。

多副本集群：Cookie 粘滞加同行租约#

如果一台 SQLite 实例已经撑满，或者希望升级时先拉起新版本再停旧版本，v1.0.3b6 发布的官方 Helm Chart（deploy/helm/octop/）和集群指南（docs/cluster_CN.md）给出了不引入外部消息队列的多副本解法。

整套集群架构由三条硬规则托住：

  1. 所有共享资产收进同一台 PostgreSQL 16 + pgvector：用户、角色、模型、连接器、通道、定时任务、JWT 密钥、技能包源文件、知识库原文与向量、专家记忆（每专家按 agent_<id> 命名空间隔离）以及多实例共享的腾讯云 CVM 授权全部在库里。注意数据库层面仍然是单点，高可用靠托管 PostgreSQL 或主从复制解决，Octop 本身不替代数据库故障转移。
  2. 前置入口必须按 Cookie 粘滞，绝不按来源 IP 粘滞：浏览器的实时流和轨迹只由接手这轮对话的那台实例在内存里持有并推送。反向代理或 Kubernetes Ingress 用 Cookie 把同一浏览器固定到同一台副本；一旦按来源 IP 粘滞，所有经过公司出口 NAT 或统一代理的流量都会被砸进同一台副本。当某台副本下线，已打开的页面会断连一次，刷新后切到存活副本并从 PostgreSQL 读回历史。
  3. 每台副本独享自己的本机数据目录（/data/.octop），严禁 NFS 共享写：本机工作区和飞书去重表 feishu-dedup.sqlite 都是单机本地文件，用 NFS 挂给多台同写只会把 SQLite 写坏。集群里管理员应通过“限制可选存储后端”开关，引导新建专家使用 PostgreSQL、S3、COS、TOS 或 OpenSandbox 工作区，防止 Pod 重建把临时盘里的工作区文件清空。此外，多副本首次冷启动必须给每台配置完全一致且符合强密码规则（至少 8 位且含字母和数字）的 OCTOP_ADMIN_USERNAME 与 OCTOP_DEFAULT_PASSWORD，否则各台会各自掉进安装向导生成互不相认的向导口令。

定时任务与 IM 通道如何做到多副本单活#

多开两三台 Octop 副本时，为什么同一条飞书机器人不会连出三条长连接，同一条每天早九点的定时任务也不会跑三遍？答案藏在 src/octop/infra/db/lease.py 只有 35 行的三个常量里：

LEASE_SECONDS = 90
RENEW_SECONDS = 30
RECONCILE_SECONDS = 25

CronManager（infra/cron/manager.py）和通道管理器在启动时都会生成进程级 instance_id，并按数据库自身时钟（PostgreSQL 用 clock_timestamp()，SQLite 用 strftime('%s','now')）在 cron_jobs 和通道记录的同一行上抢占租约：

  • 只有抢到行的那台副本真正运行该定时任务或保持该 IM 通道连接；持有者每 30 秒续租一次，把过期时间往后推 90 秒。
  • 进程优雅退出（stop()）时主动释放自己持有的租约行；如果进程意外硬崩，最多等 90 秒租约自动过期。
  • 其他存活副本每 25 秒跑一轮 reconcile 巡检，发现过期或无主行立刻抢占接管。唯一需要留心的小窗口是飞书去重表留在原机器的 feishu-dedup.sqlite 上，通道刚切到新副本的极短窗口内，飞书重发的同一条消息可能会被新副本再处理一次。

另外，CronManager 在任务行为上也在 v1.0.3b6 做了细化：task_type 依然区分直接推送固定文案（text，不花模型费用）与唤醒专家生成后再推（agent）；而投递目标 session_key 除了默认指向所有者的工作台会话，还可以通过 infra/cron/session_target.py 指定 latest（跟随最新对话）或 thread:<thread_id>（固定续写某一条历史对话），后台标签页收到的定时提醒则改为原生系统通知（v1.0.3b4）。

架构取舍：单机够用到何时，复杂度卡在哪里

从启动装配、身份隔离、多层存储一路拆到多副本租约，整个 Octop 的技术选型呈现出一条非常鲜明的主线：宁可在宿主内部把边界和状态机写严实，也不为了纸面上的高大上架构过早引入外部中间件。看完 v1.0.3b7 的全部演进之后，可以客观盘一盘这套架构最值得抄的作业、当下真正聚集复杂度的地方，以及什么时候才真的该动刀拆分。

五个经受住版本迭代的好选择#

把 v1.0.3b1 到 v1.0.3b7 的变化串起来看，有五项决策越往后走越显出威力：

  1. 宿主与四大运行库硬切边界：把 LangGraph 循环、IM 协议、长期记忆和浏览器 CDP 拆成独立发版的 Python 包，宿主只管用户、权限、控制面、装配和工作台。每次修底层运行库漏洞（比如记忆长会话分批提炼或 harness 协议升级），宿主改一行 pyproject.toml 就能平滑升级，代码库不至于在几个垂直领域同时腐烂。
  2. 果断收口失败或过重的实验：v1.0.3b5 彻底下线只支持 SQLite 的 history_v2，并用启动一次性迁移把老用户平滑接回 thread_messages；同版本把桌面壳从 Wails 切成 Electron 45；v1.0.3b3 把庞大的内置市场目录迁到远程市场。对一个高速迭代的开源平台来说，及时做减法比堆新功能稀缺得多。
  3. 用 ADR 003 + 同行租约走完多副本第一步：没有为了多实例一上来就强绑 Redis 和 Celery，而是把技能包与知识库并进共享 PostgreSQL、给 Cron 和 IM 通道加上 90s/30s/25s 同行租约、入口靠 Cookie 粘滞。既守住了单机 SQLite 的零依赖体验，又给了中小团队一套能直接上 Kubernetes Helm 的横向扩展方案。
  4. 托管专家走回环 MCP 而非重写外部 Runner：面对 Claude Code、OpenCode、Codex 等形态各异的外部编程 Agent，不试图魔改它们的内部循环，而是借 ACP 统一会话模式与审批队列，再把 Octop 的知识库、专家回调、文件、定时任务和插件封装成 6 个本地回环 MCP 递过去，集成成本压到极低。
  5. 共享展示但隔离执行状态：团队房间用主持人 thread_id 做共享展示，用 conversation_id~member 隔离成员 checkpoint 和工作区；共享专家默认隔离所有人的私人线程，只有显式标记 contributed 才开放阅读。

当下复杂度真正堆在哪里#

没有哪套架构只有甜头没有代价。把 v1.0.3b7 的代码摊开量一遍，压力高度集中在三个超大核心模块和两类结构张力上：

三个高密度核心模块：src/octop/infra/agents/manager.py 已经接近五千行，src/octop/infra/gateway/process/processor.py 超过两千两百行，前端 dashboard/src/pages/Chat/hooks/chatStore.ts 同样体量可观。大文件本身不自动等于坏设计，但它意味着每次改动都要同时踩稳普通聊天、托管 ACP、专家团队、HITL 审批、模型故障转移、用量统计和 Bridge 远端代理七八条契约，任何一个角落漏测都容易引发回归。

两类固有结构张力：

  • 多层存储的一致性与清理成本：控制面、checkpoint、消息投影、长期记忆、知识索引和远程工作区各自落盘，跨层删除必须严格排顺序（先清 checkpoint 再删线程行），共享 PostgreSQL 上更是因为 checkpoint 表缺少原生外键归属，不得不把孤儿清理收成只统计不删除的保守策略。
  • 进程内状态与多副本粘滞的边界：虽然多副本已经能共享配置、知识库和单活通道，但正在进行的 WebSocket 流、团队在途 TeamJobTracker、取消信号和飞书本地去重表仍停留在单进程内存或本机磁盘里。副本重启或滚动发布时，在途流必然中断一次，需要刷新重新接轨。

什么时候才真的需要引入进程外队列或拆 Worker#

先看真实测量数据（事件循环阻塞延迟、同时活跃回合数、文档解析/OCR CPU 占用、数据库锁等待和尾延迟），不要拿“注册用户破千”这种静态数字当拆分理由。只有出现下面四种信号之一时，进程外队列和独立 Worker 才值回它的运维票价：

  1. 大量重 CPU 后台任务拖慢对话事件循环：例如高频批量上传几百页扫描 PDF 做 OCR 和本地向量化。此时最稳的第一刀是只把文档解析与建索引抽成独立 Worker，不动用户、权限、专家和聊天主进程。
  2. 要求任务跨进程重启不断线且必须可靠接续：例如几十步的自动化巡检或长时代码生成，要求进程崩溃后由另一台节点自动捞起未完成派工，而不是靠人工刷新重试。
  3. 团队异步派工需要跨实例分发与整树取消：现有的进程内 TeamJobTracker 和仅取消主持人流的语义无法满足强一致任务树控制。
  4. 执行沙箱需要独立的弹性伸缩池：代码执行和浏览器自动化资源消耗波动极大，与轻量控制面混部会互相挤占内存。

记住一个前提：加一套进程外队列绝不只是多装一个 Redis。你必须同步设计持久 job_id、租约与 fencing token、失败重试分类、外部写操作幂等键、取消信号跨节点传播和流式帧跨实例路由（Pub/Sub）。如果目前单机 SQLite 或者 2~3 副本 PostgreSQL + Cookie 粘滞已经跑得稳稳当当，保留模块化单体就是最省钱也最容易排障的架构。

代码实战：用两百行标准库模型验证六条边界

前面十六章讲的边界分散在宿主、中间件、数据库和 ACP 适配器几十个文件里。光读源码容易只记住函数名，动手把最关键的几条不变量压成一个零依赖可运行程序，再用单元测试把每条边界的正反用例跑一遍，手感会立刻扎实起来。

配套代码放在本仓库的 examples/mini_host.py，测试放在 examples/test_mini_host.py。它只依赖 Python 3.10+ 标准库与内置 SQLite，不调真实 LLM，不启 WebSocket，也不发外部邮件，专门用来验证 Octop v1.0.3b7 的六条核心架构边界：

  1. 共享专家不共享私人线程，显式 contributed 标记才允许同专家成员查看单条对话。
  2. session_key 改绑新线程时，旧线程完好保留且仍按身份受控访问。
  3. HITL 审批绑定预先落库的 payload，条件更新保证重复批准幂等、取消后不可再批准。
  4. 托管专家的 ACP 会话模式解析自动忽略原生 ask/craft、保留 plan，并按无人值守标记决定 ask/yolo 审批门。
  5. 连续相同工具调用熔断器只在 (tool_name, sorted_args) 连续超过上限时 jump_to="end"，换工具、换参数或纯文本回复立刻重置。
  6. 孤儿 checkpoint 清理对 SQLite 仅在 apply=True 时删除，对共享 PostgreSQL 永远只统计不删除（且跨全部专家汇总活跃线程），外部独立数据库直接跳过扫描。

六张表先钉住数据边界#

MiniHost 用六张极简 SQLite 表把状态关系立起来：agents 存专家归属、分享标志和记忆后端类型；threads 存对话归属与 contributed 共享标记；sessions 存入口键到当前线程的可变指针；actions 存待审批动作的固定载荷和三态流转（pending / approved / cancelled）；outbox 以 action 为主键存待投递记录；checkpoints 模拟 SQLite、共享 PostgreSQL 和外部 PostgreSQL 三类存储中的图状态字节数。

这里刻意把所有表放进同一个 SQLite 库，方便在一个本地事务里把状态机演清楚。真实 Octop 里这些表横跨控制面、checkpoint 和外部连接器，跨库并没有天然全局原子事务。

边界一与二：专家分享、私有线程与显式贡献#

对照第 5 章的 resolve_thread_id() 与 thread_visible_to()，MiniHost.assert_thread() 严格执行先查专家访问、再查线程归属两步检查：

def assert_thread(self, user: int, agent: str, thread: str) -> None:
    self._agent_access(user, agent)
    row = self.db.execute("SELECT * FROM threads WHERE id=?", (thread,)).fetchone()
    if row is None or row["agent"] != agent:
        raise PermissionError("thread inaccessible")
    if not (row["user"] == user or bool(row["contributed"])):
        raise PermissionError("thread inaccessible")

当 research 设为 shared=True 时，用户 9 可以调用 open_thread(9, "research") 开启自己的独立会话，但拿用户 7 的 thread_id 调用 assert_thread() 会直接抛 PermissionError，调用 assert_agent_owner(9, "research") 同样被拒。只有当用户 7 显式调用 contribute_thread(7, "research", thread)（且前提是该专家本身已共享，私有专家直接拒绝共享对话）之后，用户 9 才获得读取权限。

而调用 open_thread(7, "research", fresh=True) 只更新 sessions 表里 research:dashboard:7:dm 指向的新线程，原来的旧线程行纹丝不动，随时可以切回。

边界三：审批绑定载荷与本地幂等#

propose() 先校验参数非空、把收件人和正文序列化为 payload 落库，返回 action_id。随后的 approve() 不允许调用方重新传入收件人或正文，并用一条带状态前提的条件更新完成状态流转：

UPDATE actions SET state='approved' WHERE id=? AND state='pending'

只有 rowcount == 1 的首次批准才在同一事务里把载荷写入 outbox。用户连点两次批准，第二次影响 0 行、返回 False，outbox 依然只有一条记录；一旦先执行了 cancel() 把状态置为 cancelled，后续任何 approve() 同样影响 0 行。持久化测试把 SQLite 落到临时目录关闭再重开，验证挂起的审批动作跨越重启后依然有效。

当然，本地 outbox 只有一行，解决的是审批层面的重复触发，不等于外部发邮件具备跨网络精确一次语义。如果后台投递器把邮件发出去之后、写回本地已发送标记之前崩溃，重启重投依然会发第二封，那一层的去重必须靠对端供应商的幂等键或状态反查来兜底。

边界四与五：托管会话模式与连续调用熔断#

这两个纯逻辑组件直接复刻了 v1.0.3b7 的核心算法：

  • resolve_managed_session_mode() 与 approval_for_session() 对照 src/octop/infra/agents/acp/session_modes.py：传入 Octop 原生的 ask 或 craft 会被忽略并继续往下取固定模式；传入 plan 会保留；当模式命中 bypassPermissions、full-access、yolo 等无人值守标记时返回 yolo，而当 Runner（如 claude_code）发布过无人值守模式但当前处于 acceptEdits 时，即使聊天曾设过 yolo 也会收紧回 ask；像 opencode 这样未发布无人值守模式的 Runner，则尊重聊天本身的 yolo 设置。
  • ConsecutiveToolCallGuard 对照 src/octop/infra/agents/middleware/consecutive_tool_call.py：先把参数 dict 按 sort_keys=True 序列化，确保 {"q": "TODO", "dir": "src"} 和 {"dir": "src", "q": "TODO"} 算出同一个签名。连调次数超过 limit 立刻返回 blocked=True, jump_to="end"；只要参数变了、换了工具，或者调用 observe_text_reply() 模拟纯文本回复，连击计数马上重置。

边界六：SQLite 可删、PostgreSQL 只统计的孤儿扫描#

scan_orphan_checkpoints(agent_id=..., apply=...) 精确建模了 v1.0.3b7 PR #2960 修复后的 gc_orphan_checkpoints()：

  • 面对 sqlite 后端的专家，拿该专家的活跃线程集合做差集；apply=False 仅汇报 found_sqlite，apply=True 才执行删除。
  • 面对 postgres 后端的专家，先汇总全库所有专家的 all_live_threads（避免单查 pg-a 时把同表里 pg-b 的活跃线程错算成孤儿），而且就算传入 apply=True，也只往 skipped_postgres 里追加 ("pg-a", "postgres_report_only", count, total_bytes)，一行都不删。
  • 面对 external_postgres 后端，直接登记 ("pg-ext", "external_database", None, 0) 跳过扫描。
