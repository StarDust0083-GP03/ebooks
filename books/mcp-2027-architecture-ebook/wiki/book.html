前言：从狂热、退潮到 2027 拐点

2025 年下半年，不少工程团队把刚接好的 MCP Server 拆回了命令行脚本。理由很实际：往系统提示里塞进四五十个工具的 JSON Schema，还没开始干活，上下文窗口就吃掉一大截；遇到跨系统的多步查询，模型只能一轮调一个工具，把几百行原始 JSON 反复塞进对话历史，既慢又贵。到了 2026 年初，Agent Skills 流行起来，很多开发者直接转向本地 CLI 配合 SKILL.md 的渐进披露，社区里关于 MCP 过于沉重、迟早被 CLI 取代的争论此起彼伏。

但如果把视线从开发者本机移到真实生产流量上，数据讲的是另一件事。Philipp Schmid 在 2026 年 11 月 26 日发布的文章《Why I'm Bullish on MCP for 2027》中列出了几组公开业务数据：在 Linear 和 Notion，Agent 创建的 issue（约 240 万条/周）和页面已经占到总量的一半左右，Notion 报告其 MCP 流量增长了 60 倍；在 Atlassian，MCP 每个工作日处理超过 500 万次工具调用，其中 44% 的用户不在研发团队，CLI 对这批非工程角色从来就不是可选项；在 Neon，基于 MCP 的 Agent 用量保持 14% 的周环比增长；连 Apple 也开始为 Pages、Numbers 和 Keynote 内置本地 MCP Server。

这两股看似矛盾的体验，其实对应着两代不同形态的 MCP。早期引起抱怨的是 2024 年底到 2025 年的有状态协议与原始 tool calling 用法：必须维护连接握手和粘性会话，列表结果无法跨会话缓存，客户端一股脑把全量 Schema 喂给模型，且只能由用户发问后被动拉取。到 2026-07-28 正式规范落地后，协议底层做了大手术，把会话和握手从核心拿掉，补齐了 HTTP 路由头、列表 TTL 缓存、无状态多往返追问和官方扩展机制；客户端侧则演化出 Code Mode、Skills over MCP、MCP Tasks、MCP Events 和 MCP Apps，把原本零散的胶水层收拢到了同一套协议边界里。

CLI 与 MCP 的真实分工#

把 CLI 和 MCP 对立成二选一，往往是因为默认了执行者是坐在终端前的软件工程师。在本地代码仓库里，给 Agent 一个终端、几个命令行工具和几份本地 Markdown 说明书确实够快，零协议封装，管道组合也很顺手。

一旦业务跨出本机终端，CLI 的短板很快会暴露出来。第一是凭证边界：CLI 和裸 curl 往往要求把长效 API Key 写进磁盘配置文件或环境变量，权限粒度粗，且和 Agent 执行的代码共享同一个进程环境，提示注入一旦突破命令限制就能直接读走密钥。第二是人群覆盖：财务、法务、运营、客服和产品团队的桌面环境里没有终端，也没有人会维护本地包管理器和环境变量，Atlassian 那 44% 的非研发调用量正是靠浏览器 OAuth 登录和零配置远程接入跑起来的。第三是多模态与强类型契约：命令行标准输出本质上是无结构文本流，遇到需要同时返回结构化 JSON、图片、音频或可交互视图的场景，只能靠脆弱的正则解析和临时文件路径硬凑。

2027 年真正成型的格局，是客户端把 MCP 从远程工具调用层升级成 Agent 运行时协议。本地进程继续用 stdio 或命令行，远程 SaaS、企业内部系统、长程异步任务和事件订阅则通过无状态 Streamable HTTP 与官方扩展接入，再由宿主里的 Code Mode 沙箱把强类型 MCP 接口编译成可执行函数，把两边的优势拼到了一起。

协议演进史：从 2024-11-05 到 2026-07-28

2025 年秋天，做远程 Playwright MCP Server 的开发者踩进过一个典型的架构坑：用户在对话里先调用工具打开网页，紧接着下一轮让模型点一下登录按钮，结果浏览器状态凭空消失了。排查下来，服务器代码并没写错，问题出在协议本身的会话语义上。ChatGPT 和早期 Claude.ai 会为每一次单独的工具调用新建并立刻关闭一个 MCP 会话，桌面 IDE 客户端却在应用启动时建一个会话一直挂到进程退出，网页端则是刷新一次页面换一个会话。同一个 Mcp-Session-Id，在不同宿主手里对应着完全不同的生命周期。

类似的结构性摩擦在 2025 年集中爆发：远程无服务器函数（Serverless）挂不住常驻 HTTP GET SSE 连接；放在标准 L7 负载均衡后面的集群被迫开启脆弱的粘性路由；TypeScript SDK 把会话状态存进内存私有字段，节点一重启全部断线；更麻烦的是，只要协议允许服务端按会话动态篡改 tools/list，任何编排器每派生一个子代理，就必须把所有已连接服务器的工具列表重新拉一遍。

理解 2026-07-28 为什么大刀阔斧砍掉握手和会话，最直接的方式是沿着官方仓库的五个正式变更日志，把这两年的演进脉络摊开来看。

为什么必须砍掉有状态会话与常驻双向流#

很多习惯了 WebSocket 或本地 stdio 开发的工程师最初会怀疑：把会话改成可选不行吗，为什么要做不向后兼容的彻底删除？SEP-2567 和 SEP-2575 给出了非常硬的工程证据。

最直接的瓶颈出在子代理场景下的列表缓存失效。只要协议规范允许某个服务器把 tools/list 绑定到会话状态（比如先调 connect_database，后续列表里才凭空多出 query 工具），客户端在连接任意陌生服务器时就无法预先判定它会不会变脸。结果就是编排器每启动一个短生命周期子代理，面对 $M$ 个服务器，就必须重跑一遍 initialize 和 tools/list，整体发现流量变成 $O(\text{subagents} \times \text{servers})$。即使 99% 的服务器工具列表在编译期就固定了，哪怕把会话改成可选项，客户端照样不敢跨会话缓存。彻底删掉会话并规定列表不得随连接状态变化，再配合 SEP-2549 的 ttlMs 缓存提示，父代理拉一次列表，所有子代理就能零成本复用，开销直接降到 $O(\text{servers})$。

另一个结构性硬伤是单会话固定基数（Cardinality）与多代理共享冲突。一个会话在协议层只能隐式挂载一份状态。假设主代理派生三个子代理一起帮用户选商品，它们需要往同一个购物车里加东西，同时各自打开独立的浏览器上下文去查不同网站。在隐式会话模型里，这是一个无解的死结：

会话分配策略 购物车（期望：共享） 浏览器上下文（期望：隔离）
子代理共享父会话 正常共享 互相踩踏、状态错乱
子代理各自建新会话 各自孤立、无法汇总 正常隔离

换成显式状态句柄（Explicit State Handles）后，编排器调一次 create_basket() 拿到 basket_id 发给所有子代理，每个子代理再各自调 create_browser() 拿到自己的 browser_id。协议本身甚至不需要定义新原语，句柄只是工具返回值和入参里的普通字符串，却天然支持跨对话恢复、跨代理移交和细粒度权限校验。

更关键的现实数据是真实仓库里几乎没人真在用会话存业务状态。SEP-2567 公布了对 1000 个随机开源 MCP Server 仓库的自动化扫描结果：

  • 90.0% 的仓库在应用层根本没有引用过 MCP Session ID；
  • 3.5% 只是复制了 TypeScript SDK 样板里的 Map<sessionId, Transport> 路由表；
  • 2.8% 只传了 sessionIdGenerator 构造参数，业务代码从未读取；
  • 真正用会话做应用层状态存储的只占 2.5%，做网关粘性路由的占 0.7%，把 OAuth 状态绑在会话上的占 0.5%。

为了这不到 4% 且语义本就混乱的存量用法，让所有客户端和服务端承担粘性负载均衡、重启丢状态、无法缓存列表的全局税，显然不划算。

与此同时，SEP-2575 顺手清理了依赖持久连接的一整批旧机制：删除 HTTP GET 独立 SSE 端点、删除 Last-Event-ID 断流续传（需要持久化和断线恢复的作业统一交给 MCP Tasks）、删除 ping、logging/setLevel 以及 resources/subscribe/unsubscribe。客户端只在真正需要接收列表变更或资源更新时，才发一条 POST 请求调用 subscriptions/listen，按需换回一条带 io.modelcontextprotocol/subscriptionId 标签的 SSE 响应流。这种按需付费（pay as you go）原则让绝大多数普通请求退化成了标准的一问一答 HTTP POST。

SEP-2577 与弃用治理：核心协议的瘦身决心#

协议成熟的一个重要标志，是敢于把早期设想美好但现实中无人维护的特性清出核心。2026-07-28 同步落地了 SEP-2596 特性生命周期政策，规定任何特性进入 Deprecated 状态后，享有至少 12 个月的宽限窗口，期间线协议行为保持不变，之后在最早可移除日期后的版本中正式删除。

下表整理自 docs/specification/2026-07-28/deprecated.mdx，列出当前已进入弃用清单的全部核心特性：

已弃用特性 弃用提案 弃用版本 官方推荐迁移路径 最早可移除时间
Roots（roots/list 等） SEP-2577 2026-07-28 通过工具参数、资源 URI 或服务端配置显式传递目录与文件 2027-07-28 及之后的首个版本
Sampling（sampling/createMessage） SEP-2577 2026-07-28 服务端直接调用 LLM 提供商 API，避免反向让客户端代跑推理 2027-07-28 及之后的首个版本
Logging（logging/setLevel 等） SEP-2577 2026-07-28 stdio 直接写 stderr，远程服务使用 OpenTelemetry（配合 SEP-414 _meta 透传 trace） 2027-07-28 及之后的首个版本

SEP-2577 弃用 Roots、Sampling 和 Logging 背后的判断很清醒。Roots 在规范里只是信息性提示，服务端并不受强制约束，反而暴露了客户端本地目录结构；Sampling 允许服务端反向要求客户端执行模型补全，甚至在 SEP-1577 加入带工具循环的采样后，客户端要同时处理人工审批、模型路由、防提示注入和防数据外泄，复杂度极高而采用率极低；Logging 则纯粹是在应用协议层重复造轮子，远程服务本就有 OpenTelemetry，本地子进程直接写 stderr 更简单可靠。

把这些高维护成本、低回报或边界模糊的机制清理出核心，再把 Tasks、Skills、Events、Apps 和企业授权放进独立版本化的官方扩展轨道，MCP 核心层在 2026-07-28 终于收敛成了一层精干、无状态、标准 HTTP 友好的传输与能力基座。接下来的一章，我们就钻进这层无状态 HTTP 内核，看看每一个请求头、错误码和缓存字段是怎么咬合在一起的。

02

无状态内核与 HTTP 标准化

2025 年把 MCP Server 放到企业 API 网关（如 Envoy、Nginx 或 Cloudflare Workers）后面时，运维团队最头疼的问题不是业务逻辑，而是流量全成了黑盒。所有请求都发向同一个 POST /mcp 路径，网关如果不把整段 JSON-RPC 请求体读进内存反序列化，就根本不知道这条请求是在调 tools/list 还是 tools/call，更不知道它要调哪个工具、访问哪个区域集群，限流、路由、WAF 审计和分区域灰度全都无从下手。再加上强制的 initialize 三步握手和 Mcp-Session-Id 粘性路由，一台普通无状态函数或标准 L7 负载均衡器根本接不住。

2026-07-28 规范通过四个紧密咬合的提案，彻底把 MCP 改造成了标准云原生 HTTP 工作负载：SEP-2575 去掉握手、把元数据放进每条请求；SEP-2567 去掉会话、用显式句柄替代；SEP-2243 把关键字段镜像到标准 HTTP 请求头；SEP-2549 给所有列表和读取结果加上 ttlMs 与 cacheScope。下面这张图对照了旧版有状态架构和 2026-07-28 无状态内核在请求链路上的差异。

图里上半部分展示的旧架构里，每一个新开的客户端或子代理都必须重走 initialize 并拉取不可跨会话缓存的列表，中间的网关被迫维护粘性会话，后端副本一旦重启就会直接丢失内存状态。下半部分的新内核里，客户端把协议版本与能力放进每条请求的 _meta，同时镜像到 HTTP 头，中间网关只需读取请求头就能直接路由和限流，后端任意无状态副本或 Serverless 实例都能独立完成验权和执行。

每请求自包含：去掉 initialize 之后怎么协商版本#

去掉 initialize 和 notifications/initialized 后，客户端可以不经握手直接发业务请求，或者在需要提前展示服务端能力时调用一次强制实现的 server/discover。每一条请求的参数 _meta 里都必须自包含以下元数据（源自 SEP-2575 与 docs/specification/2026-07-28/basic/transports/streamable-http.mdx）：

  • io.modelcontextprotocol/protocolVersion（必填）：本条请求遵循的协议版本，例如 "2026-07-28"。
  • io.modelcontextprotocol/clientCapabilities（必填）：本条请求周期内客户端声明支持的能力与扩展（例如 elicitation、extensions）。空对象 {} 表示不支持可选能力，服务端绝不能凭先前请求去猜测客户端能力。
  • io.modelcontextprotocol/clientInfo（建议每请求携带）：客户端软件名称和版本，用于日志与调试。
  • io.modelcontextprotocol/logLevel（可选）：替代已删除的 logging/setLevel，只有请求里显式带了这个字段，服务端才允许在响应流里发 notifications/message。

服务端在响应的 _meta 里同样可以回传 io.modelcontextprotocol/serverInfo，规范特别提醒（server/discover.mdx）：serverInfo 是服务端自报的，未经协议校验，只用于界面显示、日志和排障，客户端不得拿它来做安全决策或改变协议行为。

版本协商也变成了内联模式。客户端直接带自己偏好的版本发请求；如果服务端不支持，就返回 HTTP 400 Bad Request 和 JSON-RPC 错误码 -32022（UnsupportedProtocolVersionError），并在 error.data.supported 数组里列出自己支持的版本，客户端挑一个双方共有的版本重试即可。如果客户端调用了服务端未实现的方法，服务端返回 HTTP 404 Not Found 加上 JSON-RPC -32601（Method not found）。

2026-07-28 还专门划定了 JSON-RPC 服务端错误码的分配边界（changelog.mdx）：-32000 到 -32019 留给各 SDK 和具体实现自定义，-32020 到 -32099 保留给 MCP 规范本身，目前已经正式分配了三个高频错误码：

错误码 名称 HTTP 状态码 触发场景
-32020 HeaderMismatch 400 Bad Request 必填 HTTP 头缺失、格式非法，或解码后的头值与 JSON-RPC Body 不一致
-32021 MissingRequiredClientCapability 400 Bad Request 请求需要某项客户端能力（如 elicitation 或 io.modelcontextprotocol/tasks），但请求 _meta 未声明
-32022 UnsupportedProtocolVersion 400 Bad Request 客户端请求的版本不被服务端支持，响应附带 supported 列表

HTTP 请求头标准化与防拆包欺骗（SEP-2243）#

为了让反向代理、WAF 和可观测性系统无需解析请求体就能看见路由信息，Streamable HTTP 要求客户端在每条 POST 请求上镜像一组标准 HTTP 头（名称大小写不敏感，值大小写敏感）：

HTTP 请求头 镜像来源字段 必填范围
MCP-Protocol-Version params._meta["io.modelcontextprotocol/protocolVersion"] 所有 POST 请求
Mcp-Method method 所有 POST 请求
Mcp-Name params.name、params.uri（或 Tasks 扩展中的 params.taskId） tools/call、resources/read、prompts/get、tasks/*
Mcp-Param-{Name} inputSchema 中标注了 "x-mcp-header": "{Name}" 的工具参数 仅当对应参数存在且非 null 时

这里有一个很容易被忽略的安全细节：如果中间网关按 Mcp-Param-Region: us-west1 把请求放行到了美西集群，但攻击者在 JSON 请求体里偷偷把 arguments.region 改成了 eu-central1，就会出现经典的双重解析源不一致（Request Smuggling / Policy Bypass）。因此规范在 Server Validation 中定了一条死规矩：任何真正处理消息体的 MCP Server，都必须校对所有标准头与自定义 Mcp-Param-* 头的值是否与 Body 完全一致（整数比较按数值等价，例如 42.0 与 42 视为相等），只要对不上，立刻拒掉并返回 HTTP 400 与 -32020（HeaderMismatch）。同时，中间网关如果基于镜像头做租户路由或限流，应当先检查 MCP-Protocol-Version 是否达到要求服务端强制校验的版本，否则绝不能盲信未校验的请求头。

为了让非 ASCII 字符、换行符或首尾空格也能安全放进 HTTP 头（遵循 RFC 9110 可见 ASCII 范围 0x21-0x7E），SEP-2243 定义了一套统一的 Base64 哨兵编码格式：

Mcp-Param-Greeting: =?base64?SGVsbG8sIOS4lueVjA==?=

当 Mcp-Name 或 Mcp-Param-* 的原始值包含非 ASCII 字符、控制字符、首尾空格，或者本身字面量就以 =?base64? 开头且以 ?= 结尾时，客户端必须对 UTF-8 字节做 Base64 编码并套上小写哨兵前缀后缀；服务端校验前必须先解码再和 Body 比对。对于 x-mcp-header 注解，规范还划定了严格的静态可达边界：只能挂在 string、integer（JS 安全整数范围内）或 boolean 这三种原始类型上，禁止用于 number 浮点类型，且路径只能穿过纯 properties 链，不能穿过数组 items、oneOf/anyOf/allOf、if/then/else 或 $ref。如果服务端下发的某个工具定义违反了这些规则，Streamable HTTP 客户端必须把那个畸形工具从 tools/list 里剔除并记日志，而不影响同一服务器上的其他合法工具。而且服务端作者绝不能把密码、Token、PII 这类敏感参数标成 x-mcp-header，因为 HTTP 头对沿途所有代理和日志系统都是明文可见的。

列表缓存：ttlMs、cacheScope 与变更失效（SEP-2549）#

在无状态内核里，server/discover、tools/list、prompts/list、resources/list、resources/templates/list 和 resources/read 这六个操作返回 resultType: "complete" 时，都必须带上 ttlMs 和 cacheScope 两个缓存提示字段（而 MRTR 中间态 input_required 或携带 inputResponses/requestState 的重试结果绝对禁止缓存）。

ttlMs 是非负整数毫秒值，类似 HTTP 的 Cache-Control: max-age：客户端记录收到响应的本地时间 t_received，在 now < t_received + ttlMs 期间直接复用缓存；ttlMs: 0 表示立刻过期。规范特意提醒，TTL 只是懒惰新鲜度提示，客户端不应该把它当成后台定时器到处空转轮询，而是在真正需要数据时再检查是否过期。

cacheScope 只有 "public" 和 "private" 两个值，直接决定多租户场景下会不会串数据：

  • "public"，响应不含用户特定数据，客户端、共享网关或代理可以跨不同调用方复用（例如所有用户看到的工具定义完全一致）。
  • "private"，响应依赖当前鉴权身份（比如按 OAuth Scope 过滤后的工具列表，或者用户私有资源内容），只能在同一个授权上下文内复用，换一个 Access Token 就必须隔离缓存。分页列表的所有页必须声明一致的 cacheScope。

此外，服务端返回 tools/list 时应当保持确定性排序（Deterministic Ordering）。这不仅是为了客户端缓存稳定，更重要的是当工具清单注入 LLM 提示词时，稳定的顺序能显著提高大模型的 Prompt Cache 命中率。如果服务端同时支持推送通知，客户端可以通过 POST subscriptions/listen 订阅 toolsListChanged 等事件；一旦收到 notifications/tools/list_changed 或 notifications/resources/updated，客户端立刻把本地还没到 TTL 的缓存标为失效，实现低频兜底加实时刷新的组合。

显式状态句柄与双传输一致性#

删掉会话后，像购物车、数据库连接或浏览器实例这类跨调用状态怎么办？SEP-2567 和 tools.mdx 给出的答案很朴素：用普通工具返回值颁发显式句柄（比如 create_basket 返回 basket_id: "bsk_a1b2c3"），后续工具把 basket_id 当普通入参传回来。Linear 的 create_issue、Notion 的 notion-create-pages、GitHub 的 create_pull_request 和 Stripe 的 create_customer 早就这么干了。

这里有一条安全底线必须分清：对已鉴权服务器，句柄只是资源名而不是通行证，服务端每次调用都必须校验 (handle, auth_context)，就像拿到一个 Google Doc 链接不代表你有权限打开它；只有对无鉴权服务器，句柄才不得不充当承载凭证（Bearer Token），此时必须用密码学随机源生成至少 128 位熵（如 UUIDv4）并设置明确过期时间，且把过期策略写进创建工具的 description 里让模型能看见。

最后看看 stdio 与 Streamable HTTP 的关系。2026-07-28 坚持两套传输保持完全一致的无状态语义：stdio 同样去掉了握手，每行一条换行分隔的 JSON-RPC 消息，元数据全在 _meta 里，日志走 stderr。两者的核心区别只剩传输力学：

  • 请求取消：Streamable HTTP 关闭该请求的 SSE 响应流即代表取消（不再发 notifications/cancelled）；stdio 共享同一对标准输入输出管道，所以仍需发 notifications/cancelled 指定请求 ID。
  • 向下兼容探测：连接未知版本的旧服务时，Streamable HTTP 客户端可以直接发一条现代 POST 请求，如果收到 400/404/405 且响应体不是现代规范认可的 JSON-RPC 错误，再回退到 initialize 或老旧的 GET SSE 端点；stdio 没有 HTTP 状态码，规范建议客户端先发一条 server/discover 探针，收到 DiscoverResult 或现代版本错误就走新协议，收到其他错误或超时再回退 initialize。

根据 2026 年 8 月更新的官方路线图（docs/development/roadmap.mdx），Transports 工作组下一步甚至计划探索 HTTP/2 over stdio，试图用一套统一的多路复用 HTTP 传输同时服务远程和本地子进程，再配合 ETag 扩展工具结果缓存。到那时，本地与远程传输层的双轨维护成本还会进一步压缩。

传输层已经轻装上阵，但要让 Agent 在不撑爆上下文的前提下精准调用这些无状态接口，核心还要看工具、资源与提示词这三类原语的契约设计。下一章我们拆解它们的 Schema 约束与错误处理机制。

核心原语与强类型契约

很多团队在 2025 年写完第一个 MCP Server 后，很快遇到两个让人哭笑不得的故障。第一个故障来自返回格式：工具把查询结果拼成一段自然语言文本塞回 content，结果上游字段多了一个逗号或者模型需要二次提取 ID 时，只能靠肉眼读字符串硬猜，一旦要做批量过滤或跨系统关联，失误率直线上升。第二个故障来自参数校验：用户说把机票订在 12 月 12 日，模型不小心填成了去年的年份 "12/12/2024"，服务端一看日期不对，直接扔出一个 JSON-RPC 协议错误 -32602 (Invalid params)；客户端把协议错误当成系统异常拦在外面，根本没告诉模型为什么错，模型只好盲目重试三遍一模一样的过去日期，最后任务彻底卡死。

这两个坑分别在 2025-06-18、2025-11-25 和 2026-07-28 被逐一填平。正是这组看似不起眼的契约升级，让 MCP 工具从给人看的字符串拼接接口，变成了给程序和模型共同消费的强类型合约。

三大原语的控制权划分#

MCP 服务端暴露的核心原语一直保持克制，只有三类：Tools、Resources 和 Prompts。官方规范用控制权归属把它们的边界切得很清楚，免得团队把所有东西都一股脑塞成 Tool：

原语 默认控制权 典型协议方法 适用场景 缓存与 MRTR 支持（2026-07-28）
Tools 模型控制（Model-controlled） tools/list、tools/call 执行有副作用的操作、查库、调外部 API、触发计算 tools/list 支持 ttlMs/cacheScope；tools/call 支持 MRTR
Resources 应用驱动（Application-driven） resources/list、resources/templates/list、resources/read 只读上下文数据（文件、库表结构、日志、Skill 文档、UI 模板），按 URI 寻址 列表与读取均支持缓存；resources/read 支持 MRTR 与 URI 模板（RFC 6570）
Prompts 用户控制（User-controlled） prompts/list、prompts/get 显式触发的工作流模板（如客户端里的 / 斜杠命令） prompts/list 支持缓存；prompts/get 支持 MRTR

工具命名也有了明确规范（SEP-986）：名称长度应在 1 到 128 个字符之间，区分大小写，仅使用 ASCII 字母、数字、下划线、连字符和点号（例如 getUser、DATA_EXPORT_v2、admin.tools.list），避免空格和特殊符号。同时，规范在 tools.mdx 里特意提醒聚合代理和客户端：工具名只在单个服务器内唯一，不要拿自报的 serverInfo.name 做命名空间前缀来消歧，因为它不保证全局唯一，客户端应当使用自己分配的稳定服务器标识来隔离同名工具（例如两台服务器都叫 search）。

另外，每个工具还可以附带可选的 annotations（描述是否只读、是否具有破坏性等）和 icons（SEP-973），但规范用醒目的安全警告提醒客户端：除非来自明确受信任的服务器，否则工具注解必须视作不可信输入，绝不能仅凭服务端自称只读就跳过破坏性操作的用户确认。

inputSchema、outputSchema 与 structuredContent#

从 2025-11-25（SEP-1613）起，MCP 确立 JSON Schema 2020-12 为默认方言；到了 2026-07-28（SEP-2106），规范进一步放开了限制：inputSchema 和 outputSchema 允许使用完整的 JSON Schema 2020-12 关键字，且 structuredContent 不再局限于 JSON 对象，可以是任意合法 JSON 值（对象、数组、字符串、数字、布尔或 null），同时要求实现做好 $ref 解析以及组合关键字的资源上限防护，避免恶意深度嵌套 Schema 拖垮解析器。

看一个带完整输入输出 Schema 的工具定义示例（遵循 docs/specification/2026-07-28/server/tools.mdx）：

{
  "name": "list_open_issues",
  "title": "List Open Issues",
  "description": "Return open engineering issues for a team",
  "inputSchema": {
    "type": "object",
    "properties": {
      "team": { "type": "string" },
      "state": { "type": "string", "enum": ["open", "closed"] }
    },
    "required": ["team", "state"]
  },
  "outputSchema": {
    "type": "object",
    "properties": {
      "items": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "identifier": { "type": "string" },
            "title": { "type": "string" },
            "priority": { "type": "integer" }
          },
          "required": ["identifier", "title", "priority"]
        }
      }
    },
    "required": ["items"]
  }
}

当工具声明了 outputSchema 时，服务端必须返回符合该 Schema 的 structuredContent，客户端应当在消费前按该 Schema 做校验。为了兼容还不认识 structuredContent 的旧客户端，规范建议服务端在 content 里同步放一份序列化文本或可读摘要。这里需要注意规范特别划出的一条概念区分：structuredContent 是服务端产生的结构化工具返回值，与大语言模型推理侧的 Structured Outputs（受限解码生成 JSON）完全是两回事。

不过，同时存在 content 和 structuredContent 也带来了一定心智负担和实现分歧。官方在 2026 年 8 月更新的路线图（docs/development/roadmap.mdx 第 4 项优先领域）里坦率承认了这一点：新成立的 Core Primitives 工作组计划在下个周期精简 tools/call 的返回形态，解决结构化与非结构化输出并存导致的保真度差异，并同步探索服务端渐进发现（Progressive Discovery）机制。

原生多模态内容块与资源引用#

相比只能输出纯文本字节流的 CLI，MCP 工具结果从协议层就原生支持混合内容块。单次 tools/call 的响应可以同时把机器可计算的字段放进 structuredContent，把给人或视觉/语音模型看的内容放进 content 数组里的独立块：

  • 文本块（type: "text"），承载可读摘要或向后兼容的 JSON 字符串。
  • 图像块（type: "image"）与音频块（type: "audio"），携带 Base64 数据与 mimeType（如 image/png、audio/wav）。
  • 资源链接（type: "resource_link"），只返回资源 URI、名称和描述，避免在工具结果里直接内联几十兆的大文件，让客户端按需调 resources/read 懒加载。规范提醒：工具返回的 resource_link 不一定出现在 resources/list 目录中。
  • 内嵌资源（type: "resource"），当数据量不大且需要随结果立即生效时，直接携带 uri、mimeType 和内容体。

所有内容块都可以挂 annotations，用 audience（如 ["user"] 或 ["assistant"]）、priority 和 lastModified 提示宿主这段内容该给谁看。比如一张给人类复核的高清截图可以标成 audience: ["user"]，而不必白白浪费视觉模型的输入 Token。

SEP-1303：把参数校验失败还给模型自纠错#

回到本章开头那个订机票填错年份的死循环。SEP-1303 在 2025-11-25 落地并延续到 2026-07-28，把工具错误严格划成了两类，核心判据只有一条：模型看到这条报错后能不能自己改参数修好。

  1. 协议错误（Protocol Errors），走标准 JSON-RPC error 对象，用于请求框架本身坏了或模型很难自修的问题，包括：调用了不存在的工具名（-32602）、请求外层不符合 CallToolRequest 结构、HTTP 头与 Body 不匹配（-32020）、服务端内部崩溃（-32603）。客户端可以选择直接拦截，不一定会喂给模型。
  2. 工具执行错误（Tool Execution Errors），走正常的 JSON-RPC result 对象，带上 "resultType": "complete" 和 "isError": true，把清晰可执行的修复提示写在 content 里。覆盖三类场景：外部 API 调用失败、所有输入参数校验错误（格式不对、日期在过去、枚举越界、必填字段缺失），以及业务逻辑错误（如句柄已过期、余额不足）。

规范明确要求客户端应当把 isError: true 的工具执行错误完整交给模型。回到订机票的例子，服务端返回：

{
  "jsonrpc": "2.0",
  "id": 4,
  "result": {
    "resultType": "complete",
    "content": [
      {
        "type": "text",
        "text": "Invalid departure date: must be in the future. Current date is 2026-11-26."
      }
    ],
    "isError": true
  }
}

模型看到当前日期提示后，下一轮马上就能把参数修正为合法日期并完成预订，不再需要人工打断。类似地，前面提到的显式状态句柄如果过期了，服务端也应当用 isError: true 明确回复 "basket bsk_a1b2c3 has expired"，引导模型重新调用创建工具，而不是扔一个冰冷的 "invalid argument"。

无状态传输、强类型 inputSchema/outputSchema、structuredContent 多模态返回和可自愈的错误边界都齐备之后，客户端执行工具的方式迎来了质变。下一章我们看 Phil Schmid 文章里的第一个重头戏：Code Mode 如何借着这套强类型契约，彻底改写 Agent 调用 MCP 的成本曲线。

04

Code Mode：终结上下文膨胀与 N 轮串行调用

让一个 Agent 做件日常排障活：先去 Linear 拉出 core 团队所有未关闭的 issue，挑出最高优先级 P0 的那几条，再分别去 Sentry 查它们过去 24 小时的报错次数和 P95 延迟，最后输出一张汇总表。按 2025 年最常见的 plain tool calling 跑法，事情会立刻变得既慢又贵。宿主先把两台 MCP Server 的几十个工具 JSON Schema 全量塞进系统提示；第一轮模型调用 linear.listIssues，返回 20 条带长描述的 issue 原始 JSON，整包灌进对话历史；第二轮模型挑出 3 条 P0，再逐一调用 sentry.getIssueStats，每一条多走一轮推理，又把一大段堆栈和标签写回上下文。把两台服务器的数据拼在一起，实际是拿昂贵的模型上下文窗口当内存，拿串行模型推理当 for 循环。

Philipp Schmid 在《Why I'm Bullish on MCP for 2027》里把 Code Mode 放到了第一条核心变化的位置，并指出这种模式正在成为 OpenCode 2.0、Claude Code、OpenAI Codex、Pi 和 Factory Droid 等新一代客户端的默认执行路径。下面这张图对比了传统串行 tool calling 和 Code Mode 在上下文占用与往返轮次上的差别。

图里上半部分的普通调用链路中，全量中间数据都必须经过模型上下文窗口，哪怕最终汇报只需要三个字段，前几十 KB 的冗余文本也会跟着后面每一轮推理反复计费。下半部分的 Code Mode 则由宿主提供一个隔离执行沙箱，把远端 MCP 工具映射成带类型的可调用函数，让模型在一轮推理里写出异步脚本，把并发查询、过滤和跨服务器 Join 全部放在便宜的沙箱内存里完成，最后只把精简摘要返回给模型上下文。

为什么 outputSchema 是 Code Mode 的前提#

早在 2025 年，就有团队尝试让模型直接写 Python 或 TypeScript 去调外部工具，但经常写出一堆字段名猜错的崩溃代码。根源在于旧工具只声明了 inputSchema，没声明返回结构。模型知道该传什么参数，却不知道返回值里列表字段叫 items、issues 还是 data.nodes，也不确定优先级字段是 "P0" 字符串还是数字 1。每次碰到未知结构，模型不得不先发一轮试探调用看一眼输出，再写处理脚本，平白多出往返和试错成本。

MCP 的 outputSchema 与 structuredContent 把这块拼图补齐了。只要服务端在 tools/list 里同时声明 inputSchema 和 outputSchema，客户端就能在模型动笔前，自动生成强类型桩代码（Typed Stubs），直接暴露给沙箱环境。Philipp Schmid 原文给出了这个最直观的 TypeScript 示例：

// Auto-generated from MCP inputSchema + outputSchema
// interface LinearIssue { identifier: string; title: string; priority: number }
// interface SentryStats { count24h: number; p95Ms: number }
//
// declare const linear: {
//   listIssues(args: { team: string; state: "open" | "closed" }): Promise<{ items: LinearIssue[] }>;
// };
// declare const sentry: {
//   getIssueStats(args: { query: string }): Promise<SentryStats>;
// };

// Model writes 1 script instead of N tool-calling turns
const issues = await linear.listIssues({ team: "core", state: "open" });
const p0s = issues.items.filter(i => i.priority === 1);

const errors = await Promise.all(
  p0s.map(i => sentry.getIssueStats({ query: i.identifier }))
);

// Only the joined summary enters model context
return p0s.map((i, idx) => ({
  id: i.identifier,
  title: i.title,
  events24h: errors[idx].count24h,
}));

这段不到 15 行的脚本体现了 Code Mode 的四个工程收益。推理轮次从 $N+1$ 压到 1，原本要串行跑四五轮的查询，现在由 Promise.all 在单次沙箱执行里并发完成，端到端延迟显著下降。过滤与聚合落在廉价计算层，在第 14 章的教学基准测试（test_09_code_mode_slashes_turns_and_context_bytes）里，面对 20 条带 600 字节正文的 issue 和对应带堆栈的 Sentry 统计，普通 tool calling 需要 4 轮推理并向模型上下文灌入上万字节原始载荷，Code Mode 只用 1 轮推理，进入上下文的最终摘要体积缩小了超过 20 倍。静态类型提前挡住字段幻觉，只要沙箱开启 TypeScript 类型检查或运行前校验，把 i.priority === "p0" 写错成字符串类型在执行前就会报错，根本不需要等到远端接口失败。提示词里的工具列表大幅瘦身，宿主无需把 50 个冗长的 JSON Schema 原文塞进系统提示，只需提供精简的类型签名索引，甚至按需动态检索子集。

三种工具调用路线的真实取舍#

工程落地时，普通 tool calling、本地 CLI 管道和 MCP Code Mode 各有适用边界，把三者放在同一张表里对照，选型会非常清晰：

这里最容易被低估的是沙箱外 OAuth 边界与原生多模态。很多开发者喜欢在本地终端里用 gh、stripe、aws 等 CLI 工具配 SKILL.md，在个人开发机上确实顺手。可一旦把这套方案搬到企业团队或云端托管 Agent，CLI 往往逼着你把宽权限 API Key 塞进容器环境变量。只要沙箱里执行的脚本读了一段带提示注入的外部文档，攻击者一句 env 或 cat ~/.config/... 就能把凭证偷走。

而在 MCP Code Mode 架构里，代码沙箱本身是无网、无磁盘凭证的纯计算隔离区（例如 V8 Isolate、QuickJS/Wasm 或无密钥子进程）。沙箱里的 linear.listIssues(...) 和 sentry.getIssueStats(...) 只是向沙箱外宿主发起的受控 RPC 桥接；真正的 OAuth 2.1 Access Token、作用域校验、人工审批弹窗和出站 HTTPS 连接全都由沙箱外的 MCP Client 负责。即使沙箱里的脚本被恶意输入诱导，它也看不到任何原始密钥，更无法绕过宿主允许的工具清单去访问任意外网地址。

多模态场景同样如此。如果一个 BI 或监控 MCP Server 返回了图表 PNG 图像和底层指标数组，Code Mode 脚本可以直接拿 structuredContent 里的数组算同比增长率，同时把 content 里带 type: "image" 的独立块原样透传给多模态模型看图，不用在脚本里折腾 Base64 落盘和文件路径传递。

落地 Code Mode 时绕不开的三个工程细节#

把 Code Mode 真正做稳，服务端和宿主各有几件不能偷懒的事。

对 MCP Server 作者而言，第一件事是把 outputSchema 当成一等公民来写，哪怕返回的是数组或嵌套对象，也要给足准确的字段类型和 required 列表，并保证 structuredContent 严格遵守该 Schema。只返回一坨 Markdown 表格的工具，在 Code Mode 里会退化成难解析的字符串，直接拖累调用成功率。第二件事是注意分页和体积上限：即使沙箱内存比上下文窗口便宜得多，无限制拉取十万条记录照样会触发沙箱 OOM 或执行超时，工具设计时应当提供明确的过滤参数（如 team、state、limit）与分页游标。

对 宿主与客户端作者而言，第一件事是隔离沙箱必须锁死资源配额与出站网络：限制 CPU 时间、内存上限、单次脚本并发 RPC 数量，禁用原生 fetch/文件系统/环境变量访问，所有对外交互只留 MCP 桥接函数这一个窄口。第二件事是把人工确认（Human-in-the-Loop）和写操作拦截依然卡在宿主层：沙箱脚本调用只读工具可以静默并发放行，但一旦触发破坏性写操作或服务端返回 InputRequiredResult，宿主必须能暂停脚本执行、把确认弹窗推给用户，等拿到结果再恢复 Promise，或者直接拒绝并抛异常给脚本处理。第三件事是错误堆栈的回传策略：脚本里某次 tools/call 返回 isError: true 时，宿主应当把这条可执行错误信息映射成可读异常，既允许脚本内 try/catch 自行兜底，也在未捕获时完整还给模型，让模型在下一轮迅速修正脚本。

当沙箱脚本在执行半途遇到服务端需要人工确认或外部授权，或者普通远程调用需要向用户追问额外参数时，无状态的集群怎么在没有粘性会话的前提下把这一来一回接上？下一章我们拆解 2026-07-28 的多往返请求机制（MRTR）和 URL Mode Elicitation。

05

多往返请求（MRTR）与无状态追问

设想一个线上发布工具 deploy_release。用户让 Agent 把 v2.4.0 发到生产环境，客户端把 tools/call 发给了负载均衡器后面的副本 A。副本 A 检查策略后发现：生产发布必须先让操作人二次确认，或者需要先去第三方平台补录一个一次性审批凭证。

在 2025-11-25 及以前的协议里，服务端要想反过来问客户端要信息，必须顺着正在打开的 HTTP SSE 响应流，倒着发一条服务端发起的 JSON-RPC 请求（elicitation/create），然后副本 A 的工作线程就得死死挂在那里干等。问题马上就来了：客户端回答后发回的 POST 必须精准路由回同一台副本 A，否则新落地的副本 B 根本不知道刚才那条挂起的协程在哪；如果用户喝了杯咖啡两分钟才点确认，中间网关或 Serverless 早就把长连接掐断了。

2026-07-28 通过 SEP-2322（Multi Round-Trip Requests，简称 MRTR） 彻底终结了服务端主动发请求的历史。新规则非常干脆：服务端绝不在任何流上发送独立的 JSON-RPC Request；当处理请求需要额外输入时，直接结束本次请求并返回一个 InputRequiredResult，等客户端收集完输入，再带着原参数和服务端签发的不透明状态令牌重试一次。下面这张图把 MRTR 无状态追问与沙箱外 OAuth 2.1 的完整边界串在了一起。

图里第 1 到第 3 步发生在副本 A 上：副本 A 校验完 OAuth 2.1 Bearer Token 后发现缺少人工确认，于是直接签发带完整性保护的 requestState，随 InputRequiredResult 一起返回，然后立即释放当前 HTTP 连接，内存中不留任何会话状态。第 4 步由宿主在本地完成表单弹窗或跳转浏览器执行带外授权。第 5 步客户端换一个新的 JSON-RPC id 重试原请求，哪怕负载均衡器把重试打到了另一台毫无上下文的副本 B，副本 B 也能靠验签 requestState 重建上下文并直接产出最终结果。

resultType、InputRequiredResult 与允许触发的边界#

为了把正常完成和需要补充输入这两种结果清晰分开，2026-07-28 规定所有协议结果都必须带上 resultType 鉴别字段（docs/specification/2026-07-28/basic/patterns/mrtr.mdx）：

  • "complete"，表示本次 RPC 已经执行完毕，返回标准结果。如果客户端连上了旧版本服务端、结果里缺了该字段，客户端必须按 "complete" 处理。
  • "input_required"，表示本次请求需要客户端补充输入后再重试，即 InputRequiredResult。（此外，第 9 章的 Tasks 扩展还引入了 "task"。）

规范严格限定了只有三个客户端方法允许返回 InputRequiredResult：tools/call、resources/read 和 prompts/get，其他任何方法都不允许触发 MRTR。而且服务端在返回 inputRequests 之前，必须检查本次请求 _meta.io.modelcontextprotocol/clientCapabilities 里客户端是否明确声明支持对应能力（比如 elicitation 里的 form 或 url 模式）。如果客户端没声明，服务端绝不能强行下发，而是应当视情况降级，或者返回 -32021（MissingRequiredClientCapability）明确告知缺少哪些能力。

看一组完整的往返报文。第一次请求（id: 1）触发了表单追问：

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "confirm_prod": {
        "method": "elicitation/create",
        "params": {
          "mode": "form",
          "message": "Confirm deploying v2.4.0 to prod?",
          "requestedSchema": {
            "type": "object",
            "properties": {
              "approved": { "type": "boolean" }
            },
            "required": ["approved"]
          }
        }
      }
    },
    "requestState": "eyJwcm...signature"
  }
}

客户端弹窗征得用户同意后，发起第二次独立请求。注意规范的两条硬要求：第一，重试请求的 JSON-RPC id 必须不同于首次请求（这里变成 id: 2），因为它们是两个完全独立的请求；第二，如果服务端返回了 requestState，客户端必须一字不差地原样回传，不得解析、篡改，也不得把它套用到并行发出的其他请求上。如果服务端没返回 requestState，客户端重试时则不得凭空带上该字段。

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "deploy_release",
    "arguments": { "version": "v2.4.0" },
    "inputResponses": {
      "confirm_prod": {
        "action": "accept",
        "content": { "approved": true }
      }
    },
    "requestState": "eyJwcm...signature"
  }
}

如果客户端漏填了必需的回答，规范建议服务端继续返回新的 InputRequiredResult 重新索要，而不是直接抛协议错误；如果客户端多塞了服务端不认识的额外字段，服务端应当静默忽略。同时回想第 2 章的缓存规则：任何 resultType: "input_required" 中间结果，以及携带了 inputResponses 或 requestState 的重试响应，都绝对禁止写入客户端缓存。

把 requestState 当作不可信外部输入来防#

因为 requestState 完整绕道了客户端，恶意或被攻破的客户端完全可能篡改、重放、跨账号移植或者调包参数。mrtr.mdx 给服务端列出了非常具体的密码学防护清单：

  1. 强制完整性保护：只要 requestState 会影响鉴权、资源访问或业务逻辑，服务端必须使用 HMAC 或 AEAD（如 AES-GCM）保护其完整性和机密性，验签失败直接拒绝。只有在篡改顶多导致请求失败的无害场景下，才允许省略完整性校验。
  2. 绑定三要素防重放：受保护的 requestState 载荷内应当编码三项数据并在收到重试时逐一核验：
    • 当前已鉴权主体（principal / sub）：拒绝由其他账号呈递的状态令牌；
    • 短有效期（TTL）：拒绝超过过期窗口的陈旧令牌；
    • 原始请求指纹（方法名加关键参数摘要）：防止攻击者拿着审批 v2.4.0 拿到的 requestState，在重试时偷偷把参数调包成 v9.9.9-evil。
  3. 一次性消费必须由服务端落库保证：规范特意加了一段警告，上述三项只能收窄重放窗口、防跨人和防调包，本身不能保证严格一次性消费（Single-use）。像一次性核销、转账扣款这类不能被重放两次的操作，服务端必须在共享存储里记录消费状态（如 nonce 或幂等键）。

这套防线已经在第 14 章的 MrtrReplica 与 test_10/test_11 中完整跑通：副本 A 签发的 requestState 在副本 B 上正常续跑，而篡改签名、换账号重放、超时、调包参数和复用 JSON-RPC id 五种攻击全部被准确拦截。

Form Mode 与 URL Mode Elicitation（SEP-1036）#

MRTR 承接的交互请求里，因为 Roots 和 Sampling 已在 2026-07-28 正式弃用，真正面向 2027 的主角是 Elicitation（docs/specification/2026-07-28/client/elicitation.mdx）。它分两种模式，安全边界划得泾渭分明。

**Form Mode（表单模式）**用于采集非敏感的结构化信息，数据会经由客户端回传服务端。为了让各种桌面、网页和命令行宿主都能稳定渲染表单，requestedSchema 被刻意限制在扁平对象（Flat Object）子集内，属性只允许 string（支持 email、uri、date、date-time 格式）、number/integer、boolean，以及单选或多选枚举（SEP-1330 规范了带 title 的 oneOf/anyOf 与无标题的 enum 写法，SEP-1034 补齐了所有原始类型的 default 默认值）。深度嵌套对象和普通数组被明确禁止。用户的响应统一采用三态模型："accept"（提交并附带 content）、"decline"（明确拒绝）和 "cancel"（关闭弹窗或按 Esc 放弃）。

规范划了一条不可逾越的红线：服务端绝不能用 Form Mode 向用户索要密码、API Key、访问令牌或支付凭证。凡是涉及敏感秘密或第三方系统授权的交互，都必须走 URL Mode（SEP-1036）。

在 URL Mode 中，服务端只返回一个带 mode: "url"、message 和目标 url 的 elicitation/create 请求，客户端向用户展示完整域名并征得明确同意后，通过安全隔离的系统浏览器（比如 iOS 上允许 SFSafariViewController，禁止客户端可窥探内容的 WKWebView）打开页面。用户直接在可信网页里输入敏感凭证或走完第三方 OAuth 流程，凭证直接存在 MCP Server 后端，全程不经过 LLM 上下文，也不经过 MCP Client。客户端重试原请求时，inputResponses 里只有 {"action": "accept"}（没有 content），表示用户同意打开链接；至于带外操作有没有完成，由服务端根据回传的 requestState 和后端状态自行判断。

这里有一个 2026-07-28 相比 2025-11-25 的关键精简：旧版曾经定义过 elicitationId 和服务端主动推送的 notifications/elicitation/complete 通知。在全面转向 MRTR 后，客户端靠重试原请求就能得知带外流程结果，服务端需要关联状态时直接把自己的标识放进 requestState 即可，于是这两个冗余元素被彻底删掉了。

防钓鱼与防令牌透传：URL Mode 的两道必考安全题#

URL Mode 把用户引到了外部浏览器，立刻引入了两个经典安全陷阱，规范在 elicitation.mdx 里花了不少篇幅给出标准解法：

第一是禁止拿 URL Mode 替代 MCP 自身授权，更禁止 Token Passthrough。MCP Client 访问 MCP Server 的身份授权必须走下一章讲的标准 OAuth 2.1；URL Mode 只用来处理 MCP Server 作为第三方 API 客户端时的外部授权，而且服务端绝不能把客户端发来的 MCP Bearer Token 透传给第三方 API，也不能把第三方凭证发回给 MCP Client。

第二是防链接转发钓鱼（Account Takeover）。设想恶意用户 Alice 触发了一个第三方授权 URL，她自己不点，而是把链接发给同一台 MCP Server 的受害者 Bob。如果服务端直接把用户送到第三方 OAuth 授权页，Bob 点完授权后，第三方回调回来，服务端错把 Bob 的第三方令牌绑到了 Alice 的账号下，导致账号接管。标准防线是：服务端给的 URL 不应该是直接指向第三方授权页的裸链接，而是先指向 MCP Server 自己的受保护入口（例如 https://mcp.example.com/connect?...），且 URL 里禁止包含敏感信息或预鉴权令牌。浏览器打开该页面后，服务端必须先校验浏览器里的登录态（如 Session Cookie 对应的 sub 身份）与发起 MRTR 的 MCP 鉴权 sub 完全一致，确认是同一个人操作后，才把浏览器重定向到第三方授权服务器。同时，客户端侧禁止预抓取 URL 元数据、必须高亮展示完整域名并对 Punycode 混淆域名发出警告。

理清了服务端如何向用户安全追问之后，下一章我们把目光转向整个 MCP 远程服务的入口闸门：OAuth 2.1、受保护资源元数据、CIMD 无预注册发现与企业 IdP 集中管控。

06

身份与授权体系：OAuth 2.1、CIMD 与企业 IdP

把远程 MCP Server 推向公司内部时，最先卡住的几乎从来不是工具写得好不好，而是安全团队的三个问题：第一，陌生客户端连上来之前既没有预分配的 client_id，企业 IdP 又为了防滥用关掉了动态客户端注册（DCR），怎么在不手工建几百个 OAuth 应用的前提下完成登录？第二，员工连了十几个 MCP Server，每个服务都要弹一次浏览器授权，员工离职时怎么保证一键回收全部 Agent 访问权限？第三，如果一个恶意 MCP Server 诱骗客户端把发给别家服务的 Token 拿来复用，或者用恶意授权服务器实施 Mix-Up 混肴攻击，协议层有没有硬防线？

2026-07-28 规范以及稳定版官方授权扩展仓库 modelcontextprotocol/ext-auth，已经把这一整套基于 IETF 标准协议栈的身份边界搭了起来。对 HTTP 传输层来说，授权是可选的，一旦启用就必须遵守这套规范；而本地 stdio 传输则明确不应套用 HTTP OAuth 流程，应从本地受控环境获取凭证。

标准协议栈与三方角色#

MCP 没有自己发明一套专有鉴权协议，而是把九份成熟 IETF/OIDC 标准拼成了一条可互操作的链路（docs/specification/2026-07-28/basic/authorization/index.mdx）：

  • OAuth 2.1（draft-ietf-oauth-v2-1-13）与 RFC 6750：要求 HTTPS、强制 PKCE（S256）、仅允许 Authorization: Bearer <token> 请求头（严禁把 Token 放进 URI 查询参数）、公开客户端强制 Refresh Token 轮换。
  • RFC 9728（OAuth 2.0 Protected Resource Metadata，SEP-985）：明确 MCP Server 是 OAuth 资源服务器（Resource Server），通过元数据向客户端指明背后对应的授权服务器（Authorization Server）是谁。
  • RFC 8414 与 OpenID Connect Discovery 1.0：客户端发现授权服务器端点与能力的标准机制。
  • RFC 8707（Resource Indicators）：把 Access Token 严格绑定到目标 MCP Server 的规范 URI（Canonical URI），从协议源头杜绝令牌跨服务滥用和 Token Passthrough。
  • OAuth Client ID Metadata Documents（CIMD，SEP-991）：用 HTTPS URL 作为 client_id，取代已弃用的 RFC 7591 动态注册。
  • RFC 9207（SEP-2468）：在授权响应里校验 iss 参数，防 OAuth Mix-Up 攻击。

把 MCP Server 定位成标准 OAuth 资源服务器的好处非常直接：鉴权逻辑可以完全委托给专门的授权服务器（如 Okta、Auth0、Keycloak、Stytch、WorkOS 或自建 IdP），MCP Server 只需做好无状态的令牌验签、受众核对和作用域检查。

授权服务器发现与受众绑定#

客户端第一次无令牌访问受保护的 MCP Server 时，整条发现与换票链按严格顺序走完：

  1. 受保护资源发现（RFC 9728）：MCP Server 返回 HTTP 401 Unauthorized，并在 WWW-Authenticate 头里给出 resource_metadata URL（以及可选的最小初始 scope 建议）。客户端必须优先解析该头里的地址；如果头里没带，则依次探测路径级 /.well-known/oauth-protected-resource/<mcp-path> 和根路径 /.well-known/oauth-protected-resource。
  2. 授权服务器元数据发现（RFC 8414 / OIDC）：拿到 authorization_servers 后，客户端必须按优先级依次尝试路径插入和追加的 .well-known/oauth-authorization-server 与 .well-known/openid-configuration 端点。拉回文档后，客户端必须按 RFC 8414 Section 3.3 核对文档里的 issuer 字段与构造 URL 所用的发行方标识完全一致，否则立刻拒收（防止恶意站点伪造诚实发行方的元数据）。客户端还必须检查 code_challenge_methods_supported 存在以确认支持 PKCE，缺失则拒绝继续。
  3. 强制 resource 参数（RFC 8707）：客户端在授权请求和换票请求中都必须带上目标 MCP Server 的规范 URI（如 https://mcp.example.com/mcp，不含 fragment，一般不带末尾斜杠）。MCP Server 在收到每条带 Bearer Token 的请求时，必须验证令牌的受众（aud）确实指向自己，不匹配就返回 401。

规范在 2026-07-28 补齐了一项容易踩坑的多授权服务器隔离要求（SEP-2352）：如果一个受保护资源列出多个授权服务器，或者后续切换了授权服务器，客户端必须按 issuer 标识分桶持久化客户端凭证和令牌，绝不能把 A 授权服务器颁发的 client_id 拿去 B 授权服务器复用。

从 DCR 到 CIMD（SEP-991）与防 Mix-Up（SEP-2468）#

在早期的 MCP 规范里，面对客户端和服务端素不相识的场景，默认推荐的是 RFC 7591 动态客户端注册（DCR）。但运行一年后，DCR 暴露了两个现实顽疾：大量企业 IdP 出于防垃圾注册和合规考虑根本不开放公开 /register 接口；而在代理型 MCP Server 场景下，DCR 叠加静态上游 client_id 和浏览器 Consent Cookie，还会诱发严重的 Confused Deputy 攻击（攻击者注册一个指向自己域名的恶意客户端，利用用户浏览器里残留的同意 Cookie 静默跳过授权确认页，偷走授权码）。

于是 2026-07-28 正式将 DCR 标为 Deprecated（PR #2858），并把 Client ID Metadata Documents（CIMD，SEP-991） 扶正为无预置关系时的首选注册方案（最新 draft/ 规范已将其引用升级到 draft-ietf-oauth-client-id-metadata-document-03）。

CIMD 的思路非常清爽：客户端把自己的元数据 JSON 托管在一个带路径的 HTTPS URL 上，比如 https://app.example.com/oauth/client-metadata.json，文档内包含 client_id（必须与文档 URL 逐字符一致）、client_name 和 redirect_uris。发授权请求时，直接把这个 URL 当作 client_id 传给授权服务器。授权服务器看到 URL 形态的 client_id，主动 GET 拉取并缓存这份文档，核验 client_id 一致性、redirect_uri 白名单以及自身信任策略（例如按域名白名单管控，并做好出站 SSRF 防护），无需预先建库、也无需跨授权服务器反复注册，同一个 URL client_id 天生跨所有支持 client_id_metadata_document_supported: true 的授权服务器通用。

客户端注册的推荐优先级由此收敛为四档：优先用预注册凭证，其次用 CIMD，再次回退到 DCR（且 OIDC 场景下按 SEP-837 必须显式指定 application_type: "native" 或 "web" 以免本地回调 URI 冲突），最后才提示用户手动填写。

但 CIMD 的静态文档无法为每个不同发行方配唯一的 redirect_uri，这让多 IdP 环境下的 OAuth Mix-Up 攻击风险抬头。为此，2026-07-28 并入了 SEP-2468（RFC 9207 iss 校验）：客户端重定向前必须在与 PKCE code_verifier 相同的单次请求记录里保存预期 issuer；收到回调时（包括错误回调），只要响应里带了 iss，或者授权服务器元数据声明了 authorization_response_iss_parameter_supported: true，客户端就必须在兑换授权码前用逐字符精确匹配（严禁大小写折叠、默认端口省略或路径归一化）核对 iss。声明支持却缺 iss、或者 iss 对不上，一律立刻中止，且不得把错误响应里的 error_description 展示给用户。

最小权限渐进提权与 Refresh Token 约定#

MCP 遵循最小权限原则，并不鼓励客户端一上来就索要全部读写删权限。如果客户端拿着只读令牌调用了写操作工具，MCP Server 返回 HTTP 403 Forbidden，并在 WWW-Authenticate 头里明确给出本操作所需作用域：

HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
                         scope="files:write",
                         resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource"

服务端应当在单次挑战里一次性给出当前操作所需的全部作用域，避免逐个挤牙膏导致用户连点好几次授权页。客户端收到挑战后执行 Step-Up 授权流：计算已有作用域与新挑战作用域的并集重新发起授权（避免丢掉先前其他操作已获批的权限），并限制重试次数防止死循环。

对于长时运行所需的 Refresh Token，SEP-2207 补齐了 OAuth 2.1 与 OIDC 的互操作细节：需要刷新令牌的客户端应当在元数据 grant_types 里声明 refresh_token，并在授权服务器 scopes_supported 包含 offline_access 时主动追加该作用域；反过来，MCP Server（资源服务器）不应把 offline_access 放进 WWW-Authenticate 或受保护资源元数据中，因为刷新令牌是客户端与授权服务器之间的事，不是资源本身的访问权限。

企业级两大稳定授权扩展#

当 MCP 离开个人浏览器、进入后台流水线和万人规模企业内网时，核心规范的交互式登录就不够用了。官方 ext-auth 仓库已经把两项扩展推到了 Stable 阶段：

机器对机器授权（io.modelcontextprotocol/oauth-client-credentials，SEP-1046），面向 CI/CD 流水线、定时后台代理和服务端到服务端集成。客户端通过 grant_type=client_credentials 直接拿应用凭证换票，依然必须携带 resource 参数绑定目标 MCP Server。规范强烈推荐采用 RFC 7523 JWT Bearer 断言（私钥签发短效 JWT，且按 RFC 10070 规定 aud 只能填授权服务器 issuer 标识，不得填 token 端点 URL），避免在环境里存放一旦泄露就长期有效的明文 client_secret。官方 SDK 示例还特意要求配置 expectedIssuer 钉死颁发凭证的授权服务器，拒绝把密钥发给任何第三方广告的未知授权端点。

企业托管授权（io.modelcontextprotocol/enterprise-managed-authorization，SEP-990），彻底解决文章开头安全团队问的第二个问题：员工不需要逐个去几十个 SaaS MCP Server 点同意，IT 管理员直接在企业 IdP（如 Okta、PingFederate、Descope、Athenz、ThunderID 等）里集中配置访问策略。流程基于 IETF 正在推进的 ID-JAG（Identity Assertion JWT Authorization Grant） 草案与 RFC 8693 Token Exchange：

  1. 员工使用企业 SSO 登录 MCP Client，客户端拿到企业 IdP 签发的 OIDC ID Token 或 SAML 断言。
  2. 客户端连接企业批准的 MCP Server 时，拿着该身份断言去企业 IdP 的 Token 端点发起 RFC 8693 令牌交换（requested_token_type: urn:ietf:params:oauth:token-type:id-jag），指定目标 MCP 授权服务器的 audience 和可选的 resource。
  3. 企业 IdP 实时评估群组、角色和条件访问策略，策略通过才签发 ID-JAG；离职或无权限员工在这一步就被挡住，客户端拿不到任何票据。
  4. 客户端用 urn:ietf:params:oauth:grant-type:jwt-bearer 拿着 ID-JAG 向 MCP 授权服务器直接换取访问令牌，全程无须弹窗跳转，且后续在企业 IdP 侧一键吊销即可全局生效。

截至 2026 年 11 月官方扩展文档记录，Okta（Cross App Access）、PingFederate 13.1+、Athenz、Descope、Janssen、ThunderID 已正式支持签发与校验 ID-JAG，Auth0、Keycloak、Stytch、WorkOS、Cloudflare workers-oauth-provider 和 FastMCP 4.0 也已进入可用或早期体验阶段。而在官方 2026 年 8 月路线图里，新筹建的 Agent Identity 工作组正沿着这条线继续往深处走：推动 DPoP（防截获令牌重放的持有证明）、工作负载身份联邦（SEP-1933），以及面向无头子代理的窄权限委托（与 IETF WIMSE 协同）。

至此，MCP 的无状态传输、强类型原语、MRTR 追问和企业级身份底座已经全部立稳。接下来的问题是如何让协议既能快速长出 Skills、Tasks、Events、Apps 这些高迭代能力，又不至于把核心规范撑成一个臃肿难改的巨无霸。下一章我们看 SEP-2133 与 SEP-3392 的扩展治理框架。

07

扩展机制与治理边界

任何通用协议在爆火后的第二年都会撞上同一堵墙：社区每周都在提新需求，有的想要异步长任务，有的想要嵌入式交互 UI，有的想要企业 IdP 策略接入，有的想要事件推送或文件上传。把这些特性全部塞进核心规范，结果一定是核心体积失控、SDK 维护者疲于奔命、每一次小改动都要拉动整个社区做破坏性升级；反过来，如果核心规范一概拒之门外，各家大厂和开源项目就会各自发明互不兼容的私有 _meta 字段和魔改方法，协议很快四分五裂。

MCP 在 2026-07-28 给出的工程解法，是把核心规范瘦身到最小公约数，再用 SEP-2133（Extensions） 与 SEP-3392（Extension Lifecycle） 搭出一套分层演进的扩展治理体系。今天我们看到的 Skills、Tasks、Events、Apps、Server Cards 和企业授权，全都是这套机制运转出来的产物。

命名空间、能力协商与默认关闭原则#

扩展机制的设计非常克制，不引入额外握手，直接复用核心协议的能力声明结构（docs/extensions/overview.mdx）。

反向域名标识符，每个扩展用 {vendor-prefix}/{extension-name} 格式唯一命名，前缀强制必填。官方扩展统一使用 io.modelcontextprotocol/ 前缀（如 io.modelcontextprotocol/skills、io.modelcontextprotocol/ui）；第三方或企业内部扩展则使用自己拥有的反向域名（如 com.example/my-extension），从命名源头杜绝冲突。

双向按需协商，服务端在 server/discover 的 capabilities.extensions 中声明自己支持哪些扩展及配置对象；客户端则在每条请求的 _meta["io.modelcontextprotocol/clientCapabilities"].extensions 中显式声明自己当前请求开启了哪些扩展。空对象 {} 表示开启该扩展且无额外参数。如果客户端连接的是 2025-11-25 旧版服务端，许多 SDK 也支持在旧 initialize 握手的 capabilities.extensions 里兼容传递相同结构。

默认关闭与优雅降级，规范定了一条硬规则：无论扩展处于哪个成熟阶段，在 SDK 和客户端里都默认关闭，必须由开发者或宿主显式选择启用（opt-in）。SDK 维护者拥有完全自主权决定支持哪些扩展，不受核心一致性测试的强制捆绑。当通信双方只有一侧支持某扩展时，支持方必须回退到核心协议行为（例如支持 MCP Apps 的服务端在面对纯文本客户端时，依然要返回可读的文本 content）；只有当该扩展对业务属于硬前提时（比如某工具必须异步创建 Task 或强制走企业托管授权），服务端才通过 -32021（MissingRequiredClientCapability）或授权错误明确拒掉请求。

SEP-3392：四阶段成熟度生命周期#

早期的 SEP-2133 只区分了实验仓库（experimental-ext-*）和官方仓库（ext-*），结果很快暴露出一个现实问题：实现者分不清哪个官方扩展已经定型可以放心上生产，哪个还在剧烈改动。为了把成熟度信号透明化，SEP-3392 在 2026 年 9 月落地，把扩展生命周期明确划成了四个阶段，并直接用仓库目录路径标明状态：

阶段 仓库与目录路径 允许的变更范围 审批权限 准入门槛 对实现者的承诺
Experimental experimental-ext-<name> 或 ext-<area>/specification/experimental/ 随时可做任意变更，无预先通知 Extension Maintainer 关联 WG/IG，维护者即可创建 无稳定承诺，建议锁死 tag 或 commit
Beta ext-<area>/specification/beta/<name> 优先增量变更；破坏性变更应罕见、打包公告并递增 revision Extension Maintainer 提交 Extensions Track SEP，且至少有 1 份官方 SDK 参考实现 欢迎真实业务试用，文档记录破坏性变更

这里有一个精巧的版本处理细节。按 SEP-2133 最初的写法，只要发生破坏性变更就必须换新标识符（如 -v2），容易造成标识符泛滥。SEP-3392 修正了这一点：阶段跃迁时标识符保持不变；Experimental 和 Beta 阶段如果确实需要破坏性变更，可以在扩展设置对象里增加或递增 revision 字符串，对端不认识该 revision 就自动不启用扩展；到了 Stable 阶段，扩展行为直接锚定在双方协商的核心协议版本号上（如 2026-07-28）。只有当新旧两种不兼容行为必须在同一个核心协议版本里并存时，才需要启用 -v2 新标识符。

08

Skills 进入 MCP：io.modelcontextprotocol/skills

2026 年上半年，团队用 Agent Skills 配合外部服务时，普遍撞上了一个维护噩梦：研发一边维护远端的 SaaS MCP Server 或命令行工具，一边还得单独建一个 Git 仓库分发 SKILL.md 和配套参考文档，挨个催同事拉取更新。一旦后端工作流改了参数约定、公司新上线了一条工单分派规则，半数人的本机硬盘里跑的还是三个月前的过期 SKILL.md。把几百行工作流硬塞进 server/discover 的 instructions 字段也不行，比如 SEP-2640 里提到的 mcpGraph 技能光一份说明书就超过 875 行，全量常驻系统提示会把上下文吃光。

Skills over MCP（io.modelcontextprotocol/skills，SEP-2640 已达 Final，扩展目前处于 Beta 阶段）把 Agent Skills 正式搬进了 MCP 协议内部，直接复用核心的 Resources 原语作为传输层，技能目录格式与渐进披露规范则完整委托给上游 agentskills.io 规范，不在 MCP 里重复定义。Philipp Schmid 在原文中指出，Anthropic 已在 Claude 和 Claude Code 上向公众开放了 Skills over MCP 测试版，Shopify、HubSpot 和 Atlassian 等服务已经能够按当前登录用户的账号与组织，实时下发定制化的业务 Playbook。下面这张图展示了从轻量目录发现到 SHA-256 摘要校验与热更新的完整生命周期。

图里把整个流程切成了四个清晰阶段：连接期只注入极轻的元数据，按需加载前必须核对清单和用户审批，拉回来的每个文件都要校验字节数与 SHA-256 摘要，远端一旦改动技能内容，旧审批自动失效并触发刷新重确认，彻底结束了手工同步 SKILL.md 的割裂时代。

skill:// 寻址规则与三个新增协议方法#

在 SEP-2640 中，一个 Skill 依然是一个包含根目录 SKILL.md 及可选支撑文件（references/、scripts/、examples/ 等）的逻辑目录，每个文件都作为一条标准 MCP Resource 暴露。服务端应当使用 skill:// URI 方案，结构为：

skill://<skill-path>/<file-path>

其中 <skill-path> 可以是单段（如 skill://git-workflow/SKILL.md），也可以带任意层级的组织前缀（如 skill://acme/billing/refunds/SKILL.md），但最后一段必须与 SKILL.md 头部 YAML Frontmatter 里的 name 字段完全一致。规范特意强调两点：第一，skill:// 的首段在 RFC 3986 语法里占了 authority 位置，但这里没有任何网络含义，客户端绝不能对它做 DNS 或网络解析；第二，服务端也可以用自有域名的方案（如 github://owner/repo/skills/refunds/SKILL.md），宿主严禁仅凭 URI 协议头就认定某个资源是技能，唯一可信的认定来源只有 skills/list 或 skills/get 的返回记录。

声明 io.modelcontextprotocol/skills 扩展的服务端必须同时声明核心 resources 能力，并实现以下方法（docs/extensions/skills/overview.mdx）：

  • skills/list（必填）：枚举服务端公开的技能清单，支持 cursor/nextCursor 分页与 SEP-2549 的 ttlMs/cacheScope 缓存字段。每个条目必须是原子完整的（清单不得跨页拆分），包含 uri、原封不动解析出的 frontmatter（至少含 name 和 description），以及完整文件清单 resources（每项含 uri、digest 和字节 size），或者针对动态生成技能标注 "resources": "dynamic"。
  • skills/get（必填）：按 URI 直接获取单个技能条目。规范允许目录极其庞大或按需生成的服务端在 skills/list 里只返回空列表或精选子集，但对它服务的每一个技能都必须响应 skills/get，未知 URI 返回 -32602（Invalid params）。这样，用户、另一个技能或 server/discover 的 instructions 可以直接指向一个未列举技能的 URI，由宿主按需拉取。
  • resources/read（复用核心原语）：读取 SKILL.md 及支撑文件的实际字节内容。
  • resources/directory/read（可选）：仅当服务端在扩展设置里显式声明 directoryRead: true 时客户端才可调用，用来分页列举目录的直接子项（子目录使用 mimeType: "inode/directory"，目录 URI 不带末尾斜杠）。

规范还给服务端划出了体量建议：单个 Skill 包含 SKILL.md 在内不应超过 512 个文件或 16 MiB，宿主则必须能完整支撑这一上限。

渐进披露怎么压住上下文开销#

把 Skills 搬进 MCP 之所以不会重演 2025 年上下文膨胀的老路，靠的是严格的三段式渐进披露，规范甚至用了 MUST NOT 约束宿主不得偷懒预加载：

  1. 连接期只取摘要：宿主调用 skills/list，只把每条技能的 name、description 和来源服务器标识放进系统提示，不拉取任何文件内容。规范明文规定，宿主在连接、列举甚至请求用户审批期间，都不得提前读取技能文件，用户审批直接绑定到清单元数据即可。
  2. 命中后再读正文：只有当模型或用户明确选用某个技能，且通过所需审批后，宿主才调用 resources/read 拉取对应的 SKILL.md。注意，普通路径直接调 resources/read 读到一份 SKILL.md 并不会自动激活技能；必须经过宿主的技能加载通道完成校验后，才算真正载入上下文。
  3. 支撑文件按需延迟加载：SKILL.md 里提到的相对路径（如 references/checklist.md）由客户端相对于技能根目录解析成 skill://code-review/references/checklist.md，等执行流程真走到那一步，再向同一台来源服务器按需读取。

如果服务端连接的是登录态远程 SaaS（如 Shopify、Atlassian 或内部运维平台），skills/list 还可以根据当前 OAuth 令牌代表的账号或组织（配合 cacheScope: "private"），动态返回专属的团队工单模板、审批规范或店铺运营剧本。这是静态托管在 Git 仓库里的本地 SKILL.md 根本做不到的能力。

SHA-256 清单、热更新与五条防投毒红线#

把远程服务器下发的 Markdown 指令直接喂给 Agent，天然带着供应链篡改和提示注入风险。SEP-2640 在完整性和信任边界上写得相当严密，核心靠清单里的 SHA-256 摘要把热更新和安全审批绑成了一体：

  1. 严格限定在保留清单内读取：技能处于活跃期（至少直到 SKILL.md 移出模型上下文）内，宿主必须保留加载时的条目清单，禁止通过该技能读取任何不在清单里的 URI。即使调用了 resources/directory/read 看到了服务端新冒出来的文件，宿主也不得把它当作当前已批准技能的一部分，必须走刷新和重审批流程。
  2. 三重落地校验：每次 resources/read 拿到字节流后，宿主在交付模型前必须校验三项：原始字节长度是否等于清单 size、计算出的 SHA-256 是否等于清单 digest、解析出的 SKILL.md YAML Frontmatter 是否与条目里的 frontmatter 逐字段一致。任意一项不符，立刻丢弃内容，不得给模型看。
  3. 变更即撤销旧审批：持久化的用户审批必须绑定到完整的（文件 URI，摘要）集合。只要远端厂商修改、新增或删除了技能里的任意一个文件，哪怕改了一个标点，摘要就会立刻变化，本地以 (serverId, uri, sha256) 为键的缓存自动失效，旧审批随之作废；宿主调用 skills/get 拉取新清单并再次向用户确认后，才能加载新版本。对于没有固定摘要的 "resources": "dynamic" 技能，宿主有权直接拒载，若允许加载也绝不能把历史审批泛化覆盖到未来任意动态生成的内容上。
  4. 来源标识与跨服务器隔离：技能的唯一身份是 (originatingServerId, skillURI)，光靠 name 不唯一，宿主绝不能允许两个不同服务器的同名技能静默互相覆盖。所有加载进上下文的技能内容必须打上来源服务器标签，且所有支撑文件读取必须锁死在来源服务器上；如果一段技能指令试图诱导 Agent 去读另一台服务器上的资源，宿主必须拦截并弹出明确标明双方服务器名称的逐次确认框。
  5. 不可信内容与防嵌套提权：技能正文一律视为不可信外部输入。凡是涉及宿主侧代码执行或类似 allowed-tools 的权限扩张，都必须按技能逐一获得显式人工批准。如果一个技能目录的子目录里嵌套了另一份 SKILL.md，父技能读取它时只能把它当普通参考文本，宿主严禁静默解析并激活嵌套技能的 Frontmatter；想激活嵌套技能，必须走独立加载和全新同意流程。落盘缓存的远端技能文件还必须设为对模型、工具及其他用户只读不可篡改（或每次读取重验哈希），并且必须排除出本地文件系统技能自动发现路径，防止重启后失去 MCP 来源标记被宿主误当成受信任的本机技能。

这一整套机制在第 14 章的 SkillsServer、SkillHostLoader 以及 test_13 至 test_15 中都有零依赖代码验证。

当服务端不仅能交付强类型工具，还能交付带版本校验和账号定制的工作流剧本之后，同步拉取这一侧的短板基本补齐了。但现实工程里还有大量活根本不可能在几秒钟的 HTTP 请求里跑完，比如跑一次 15 分钟的 CI 流水线、做一轮全库迁移、或者等一位审核人半小时后点批准。下一章我们看面向长程异步作业的 MCP Tasks。

09

长程异步执行：MCP Tasks

在 2026-07-28 之前，想让一个 MCP 工具跑一趟 8 分钟的端到端测试或者云端视频转码，开发者手里只有两个别扭的选择。要么硬扛着 HTTP 连接不放，祈祷沿途的 Nginx、Cloudflare、公司出口代理和客户端 SDK 全都别在 60 秒或 120 秒时把空闲连接掐断；要么在业务层自己手搓一套 start_job / check_job_status / get_job_result 的自定义工具三件套，每家服务器字段名和状态枚举各写各的，客户端宿主完全看不出这是一条挂起中的异步任务，断线重启后也无法统一接管恢复。

2025-11-25 曾经通过 SEP-1686 把实验性 Tasks 塞进过核心规范，但经过大半年真实落地，暴露出三个结构性毛病。第一，握手极其脆弱：客户端必须先调 tools/list 查每个工具的 execution.taskSupport，才能决定调用时带不带 task 参数，不能用统一方式透明调用所有工具。第二，tasks/result 是个阻塞陷阱：旧设计要求任务进入 input_required 时，客户端提前调用阻塞式的 tasks/result 撑开一条 SSE 通道，好让服务端倒着往回塞 elicitation/create 请求，这直接撞上了 2026-07-28 禁止服务端主动发请求的铁律（SEP-2260）。第三，tasks/list 在无会话架构下根本没法安全界定归属范围：删掉 Mcp-Session-Id 后，对于未鉴权或弱绑定场景，服务端只认一个个独立的高熵 taskId，一旦开放全局 tasks/list 就会导致跨用户任务泄露。

于是 2026-07-28 通过 SEP-2663 做了一次彻底重设计：把旧版实验 Tasks 移出核心，发布为官方扩展 io.modelcontextprotocol/tasks（目前处于 Beta 阶段，路线图明确标定目标为成熟后晋升 Core），用一套干脆利落的纯异步状态机彻底替换掉了阻塞式旧模型。

服务端主导的多态返回：告别 tools/list 预热#

新版 MCP Tasks 最舒服的改动，是把要不要创建异步任务的决定权完全交给了服务端，客户端再也不用提前探测每个工具支不支持异步（docs/seps/2663-tasks-extension.mdx）。

协商只需要一步：服务端在 server/discover 里声明 "io.modelcontextprotocol/tasks": {}，客户端在每条请求的 _meta["io.modelcontextprotocol/clientCapabilities"].extensions 里带上同一键名。声明之后，客户端照常发一条普通的 tools/call 请求，既不需要多传特殊标志，也不用先拉 tools/list。服务端根据当前任务的实际预估耗时，按单次请求动态决策：

  • 几百毫秒能算完的，直接返回标准 CallToolResult（resultType: "complete"）。
  • 需要几分钟跑完的，先把任务持久化落盘，再返回 CreateTaskResult（resultType: "task"）。

注意规范的持久化顺序要求：服务端在返回 CreateTaskResult 之前，任务必须已经持久化落成，确保客户端紧接着发来的第一次 tasks/get 一定能查到，在最终一致性存储上也要等写入可见后再回包。如果一个工具必须以异步任务运行，但来访客户端的请求 _meta 里没有声明 io.modelcontextprotocol/tasks，服务端绝不能擅自返回 CreateTaskResult，而是必须返回 -32021（MissingRequiredClientCapability）并在 data.requiredCapabilities 里指明缺少该扩展。

对于不想改动上层业务签名的客户端 SDK，规范给出了很实用的实现提示：SDK 内部完全可以在 callTool() 里透明拦截 resultType: "task"，自动走完后台轮询并把最终 CallToolResult 返回给调用方；而具备异步编排能力的高级 Agent 宿主，则可以把 taskId 直接暴露为后台作业句柄，让主代理一边并行干别的事，一边等任务终态。

五态生命周期与三个精简 RPC#

删掉阻塞式的 tasks/result 和高风险的 tasks/list 后，整个 Tasks 扩展只剩三个清晰的方法：tasks/get、tasks/update 和 tasks/cancel，围绕五个状态流转（docs/extensions/tasks/overview.mdx）：

任务状态 性质 携带附加字段 含义与流转规则
working 进行中 可选 statusMessage 任务正在后台执行
input_required 进行中（挂起） inputRequests 执行中途需要客户端提供人工确认或输入，等待 tasks/update
completed 终态（不可变） result 原始请求执行完毕，内联原始结果（包含 isError: true 的工具业务报错）
failed 终态（不可变） error 执行期间发生 JSON-RPC 协议级错误（不得混用普通业务错误）
cancelled 终态（不可变） 可选 statusMessage 任务在完成前被取消

一旦进入 completed、failed 或 cancelled 三个终态之一，任务状态永久冻结，不再变化。还要留意一个容易写错的细节：completed 和 failed 的划分严格对齐 SEP-1303，如果一个工具任务正常跑完了但业务上返回了 isError: true（比如目标仓库里测试没过），任务状态应当是 completed 且在 result 里原样携带带 isError: true 的 CallToolResult，让模型看到测试失败详情；只有发生 JSON-RPC 级异常（如服务端内部崩溃或任务超过 TTL 失效）才用 failed。

在 tasks/get 轮询中，服务端通过 pollIntervalMs 给出建议轮询间隔（且允许在任务生命周期内动态调整，比如前期慢、收尾快），客户端应当遵守该间隔，以免被服务端限流，同时应当持久化 taskId，这样哪怕客户端进程崩溃或网络断开，重启后照样能凭 ID 接上进度。如果不想纯轮询，服务端也可以支持通过 subscriptions/listen 传入 notifications: { taskIds: [...] }，由服务端在状态变化时直接推送携带完整 DetailedTask 的 notifications/tasks 通知，省掉额外一次 tasks/get 往返。注意，Tasks 扩展明确禁止在监听流上混发 notifications/progress 或 notifications/message。

任务中途追问（tasks/update）与协作取消（tasks/cancel）#

长程任务跑着跑着常常需要人工拍板，比如批量迁移脚本扫出 3 张高危表，需要管理员确认后再继续删旧索引。SEP-2663 复用了 MRTR 的 inputRequests/inputResponses 数据结构，但明确区分了两个时机：

  • 建任务之前需要补充信息（比如连参数都没齐、还决定不了要不要建任务）：直接在原始 tools/call 上同步走第 5 章的 MRTR（InputRequiredResult）解决。
  • 建任务之后执行到半途需要输入：任务状态切到 input_required，在下一次 tasks/get（或 notifications/tasks）里附带当前所有未满足的 inputRequests 快照。

客户端看到 input_required 后，把请求呈现给用户，拿到答复后调用 tasks/update 提交 inputResponses，服务端返回空确认即可（允许最终一致性，不必等后台状态立刻翻回 working 才回包）。为了防止连续两次轮询把同一个确认弹窗反复弹给用户，规范定了两条互保约束：服务端保证同一个 taskId 整个生命周期内，inputRequests 的每个键名绝不复用；客户端按已处理键名做去重，服务端则静默忽略重复或已失效的键。

取消任务同样走专门的 tasks/cancel 方法，规范明文禁止用核心的 notifications/cancelled 去取消 Task。取消是协作式（Cooperative）且最终一致的：服务端收到 tasks/cancel 只需立刻返回空确认并尽量通知后台作业停手，但并不保证一定能拦住已经走到最后一毫秒的写入，因此任务最终仍有可能落到 completed 而非 cancelled；客户端发完取消后即可自行清理本地记录，无需死等状态翻转。

路由头、高熵能力令牌与 TTL 安全边界#

把 Tasks 跑在分布式 HTTP 集群里，还有三道架构与安全约束不能漏：

  1. Mcp-Name 承载 taskId 实现网关路由：在 Streamable HTTP 下，发送 tasks/get、tasks/update 或 tasks/cancel 时，客户端必须把 HTTP 头 Mcp-Name 设为 params.taskId（Mcp-Method 照常设为对应方法名）。如果某些服务端的后台作业状态只存在特定分片或节点上，中间网关无需拆解 JSON Body 就能按 Mcp-Name 精准路由。
  2. 高熵 taskId 与权限重验：如果服务端有 OAuth 2.1 鉴权，每次 tasks/get、tasks/update 和 tasks/cancel 都必须重新校验调用方身份是否匹配任务创建者（owner_principal），不能只凭猜到或捡到一个 taskId 就偷看别人任务的结果；对于无鉴权场景，taskId 必须具备至少 128 位密码学随机熵（例如 32 位十六进制随机串或 UUIDv4），防止枚举撞库。
  3. ttlMs 兜底与资源回收：每个任务都有自创建起算的 ttlMs（null 表示无过期上限）。超过 createdAt + ttlMs 后，服务端有权把未完成任务标为 failed 并回收存储，客户端也应把超时未刷新的任务视作失效，避免僵尸轮询永远挂在调度器里。

Tasks 解决的是 Agent 自己发起长耗时作业后如何持续追踪直到完成。但现实工作流还有另一半完全相反的方向：凌晨两点生产环境爆了一条 P0 安全告警、客户发来一封紧急索赔邮件、或者 GitHub 仓库里合并了一个新 PR，此时用户压根没打开对话框，Agent 根本不知道发生了什么。下一章我们看让 Agent 真正跨入常驻与多人协作时代的 MCP Events。

10

常驻与多人协作代理：MCP Events

凌晨两点十四分，auth-api 触发了一条 P0 安全告警。在 2026 年秋以前，就算你的团队接好了二十台 MCP Server，Agent 这会儿也在呼呼大睡。传统 MCP 是纯拉取驱动的：用户或模型不发问，服务端就永远沉默。核心规范里虽然有 subscriptions/listen 和 notifications/resources/updated，但它们根本扛不起异步事件驱动的三项硬要求：第一，核心通知只报某个 URI 变了，不带订阅过滤参数，也没有载荷 Schema，表达不了只订阅 auth-api 的 P0 告警；第二，核心通知要求客户端死死挂着一条长连接，一断网就什么也收不到；第三，没有游标（cursor），断线期间发生的所有事直接丢进黑洞，客户端甚至不知道自己漏了消息。

MCP Events（io.modelcontextprotocol/events，SEP-3415 已达 Final，扩展处于 Beta 阶段，要求核心协议 2026-07-28 及以上）补齐了 Agent 运行时最关键的最后一块动态能力：把 MCP 从被动应答的远程工具箱，推进到外部事件触发、离线可唤醒、多人可协作的常驻代理平面。Philipp Schmid 在原文里提到，Shop MCP（订单变更）和 Vercel（deployment.succeeded）等早期服务已经上线了事件支持，OpenCode 2.4.0 等宿主则把事件订阅封装成了自动化工具，ChatGPT 等远程持久化宿主开始开放回调端点，在用户离线时也能接住告警并自动拉日志完成初筛。下面这张图把 MCP Events 的三种投递模式、去重消费层和 MCP Tasks 的协同链路画了出来。

图里左侧的三条分支对应不同部署形态的投递选择，中间的 Client SDK 消费层统一吸收游标持久化、缺口感知、eventId 去重与不可信输入隔离，右侧则由唤醒后的 Agent 按需触发工具或把耗时的修复排查工作转成 MCP Tasks 持续跟踪。

为什么必须同时定义三种投递模式#

SEP-3415 最务实的设计决定，是没有强推某一种统一传输，而是按部署现实同时定义了 Webhook、Push 和 Poll 三种模式。原因很直白：Serverless 服务端挂不住成千上万条常驻推送连接；跑在开发者笔记本或内网 NAT 后面的 CLI 客户端没有公网 HTTPS 回调地址；对电池和费用敏感的移动端或托管宿主又不该无休止空转轮询。任何单一模式都会把至少一类真实场景拒之门外。

因此在 events/list 返回的每个事件类型描述符里，除了事件名 name、订阅过滤参数 inputSchema（同样支持 x-mcp-header 镜像到 HTTP 头）和事件载荷 payloadSchema 之外，服务端通过 delivery 数组声明该事件支持哪几种模式（三选其一至全选皆可，没有强制项），客户端 SDK 根据自身运行环境自动择优（典型优先级：有公网回调就选 Webhook，能保活连接就选 Push，其余走 Poll）：

投递模式 协议方法 服务端状态与保活机制 适用部署形态 顺序保证
Webhook events/subscribe / events/unsubscribe 服务端保存带可续期 TTL（refreshBefore）的回调订阅，支持 ttlMs: null 申请永不过期（服务端可拒绝并给有限值） 远程无状态/云端常驻宿主、支持前向代理（Forward Proxy）中转 尽力有序，以 timestamp 为准
Push events/stream 单条订阅一条长生命周期请求（HTTP POST 返回 SSE，stdio 走 stdout 按 subscriptionId 解复用），服务端按 heartbeatMs（默认建议 30 秒）发 JSON-RPC 心跳推进游标 本地 stdio 服务、常在线桌面端或实时构建/部署日志流 订阅内严格有序
Poll events/poll 服务端无需保存每客户端订阅状态；首次传 cursor: null 拿到起点游标，后续按 nextPollMs 轮询（客户端应设 1000ms 下限防死循环），hasMore: true 时立即连拉清积压 Serverless 无状态服务端、NAT 后简单 CLI 订阅内严格有序

有一条架构原则贯穿三种模式：客户端永远是订阅清单的唯一权威来源。服务端不提供 events/subscriptions/list 枚举接口；如果服务端重启丢了内存里的短 TTL 订阅，客户端下一次续期或重连时带着本地持久化的订阅参数和 cursor 就能无损重建。还要注意 Push 模式的心跳细节：Streamable HTTP 下，events/stream 的心跳故意不用 SSE 注释行（: keepalive），而是发正式的 notifications/events/heartbeat JSON-RPC 通知，因为心跳帧里必须携带最新的 cursor，防止长时间静默导致客户端手里攥着过老的游标落出上游保留窗口。客户端连续三个 heartbeatMs 没收到任何帧，就判定流已死并带随机抖动（jitter）重连。

Webhook 契约、Standard Webhooks 签名与续期机制#

回到凌晨两点的 P0 安全告警场景。远程宿主（比如 ChatGPT 或企业后台调度器）暴露一个 HTTPS 回调地址，调 events/subscribe 注册过滤条件与密钥（注意 SEP-3415 中 Webhook 投递对象使用 delivery.mode: "webhook" 和 delivery.url 字段，早期草案及部分示例写法使用 type/callbackUrl，对接具体服务端时需按其 revision 与 Schema 对齐）：

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "events/subscribe",
  "params": {
    "name": "security.alert.opened",
    "arguments": { "severity": "p0" },
    "delivery": {
      "mode": "webhook",
      "url": "https://host.example/mcp/webhook/sub_01H",
      "secret": "whsec_bXlzZWNyZXRrZXkyNGR5dGVzbWluaW11bQ=="
    },
    "cursor": null,
    "maxAgeMs": 300000,
    "ttlMs": 3600000
  }
}

这里有四条规范级细节非常值得工程团队记牢：

  1. 密钥必须由客户端生成且符合 Standard Webhooks 规范：delivery.secret 必填，格式必须是字面前缀 whsec_ 后接 24 到 64 字节密码学随机数的 Base64 编码，服务端遇到不合规密钥必须以 InvalidParams 拒收。投递时服务端按 Standard Webhooks 规范对消息 ID、时间戳和原始 Body 计算 HMAC-SHA256 签名；接收端必须验签并校验时间戳窗口以防重放。
  2. 服务端派生确定性 id：响应返回的 id（如 sub_a3f1c8e2b0d49f7e）由服务端根据 (principal, delivery.url, name, arguments) 确定性计算，每次投递放在 X-MCP-Subscription-Id HTTP 头里供接收端路由。重复调用同一组键的 events/subscribe 是幂等的，既用来刷新 refreshBefore 租约，也用来在服务端重启后原地重建订阅。
  3. 回调端点防 SSRF：回调 URL 必须走 https，服务端在真正投递前必须先验证端点并校验解析出的目标 IP，拦截私有网段、回环地址和云元数据地址（如 169.254.169.254），防止攻击者借事件订阅把 MCP Server 当内网探测跳板。
  4. 前向代理（Forward Proxy）解耦模式：规范特意指出，Webhook 回调地址不必就是最终运行模型的客户端本身。很多桌面或移动宿主会部署一个轻量的公网前向代理统一接住远程 MCP Server 的签名 Webhook，再通过 Push 或 Poll 转交回内网客户端，把公网暴露面收敛到单一网关。

游标、缺口感知、eventId 去重与轨迹续跑#

外部事件投递在分布式系统里天然是至少一次（at-least-once）语义。SEP-3415 用一套克制的字段把可靠消费的边界讲清了：

每一条事件发生对象 EventOccurrence 都包含 {eventId, name, timestamp, data, cursor}。服务端应当直接复用上游系统自带的稳定事件 ID（如 Stripe 的 evt_*、GitHub 投递 GUID、Kafka offset 或邮件 Message-ID），这样哪怕同一事件同时从 Webhook 和断线补拉（Poll backfill）两条路径送达，客户端也能精准识别重复。去重的作用域严格限定在单条订阅 (name, arguments) 内；如果用户同时订了某个频道的所有消息和某位老板发的所有消息，同一条消息触发了两条不同订阅，两边拿到相同 eventId 并不算重复，各自都要投递。

游标 cursor 对客户端完全不透明，支持上游可重放时用于断线续传；如果上游本身没有历史日志，服务端返回 cursor: null，客户端接受断线期间事件不可恢复的事实。客户端还可以在重连或轮询时传入 maxAgeMs（有界回放），避免一台离线一周的笔记本一开机就把过去七天积压的几万条事件瞬间灌进 Agent。如果客户端传来的旧游标已经落出了上游保留窗口，服务端不会报错中断，而是返回 truncated: true 和最新起点游标，明确提示中间可能存在漏掉的事件，让 Agent 视业务重要性决定要不要主动调工具重新拉取一次权威状态。

事件通过验签和去重交给 Harness 之后，真正决定产品体验的是轨迹续跑策略（Continuation），Philipp Schmid 在原文里点明了两种截然不同的路由模式：

  • 同轨迹续跑（Same Trajectory）：把新事件直接注入发起订阅的那条对话线程里，适合围绕同一项持续工作（比如盯着某个 PR 的 CI 与评审进展、跟进一个线上事故工单）保持完整上下文记忆。
  • 隔离新轨迹（Isolated Trajectory）：每来一条新事件就派生一条全新的独立执行轨迹，适合每收到一封高优客户邮件或每出现一条新 P0 安全告警这类彼此独立的工单分诊，防止多起不相关事件把同一条长对话搅成一锅粥，也能把某一条恶意外来事件里的提示注入严格隔离在单次沙箱轨迹内。

Events 与 Tasks 的分工和组合#

架构评审里最常被问到的问题是：MCP Tasks 和 MCP Events 都在解决异步，到底什么时候用哪个？官方规范划出的分界线非常清楚：等待自己刚发起的长耗时作业出结果，用 MCP Tasks；监听外部系统在未知时刻发生的业务活动，用 MCP Events。

两者组合起来就是 2027 年无人值守代理的完整执行回路：

  1. 团队提前通过 events/subscribe 订阅 security.alert.opened（过滤 severity: "p0"）并写好常驻处置指令。
  2. 凌晨两点告警触发，服务端签名 POST 到宿主回调，宿主验签去重后在隔离轨迹中唤醒 Agent。
  3. Agent 拿到最小载荷（只有 alertId 和 service，遵循安全规范绝不把整段外部日志塞进事件体），随后用 OAuth 2.1 令牌调用日志和代码仓 MCP Server 查明根因。注意：收到事件本身绝不授予 Agent 任何执行权限，后续所有工具调用仍须走完整的 OAuth 校验，且服务端在订阅期满或账号权限被撤销时必须立即终止事件投递。
  4. 如果排查或回滚需要跑一趟耗时 10 分钟的自动化验证流水线，Agent 调起部署工具拿到一个 MCP Task 句柄，在后台持续轮询或监听状态，跑完后把根因摘要和修复链接发到值班频道，等值班工程师早上打开电脑就能直接拍板。

文本回复、类型化脚本、异步任务和事件唤醒都已经就位，但工程师和业务人员终究不只是盯着纯文本日志工作。当你面对一张 P95 延迟趋势图、一个需要筛选几十个维度的发布看板、或者一份需要缩放批注的 PDF 和设计稿时，纯文本和原始 JSON 远远不够。下一章我们看已经进入 Stable 阶段的 MCP Apps。

11

产品原生智能体化：MCP Apps

用户在对话窗口里提出要求：把上个季度各区域的营收异常和 P95 延迟对比拉出来，顺便把核心服务的发布单配好。如果 MCP Server 只返回一段 Markdown 表格和四条外部链接，用户接下来就得切出对话、连续点开四个浏览器标签页，在四个不同后台之间来回复制 ID、筛选时间范围、再切回聊天框告诉 Agent 自己选了哪几项。一旦需要多维交互筛选、表单联动配置、3D 模型/地图钻取或者实时监控看板，纯文本和静态图片很快就不够用了。

MCP Apps（io.modelcontextprotocol/ui，SEP-1865 已达 Final，扩展本身在 ext-apps 仓库中已达到 Stable 阶段）把交互式界面正式纳入了 MCP 协议。根据官方客户端支持矩阵与 Philipp Schmid 原文记录，目前 Claude（Web 与 Desktop）、ChatGPT、Cursor、VS Code GitHub Copilot、Microsoft 365 Copilot、Slack 新版 MCP 客户端、Google Antigravity、Goose、Postman、MCPJam 和 Glean 等主流宿主都已经落地了这一模式，覆盖行内聊天卡片、侧边发布看板和自定义文件查看器三种核心形态。

为什么不在工具结果里直接返回 HTML，而是用预声明 ui:// 资源#

早期的社区实验（如 MCP-UI 早期方案）曾尝试让工具调用直接在返回体里内联一段 HTML，虽然写起来省事，但很快在宿主侧暴露出三个硬伤：第一，每次工具执行完才开始传输前端代码包，首屏渲染延迟高，无法流式展示工具输入；第二，界面模板和业务数据搅在一起，宿主没法缓存 UI 壳子；第三，安全团队无法在执行前对 UI 资源做静态审查或版本核验。

因此 SEP-1865 统一了 MCP-UI 与 OpenAI Apps SDK 两条路线，确立了工具声明加预声明 ui:// 资源的双原语解耦架构（docs/extensions/apps/overview.mdx 与 docs/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp.mdx）：

  1. 能力协商：客户端在每条请求的 _meta["io.modelcontextprotocol/clientCapabilities"].extensions 里声明支持 io.modelcontextprotocol/ui 及可渲染的 MIME 类型（目前首发基线为 text/html;profile=mcp-app）；服务端在 server/discover 中广告同一扩展。面对不支持该扩展的纯文本或命令行客户端，服务端必须按优雅降级原则继续返回有意义的文本或 structuredContent。
  2. 元数据绑定与预加载：需要交互界面的工具在工具描述中挂上 _meta.ui.resourceUri，指向一个 ui:// 资源（例如 ui://analytics/latency-dashboard）。因为资源地址在 tools/list 阶段就已经声明，宿主完全可以在工具真正被调用之前就预取并缓存 HTML 模板，甚至在工具还在流式输出参数时提前把界面架子撑起来。
  3. 资源获取与策略解析：宿主通过核心 resources/read 拉取该 ui:// 资源，拿到打包好的 HTML/JS/CSS（资源元数据 _meta.ui 内还可声明 csp 外链白名单与 permissions 如麦克风/摄像头请求）。
  4. 受限 iframe 渲染与双向 JSON-RPC：Web 或桌面宿主把 HTML 放进严格受限的沙箱 <iframe> 中渲染。App 与宿主之间不发明专有私有消息格式，也不向 iframe 注入宿主私有全局对象，而是通过浏览器标准 window.postMessage 通道收发 MCP 风格的 JSON-RPC 消息（复用 tools/call 等核心方法，加上 ui/initialize 等 ui/ 前缀专用方法）。

下面这条完整交互链路最能体现 MCP Apps 相比独立 Web 应用的优势：

  • 模型调用 get_latency_report 工具，服务端返回底层的 structuredContent 指标，宿主把结果推送进对话里已渲染好的折线图 iframe；
  • 用户直接在图上拖拽时间区间、点选某条毛刺曲线，iframe 通过 postMessage 向宿主发一条 tools/call 请求下钻该时间段慢查询；
  • 宿主按现有 MCP 鉴权与权限策略（必要时弹窗征求用户同意）转发给 MCP Server，拿到最新数据推回 iframe 刷新图表；
  • 用户选中某条异常慢查询并触发助手分析动作，iframe 通过上下文更新消息把选中项回传给宿主和模型，对话直接接着往下走，全程零跳转、零重复登录、零手写外部前端鉴权代码。

更重要的是，iframe 里的 App 还可以把跨域动作委托给宿主能力。比如一个项目管理 MCP App 需要发一封延期通知邮件，它不需要自己去对接 Gmail 或 Outlook 的 OAuth 接口，只需向宿主发出意图请求，由宿主经用户确认后路由给用户早已接好的邮件 MCP Server 执行。

三种宿主视图形态与产品边界#

在 Philipp Schmid 的观察和主流宿主落地实践中，MCP Apps 已经分化出三种各司其职的呈现形态：

  • 对话行内视图（Inline in Chat）：适合延迟图表、审批确认单、代码差异对比、地图点选和小型配置表单，紧贴上下文讨论，看完即走。
  • 独立侧栏工作区（Side Panels）：适合发布看板（Release Board）、持续刷新的实时监控面板、多步骤工单分诊队列，让用户一边在左侧和 Agent 讨论，一边在右侧持续操作持久视图。
  • 自定义文件查看器（Custom Viewers）：适合 PDF 批注、3D 场景（如 ext-apps 官方示例中的 Three.js 与 CesiumJS 地球仪）、音频乐谱、白板（如 Excalidraw）等富媒体内容，替代简陋的纯文本预览。

反过来，官方指南也很清醒地划出了不该做 MCP App 的边界：如果你的界面与对话上下文无关、不需要模型协助决策、也不需要复用宿主已连接的其他工具能力，做个普通独立 Web 应用反而更简单、屏幕空间也更大。MCP Apps 的真实价值在于把人机协作最频繁的那几步可视化确认和钻取无缝嵌进 Agent 工作流，而不是把整套后台管理系统硬塞进聊天框。

沙箱边界与宿主侧安全治理#

把第三方 MCP Server 返回的可执行 HTML/JavaScript 直接放进用户主应用里跑，如果不把隔离做死，后果比普通跨站脚本更严重。SEP-1865 和 ext-apps 的安全模型（宿主侧官方提供了 @modelcontextprotocol/ext-apps 的 AppBridge 与 @mcp-ui/client 组件）守住了四道关口：

  1. 强隔离 iframe 沙箱：iframe 无法访问父页面 DOM、无法读取宿主 Cookie 和 localStorage、无法顶层导航劫持父页面，也不能在父窗口上下文里执行脚本。
  2. 严格 CSP 与最小能力授权：除非资源的 _meta.ui.csp 明确声明且宿主安全策略放行，默认封死任意外域脚本加载与外联请求，防止界面偷偷把对话推送进来的敏感业务数据外传（Data Exfiltration）。类似 sendOpenLink、麦克风、剪贴板等宿主能力默认关闭，按需受控开放。
  3. 可审计的 JSON-RPC 桥接：UI 发起的每一次 tools/call 或上下文注入都必须经过宿主的 postMessage 桥接层。宿主可以完整记录审计日志、限制该 App 只能调用自身所属服务器的白名单工具，并对所有写操作强制弹人工确认框。
  4. 防界面侧间接提示注入：UI 回传给模型的上下文更新同样来自不可信的第三方代码。如果一个恶意 MCP App 在用户无感知的情况下偷偷往模型上下文里塞进隐藏指令（比如诱导模型去调另一台服务器的删除工具），宿主必须把 UI 上下文更新明确标示来源，并对跨服务器工具调用保持严格的人工审批门禁。

说到这里，我们已经把 2027 年 MCP 运行时最亮眼的拼图全部摊开了：无状态 HTTP 内核、强类型契约与 Code Mode、MRTR 与 OAuth 2.1/企业 IdP、Skills、Tasks、Events 和 Apps。但 Philipp Schmid 在文章后半段特意泼了一盆很务实的冷水：这套体系还有三块硬骨头没啃完。下一章我们直面这些未解的工程缺口，把发现机制、意图可观测性和纵深安全攻击面一次拆透。

12

未解难题：发现、可观测性与纵深安全

把一个远程 MCP Server 做到符合 2026-07-28 规范，上线后的第一个月往往还是会遇到三类扎手的运营难题。第一类来自上线推广：厂商为了被不同客户端找到，得把同一份服务器配置挨个提交给五个互不相通的目录和市场，版本一升级到处失步。第二类来自线上排障和产品迭代：后台监控日志每天刷过几十万次 tools/call，工具成功率 99.5%，可产品经理根本不知道用户为什么调它、模型是不是绕了三圈弯路才勉强凑齐参数、最后到底帮没帮用户把事办成。第三类来自安全评审：每给协议加上一项新扩展（Code Mode、Webhook Events、iframe Apps、一键本地安装），攻击面就实打实往外扩一圈。

Philipp Schmid 在原文的 What still needs work 一节里直接点出了这三块缺口：发现、可观测性与意图、纵深安全。对照 mcp-spec 仓库现有的 Registry 文档、SEP-2127、安全最佳实践与 SEP-1024，我们可以准确分辨哪些已经有标准雏形，哪些在 2027 年依然悬而未决。

发现层：从中心化 Registry 到 /.well-known Server Cards#

目前 MCP 社区的发现体系正在两条轨道上并行演进，各有明确职责边界。

第一条轨道是官方 MCP Registry（docs/registry/about.mdx，目前处于 preview 阶段，由 Anthropic、GitHub、PulseMCP 和 Microsoft 等维护）。它是一个中立、不做主观评分的中心化元数据仓库，通过反向 DNS 命名空间验证（GitHub、DNS 或 HTTP 挑战，例如 io.github.user/server-name 或 com.example/server）确保发布者真实身份，以统一的 server.json 格式指向 npm/PyPI/Docker 包或公网远程 URL。注意它的三个明确设计边界：

  • 不托管二进制代码，也不做私有服务托管：代码依然留在 npm、PyPI 和 Docker Hub，企业内网私有 MCP Server（如 mcp.acme-corp.internal）需要自行实现符合 Registry OpenAPI 规范的私有注册表。
  • 不直接面向终端宿主，而是供下游聚合器拉取：官方预期各类应用市场和聚合器按小时拉取元数据，再叠加评分、策展和额外安全扫描。
  • 本身不做代码级安全扫描：官方明确把漏洞扫描与恶意代码检测委托给了底层包仓库和下游聚合器，主站只负责命名空间认证、字段校验和人工下架。

第二条轨道就是 Philipp Schmid 点名看好的去中心化域名发现：MCP Server Cards（SEP-2127 已达 Final，扩展处于 Beta 阶段，ext-server-card）。它要解决的是连接前发现：客户端拿到一个域名（如 restaurant-a.com），无需人工去五个市场翻找，也无需提前打开 MCP 连接，直接访问域名下的 /.well-known/ai-catalog.json 就能找到该域名关联的若干 MCP Server Card（推荐托管在 <streamable-http-url>/server-card），一次静态 HTTP GET 就能读出服务器身份、远程传输 URL、支持协议版本与连接指引，且天然兼容 CDN 缓存和自动化索引。

SEP-2127 做了一个极其关键的安全取舍：Server Card 故意不包含工具、资源和提示词列表，也不声明运行时扩展能力。因为这些列表可能因登录账号、权限 Scope、灰度开关和部署状态而异，如果允许静态卡片直接广告工具清单，客户端就会基于过期或被篡改的静态文档做权限和安全判断。静态卡片只回答服务器在哪、怎么连；连上之后的一切能力与工具清单，一律以带鉴权的实时 server/discover 和 tools/list 为准，两者冲突时始终以实时结果为准。

尽管如此，发现层离真正省心还差最后一公里：当域名发现普及后，自动化供应链扫描、恶意工具描述检测（Tool Poisoning）和可信签名背书怎么无缝接入客户端安装流，目前社区里还没有统一的强制标准。

可观测性与意图黑洞：隔离原则带来的天然张力#

回顾第 1 章提到的 MCP 四条核心设计原则之一：服务端不得读取完整对话，也不得窥探其他服务器（docs/specification/2026-07-28/architecture/index.mdx）。这条隐私隔离红线保护了用户，却给服务端可观测性留了一个大坑。

从服务端视角看，每天收到的是一堆孤立的 JSON-RPC 请求：有人查了三次列表、调了一次详情、接着没下文了。服务端根本不知道这是模型顺利完成了任务，还是返回字段写得太晦涩导致模型看懵放弃了；也不知道用户原本想做数据分析、排障还是写代码。

目前协议层已经落地的可观测性标准只有 SEP-414，它约定了在 _meta 里透传 OpenTelemetry 的 traceparent、tracestate 和 baggage 字段，解决了分布式链路追踪的串连问题。但链路 ID 只能告诉你哪几个 RPC 属于同一次调用，回答不了为什么调和效果好不好。

Philipp Schmid 在原文里提到了两条正在试水的补充手段：一是客户端在请求元数据里传递脱敏后的高层意图标签（如 telemetry.intent）；二是服务端主动暴露轻量反馈工具（类似 Cloudflare 的 submit_feedback），允许模型在遇到工具描述模糊、参数难凑或结果缺失时提交结构化改进反馈。工程上这里有一个微妙的平衡点：意图元数据绝不能变成变相泄露用户完整聊天记录的后门，必须限制在粗粒度任务分类或用户显式同意的遥测范围内；而反馈工具也必须防模型滥用刷屏或把敏感业务上下文误塞进反馈正文里。如何用标准扩展既保护对话隐私、又让服务端看懂调用意图，是 2027 年非常值得关注的演进方向。

纵深安全：2027 新扩展带来的五重攻击面#

随着 MCP 从纯工具调用进化成完整运行时，安全边界远不止校验 OAuth Token 那么简单。把官方 security_best_practices.mdx、SEP-1024 和 Phil Schmid 的风险清单合并起来，工程团队在上线前必须逐项核查五类攻击面：

攻击面 典型攻击手法 规范与工程防线
1. 身份与代理链路 令牌透传（Token Passthrough）、OAuth Mix-Up 混肴、代理型服务器 Confused Deputy、本地 localhost 回调劫持 严格验证 RFC 8707 aud 受众；校验 RFC 9207 iss；代理服务器对每个注册客户端单独实施带 __Host- Cookie 与防点击劫持的二次同意页；弃用 DCR 转向 CIMD 域名信任策略
2. 提示注入与工具投毒 恶意或被攻破的外部工具在 description、返回文本或资源内容中藏匿隐藏指令（Tool Poisoning / Indirect Prompt Injection），诱导模型调用另一台高权限服务器 永远把工具注解、返回内容、技能正文、事件载荷视为不可信输入；跨服务器写操作和敏感读取强制人机确认；宿主打通来源标签隔离
3. 不可信 Webhook 与 SSRF 攻击者利用 events/subscribe 或 CIMD 元数据拉取功能，让服务端向内网 169.254.169.254、127.0.0.1 或内网管理端口发起请求；伪造或重放事件 POST 强制 HTTPS 与目标 IP 校验（拦截私有、回环、链路本地网段，防范 DNS 重绑定）；严格校验 Standard Webhooks HMAC 签名与时间戳窗口；事件载荷最小化，事件触发隔离新轨迹
4. Code Mode 沙箱与 MCP Apps iframe 沙箱脚本试图读取宿主机磁盘、环境变量或直连外网外泄数据；恶意 MCP App 突破 iframe 偷取宿主 Cookie 或静默伪造模型上下文 Code Mode 运行在无磁盘凭证、无直连外网的隔离沙箱，OAuth 留在沙箱外；MCP Apps 锁死受限 iframe + 严格 CSP，所有 postMessage JSON-RPC 经宿主白名单审计
5. 本地服务器安装与 DNS 重绑定（SEP-1024） 钓鱼链接诱导用户一键安装恶意本地 MCP Server 静默执行任意命令；远程网页通过 DNS 重绑定攻击监听 0.0.0.0 的本地 HTTP MCP Server SEP-1024 强制规定：安装前弹窗展示未截断的完整命令和全部参数并要求用户显式点击确认；本地 Streamable HTTP 仅绑定 127.0.0.1 且强制校验 Origin 头，非法 Origin 一律回 HTTP 403

此外，在企业网关侧还有一个实战细节：千万不要以为把 MCP Server 藏在公司 VPC 里就高枕无忧了。凡是支持 CIMD、远程资源读取、URL Mode Elicitation 或 Events Webhook 的服务端，都会主动向外发 HTTP 请求，必须统一经过带出口白名单与私网黑名单的专用 Egress Proxy（出口代理），不能直接给服务端容器开放任意出站网络权限。

把安全边界拉直之后，最后还剩一个最具前瞻性的架构命题：如果一台客户端已经集齐了 Code Mode、Typed Tools、Skills、Tasks、Events 和 Apps，多代理协作本身还需要另发明一套全新的协议吗？下一章我们拆解 Philipp Schmid 原文最后抛出的核心判断：把 Agent Harness 本身做成 MCP Server，以及为什么把整个 SaaS 包成单个 ask_agent 工具是必须避开的架构反模式。

超越远程工具：把 Harness 做成 MCP Server 与架构反模式

2026 年做多代理（Multi-Agent）系统的团队，几乎都重复干过一件吃力不讨好的事：给主代理和子代理之间自己画一套专有通信协议。有人用 Redis Pub/Sub 拼任务队列，有人自己写了一套 HTTP 回调网关管子代理生命周期，有人又另造一套共享黑板 API 给同伴代理同步进度。结果每换一个外部编排器或者想把两支团队的 Agent 接在一起，又得从头写一遍胶水适配器、鉴权转发和超时重试逻辑。

Philipp Schmid 在《Why I'm Bullish on MCP for 2027》的结尾给出了一个非常犀利的判断：**2027 年胜出的 Agent Harness 不仅要做好 MCP 客户端集成，Harness 自己也应该暴露成一台 MCP Server。**与其另起炉灶发明一套私有跨代理协议，不如让多代理协作直接复用它们本来就精通的那同一套 MCP 原语。下面这张图把 Harness-as-MCP-Server 的编排平面，连同前文拆解的四重安全防线与三大工程缺口收束在了一张总览里。

图里左侧展示了同一套 MCP 协议如何向下连业务系统、向上做多代理协作；右侧对应每新增一层扩展能力就必须同步补齐的四重安全边界；底部则提醒架构师在 2027 年落地时持续盯着发现层与意图可观测性两块未完拼图。

用现成 MCP 原语拼出多代理协作平面#

把一个 Agent Harness 暴露成 MCP Server 后，多代理系统里最麻烦的三件事，全部能严丝合缝地映射到我们前面几章刚拆过的标准协议能力上，不需要发明任何一个专有新字段：

  1. 子代理派发即 MCP Tasks（io.modelcontextprotocol/tasks），主代理或外部协调者调用类似 spawn_subagent 的工具，Harness 立即返回一个 resultType: "task" 的高熵 taskId 句柄。子代理在后台跑几分钟甚至半小时，协调者按 pollIntervalMs 轮询进度或通过 subscriptions/listen 接收 notifications/tasks；子代理中途卡在需要人工审批或信息补全时，状态自然切到 input_required，经 tasks/update 拿到输入后继续跑；任务超时或不再需要时，通过 tasks/cancel 协作取消。子代理崩了、协调者重启了，句柄都在，状态机清晰可追。
  2. 共享协作看板（Swarm Board）即强类型 Tools，多个并行工作的子代理需要共享中间发现、认领未分配子任务、避免重复踩同一个坑。Harness 直接暴露一组带 inputSchema 与 outputSchema 的看板工具（例如 board.post_finding、board.claim_work、board.list_open_items），配合显式 board_id 句柄（遵循 SEP-2567），子代理甚至可以用 Code Mode 在沙箱里一次性拉取并过滤整个看板的未认领项，再写回结构化结论。
  3. 跨代理唤醒即 MCP Events（io.modelcontextprotocol/events），协调者或同伴代理不必傻傻地开一堆高频定时器空转。Harness 暴露 task.completed、board.finding_posted、review.requested 等标准事件类型；当某个子代理把测试跑绿、或者在看板上贴出一条阻断级缺陷时，Harness 通过 Push（本机/同集群）或 Webhook（跨团队/跨云常驻）瞬间唤醒协调者或负责修复的同伴代理，并且天然自带 cursor 断点续传与 eventId 去重。

这种设计最实在的工程红利，是复用既有鉴权、网关与工具链。给一个跨部门协作代理划定权限，直接用第 6 章的 OAuth 2.1 Scope 和企业 IdP ID-JAG 策略管控（比如只允许外部伙伴代理认领特定队列的任务、只读某块看板）；监控和限流直接复用第 2 章的标准 Mcp-Method/Mcp-Name HTTP 网关；连给新同事解释怎么把新子代理接进来，都可以直接用第 8 章的 Skills over MCP 下发协作 Playbook。

必须避开的架构反模式：别把 SaaS 包成单个 ask_agent 工具#

看到这里，有些 SaaS 团队可能会动一个极具诱惑力的念头：既然 Harness 可以做成 MCP Server，干脆把整个 CRM、工单系统或数据库平台也藏在一个自带内部小模型的 ask_crm_agent(prompt: string) 单一端点后面，省得设计那么多精细工具。

Philipp Schmid 在文章最后一段直接给这种做法判了死刑：好的 MCP Server 是面向 Agent 暴露工具，而不是把 Agent 伪装成工具（Good MCP servers expose tools for agents, not agents as tools）。

把整个常规 SaaS 产品包成一个单一的 ask_agent 端点，在实际工程里会立刻踩中四颗大雷：

  1. 严重的上下文饥饿（Context Starvation），用户手里的主 Agent 掌握着完整的对话历史、本机代码仓库、Slack 讨论、Sentry 报错和另一台业务系统的数据；而被关在黑盒里的 ask_crm_agent 只能看到主 Agent 临时塞进 prompt 参数的那两句话。它既不知道用户真正的约束，也没法参考其他系统的数据，只能盲人摸象般给出泛泛回答。
  2. 彻底废掉 Code Mode 与跨系统组合能力，单一自然语言接口没有精细的 outputSchema，主 Agent 无法在沙箱里把 CRM 客户列表和 Stripe 账单、Linear 工单做内存 Join，只能退回低效的自然语言传话游戏，每传一次就多一层信息衰减和幻觉放大。
  3. 双层模型推理叠高延迟、成本和不可控性，主模型花一轮组织提问，黑盒里的次级模型再花五轮调内部 API 并润色成散文，主模型再花一轮把散文读懂并提取字段，端到端延迟翻倍，出错时几乎无法定位到底是主模型没问清，还是黑盒代理自己编错了。
  4. 破坏统一的审计与最小权限边界，原本清晰可审计的 list_customers（只读）和 refund_invoice（破坏性写操作，需人工确认）全部被揉进了同一个 ask_agent 字符串入口里，宿主和企业网关根本无法在调用前分辨这次自然语言提问背后到底会触发只读查询还是删库改单。

把这两种模式什么时候该用、什么时候绝不能用，压成一张选型判断表：

场景特征 推荐架构形态 典型例子

先看 StatelessMcpServer 中对 x-mcp-header 和 SEP-1303 参数校验的处理逻辑。当请求体进入 tools/call 时，服务端先核验所有标注了 x-mcp-header 的自定义请求头是否与请求体里的实际参数一致（防代理网关与后端解析分裂），不符直接回 HTTP 400 和 -32020；只有通过传输层校验后，才做业务参数完整性校验，一旦缺少必填字段，不再抛 -32602 协议错误，而是返回 HTTP 200 加上 isError: true 的工具执行错误，把缺失字段名清晰地交还给模型自纠错：

# Validate x-mcp-header mirrored parameters (SEP-2243)
for arg_name, hdr_suffix in spec.x_mcp_headers.items():
    hdr_key = f"mcp-param-{hdr_suffix.lower()}"
    if arg_name in arguments and arguments[arg_name] is not None:
        if hdr_key not in norm_headers:
            err = McpProtocolError(400, ERR_HEADER_MISMATCH, f"Missing header Mcp-Param-{hdr_suffix}")
            return err.http_status, err.to_jsonrpc(req_id)
        decoded = decode_mcp_header_value(norm_headers[hdr_key])
        if decoded != expected_str:
            err = McpProtocolError(400, ERR_HEADER_MISMATCH, f"Mcp-Param-{hdr_suffix} mismatch")
            return err.http_status, err.to_jsonrpc(req_id)

# Validate required input arguments per SEP-1303 (tool execution error isError=True)

核心术语对照#

  • Streamable HTTP：MCP 的标准远程 HTTP 传输绑定，单一路径接收 POST，按单次请求选择返回普通 JSON 或绑定到该请求的 SSE 响应流。
  • MRTR（Multi Round-Trip Requests）：多往返请求模式。服务端通过返回 resultType: "input_required" 和不透明 requestState 暂停请求并索要输入，客户端收集完后换新 JSON-RPC id 重试，无需粘性会话。
  • Code Mode：由 Agent 宿主提供无原始凭证隔离沙箱，依据 MCP inputSchema 与 outputSchema 生成类型化函数桩，让模型一次编写脚本在沙箱内存里并发调用、过滤与 Join 多台服务器数据。
  • CIMD（Client ID Metadata Documents）：以客户端自托管的 HTTPS 元数据 URL 直接作为 client_id 的 OAuth 注册方式，取代已弃用的 RFC 7591 动态客户端注册。
  • ID-JAG（Identity Assertion JWT Authorization Grant）：企业托管授权扩展中，客户端拿企业 SSO 身份断言向企业 IdP 通过 RFC 8693 换取的授权断言，再通过 JWT Bearer Grant 换取目标 MCP Server 的访问令牌。
  • Explicit State Handles（显式状态句柄）：无会话架构下由创建类工具返回、由模型在后续工具参数中显式传递的不透明资源标识（如 basket_id）。
