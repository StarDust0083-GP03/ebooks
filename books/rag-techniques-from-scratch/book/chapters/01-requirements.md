# 需求篇：先框住哪些问题必须答对

动手选向量库之前，先拿一个具体请求把验收标准钉死：“支付回调验签和幂等如何处理？”如果系统只找回验签顺序，就漏掉了重复通知的去重规则；如果它把已废弃的 v1 文档排在前面，就会给出“先改订单状态再异步验签”这种完全相反的危险建议。检索接口返回两条高分片段，离满足这项业务需求还差得远。

## 三类使用者，五类边界请求

研发知识库主要服务三类角色：刚接手支付模块的新人想理清主流程，值班研发要快速核对异常条款和评审负责人，文档维护者则关心新发布的规范有没有立刻替换掉旧版。同一套检索后端要承接不同诉求，先把五类典型请求的底线列清楚：

| 请求类型 | 必须交付的内容 | 明确禁止的行为 |
| --- | --- | --- |
| 回调处理顺序 | 现行 v2 规范的完整前置条件 | 引用已废弃的 v1 规则 |
| 重复通知如何处理 | 幂等键构成与重复事件处理策略 | 把验签等同于幂等 |
| 回调模块找谁评审 | 模块归属记录加上对应团队负责人 | 仅凭相似人名猜测 |
| 某一笔退款到账了吗 | 明确告知需查询实时业务系统 | 用规范文档臆断单笔交易状态 |
| 查看同事私人排查笔记 | 按服务端认证身份严格隔离 | 被换问法或提示注入套出他人笔记 |

第一版只承诺把现行规范的证据找全、找准，并附上可核对出处。跨文档查负责人这类两跳题先留作评估里的挑战样本，等数据证明现有链路答不上来再考虑二次检索或图谱，不为了演示炫技一上来就搭图数据库。实时交易查询、历史时点回溯、自动执行退款和全库聚合统计全部排除在第一版范围外。

## 响应结构要先区分状态

很多问答接口失败时只会统一回复一句“未找到相关资料”。用户分不清究竟是知识库里确实没写、权限不够、还是下游向量库超时了。先把响应协议拆清楚，前端展示和离线评估才能各司其职：

```json
{
  "request_id": "demo-001",
  "status": "evidence_ready",
  "answer": null,
  "citations": ["callback-v2:0", "callback-v2:1"],
  "index_version": "teaching-v1"
}
```

这里有三个核心状态必须分开：`evidence_ready` 表示授权、召回和预算打包均已完成，证据包可以交给生成器或直接展示，但本身不保证最终自然语言回答无误；`insufficient_evidence` 表示在当前用户可见范围内确实没找到足够证据，应触发拒答或人工接管；`dependency_failed` 表示检索服务、重排器或上游模型异常，运维需要告警，不能伪装成“公司没有这条规范”。

每一条引用至少要落到文档标识、版本号和片段位置。界面上如果只在回答末尾挂一长串文档标题，审阅者根本没法核对哪句话出自哪一段，也发现不了模型拿验签段落去强行佐证幂等结论的错配。

## 文档更新与删除也是功能需求

支付规范从 v1 升到 v2 后，日常查询默认只能看到 v2。旧版可以留作审计归档，但绝不能因为措辞更贴近用户的老问法就混进当前回答。同样，一旦某位同事删掉自己的私人排查笔记，原文不可读还不够，基于它生成的向量、问题代理、章节摘要和问答缓存都必须同步失效。

在配套代码里，我们用 `active` 布尔字段表示当前生效视图，用 `scope` 字段区分公共文档与个人笔记。命令行参数 `--user` 只在离线实验里充当身份替身；放到真实服务端时，用户身份和租户必须来自可信会话或令牌校验，绝不能相信客户端在请求体里自己声明的用户名。

## 怎么写可验证的验收条件

“回答准确率达到 95%”这类指标缺乏题集、判定规则和样本口径，落到工程上基本没法测。更稳妥的做法是先把需求写成固定题集和必要证据清单。

以回调综合题为例，它的标准答案集合包含 `callback-v2:0` 和 `callback-v2:1` 两条片段。哪怕检索器把第一条排到榜首、拿满 MRR 1.0，只要第二条没进最终上下文，这道题在完整性指标上依然记为失败。除正常有答案题外，验收集还必须固定保留三类专项样本：无答案拒答题、废弃版本干扰题和跨用户越权题。面对这三类样本，干净利落地少答甚至不答，比强行凑满 top-k 更有价值。

## 为什么第一版先不上 Agent

第一版的高频问题几乎都能在“一次授权检索 + 一次证据打包”里收口。过早引入自主规划 Agent，会额外多出工具误选、多轮循环、费用翻倍和难以复现的轨迹波动。先把每一步写成输入输出明确的函数，保留候选 ID 与注入 ID 日志；等评估集里的真实失败案例证明单轮检索解不了“查模块再查负责人”，再按受控状态机逐步放开第二轮检索。
