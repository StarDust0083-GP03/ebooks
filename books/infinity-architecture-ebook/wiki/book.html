前言：为什么一台树莓派能装下七万五千个 Agent

线上跑过长周期 Coding Agent 或运维 Agent 的人，大概率撞过同一堵墙：模型只花了三秒钟决定触发一次 CI 构建，或者发出一条等待人工审批的工单，接下来的二十分钟甚至三天里，整个 Agent 进程却只能挂在那里干等。stdio 管道不能关，HTTP 会话不能断，协程栈和内存上下文不能放，扔进 AWS Lambda 还会撞上十五分钟执行上限。把并发量拉到几百个，内存和闲置算力账单立刻失控；如果再让多个子 Agent 同时改同一个代码仓库，工作目录里很快就会出现互相覆盖的脏文件。

UC Berkeley Hydro 团队开源的 hydro-project/infinity 从头拆解了这套阻塞假设。它把异步运行时的思想搬进了 Agent 系统：单次执行切片（slice）绝不阻塞在外部工具上。模型一旦吐出异步工具调用，运行时先把这一轮对话刷进持久化存储，发出一次即发即忘（fire-and-forget）的 HTTP POST，随后立刻退出当前切片。两轮之间，一个等待中的 Agent 在系统里只剩几行历史记录，没有驻留任务，没有调用栈，也没有打开的网络连接。等几分钟或几天后工具把结果推回回调地址，运行时再按线程 ID 重新加载历史、继续推理。

沿着这条主线，infinity 在同一个 Rust 工作区里搭出了三层互相咬合的工程组件：

  • Infinity Runtime（infinity-agent-core 与 infinity-agent-lambda），负责切片执行、三阶段历史缓冲、去重、线程树、位置索引压缩，以及同一套核心逻辑在本地常驻进程与 AWS Lambda 无服务器环境之间的复用。
  • Reactive Agent Protocol（RAP）（rap-protocol、rap-client、infinity-rap-bridge 与 infinity-mcp-bridge），用无状态 HTTP 触发加异步回调取代长连接会话，原生支持长耗时工具、事件订阅、OAuth 授权、人工确认弹窗、前端视图更新与跨机迁移，同时通过桥接层兼容现有 MCP 服务。
  • Infinity Code 与堆叠沙箱（infinity-daemon、infinity-agent-cli、sandbox-core、sandbox-local、sandbox-remote），面向本地与远程机器的并发编码代理。每个线程拿到独立的 Jujutsu 工作区或 Git worktree，并通过 macOS sandbox-exec 或 Linux Bubblewrap 限制写权限，并行干活后再把子沙箱压缩合回父书签，宿主工作目录始终保持干净。

阻塞式 Agent 的死结与无阻塞切片不变量

让一个编码 Agent 在真实仓库里跑 cargo test --workspace，或者让运维 Agent 等一个 GitHub PR 通过人工审批，传统同步循环很快会露馅。模型在第 1 秒吐出一条工具调用，工具需要跑二十分钟，MCP 的 stdio 管道或 HTTP SSE 会话就必须一直开着，调用栈上的异步任务、内存里的整段对话历史和宿主进程谁都不能退。把这套模式搬到多 Agent 并行场景，问题会成倍放大：一百个等待 Webhook 的 Agent 占着一百份常驻内存和一百条长连接；放到 AWS Lambda 这类按毫秒计费、单次调用最多十五分钟的无服务器平台上，等待本身就直接变成超时故障和纯浪费账单。

为什么传统 Agent 架构卡在等待上#

常规 Agent 框架把一轮多步任务写成一条长循环：while !done { call_llm(); await call_tool(); }。这种写法把两件性质截然不同的事情绑死在同一个操作系统进程生命周期里。

大模型推理和本地状态更新属于短时、有界的计算，通常几秒到几十秒结束。而外部世界里的工具耗时完全无界：跑完一轮集成测试可能要二十分钟，等一位同事在 Slack 里点下确认按钮可能要两小时，订阅一个仓库的 PR 动态更是按周甚至按月计算。一旦运行时在 await call_tool() 上挂住，进程亲和性就被锁死了。结果回包必须回到原来那台机器、原来的那个进程、原来的那条管道；机器重启或容器回收，这轮任务就断了线。

上面这张图对比了两种执行模型的分叉点。上半部分是传统阻塞循环，进程在二十分钟等待期里全程在线；下半部分是 Infinity 的解法，把长循环切碎成一个个彼此独立、绝不等待外部 I/O 的执行切片（slice）。

一条核心不变量：切片绝不阻塞#

阅读 docs/docs/infinity-runtime/architecture.md 和 crates/infinity-agent-core/src/system/thread.rs，整个 Infinity 运行时的设计都围绕同一条约束展开：单个执行切片绝不阻塞在任何外部操作上。

这条约束逼出了四个连环设计决策：

  1. 万物皆消息（Everything is a message），crates/infinity-agent-core/src/message.rs 里只定义了一种入口信封 InputMessage。用户输入、异步工具结果、外部订阅事件、子线程回报、OAuth 跳转请求、人工选择弹窗、上下文压缩指令以及定时器唤醒，全都包装成 InputMessage 投进输入队列，通过 group_id: ThreadId 路由到对应线程。进程里不存在一个记录着正在等工具 X 或睡到早上九点的内存状态机。
  2. 先落盘、再派发、立刻让出，当模型决定调用异步工具时，切片先执行 HistoryManager::sync() 把本轮对话与工具调用写入持久化存储，然后向工具服务器发出一次无状态的 HTTP POST（携带 callback_url），只要对方回一个 2xx 确认收到，当前切片立刻结束。本地常驻驱动退出当前任务，Lambda 函数直接结束进程。
  3. 跨线程并发靠队列分组，不靠分布式锁，同一个线程的两次切片不能并发读写同一份历史，否则消息顺序会乱；不同线程之间没有共享可变状态，应该彻底并行。Infinity 没有在运行时里手写分布式锁，而是把串行约束直接交给队列层：AWS 侧用 SQS FIFO 的 MessageGroupId 绑定 group_id，本地侧用 route_loop 为每个活跃 ThreadId 维护单条 mpsc 通道。
  4. 重投递安全靠持久化去重与尾扫，队列只能保证至少一次投递（at-least-once），因此每个切片必须幂等。用户输入与订阅事件在 StateStore 中记录已处理 ID；工具结果则直接逆向扫描历史尾部匹配待应答调用，重复送达自动丢弃。
维度 传统阻塞式 Agent（如直连 MCP） Infinity 无阻塞切片运行时
工具等待期资源占用 进程、任务栈、连接与内存历史全程常驻 仅持久化存储中的历史行，无任务、无栈、无连接
进程亲和性 强绑定原进程与 stdio/SSE 通道 无亲和性，任意进程按 ThreadId 重载历史继续

七万五千个 Agent 放进树莓派是怎么测出来的#

README 开篇提到 Infinity 轻到能在一台树莓派内存里装下 75,000 个 Agent。这句宣传语背后对应的真实代码是 crates/infinity-agent-core/examples/agent_scale.rs，以及文档里嵌的实测数据 docs/src/components/MemoryChart.tsx。

拆开 agent_scale.rs 看测量口径很清楚：基准程序在一个单线程 tokio::task::LocalSet 上启动 LocalAgentSystem，使用内存版 InMemoryConversationStore 和 InMemoryStateStore，配合一个进程内脚本化模型 ScriptedModel 和异步回环工具 RunCommand。每个 Agent 真实走完 20 轮完整切片链路，每轮包含两次模型流式补全（每次 12 块、共约 1.2 KB 文本）加一次异步工具经队列回传。每跑完一波（WAVE=4000），程序等待所有线程驱动退出进入空闲态，排空生命周期通道，调用 Linux 的 libc::malloc_trim(0) 把分配器缓存还给内核，再读取 /proc/self/status 里的 VmRSS。

上游在 AMD EPYC 9R14 上跑 AGENTS=80000 TURNS=20 WAVE=4000 的记录如下：

  • 0 个 Agent 基准 RSS：5,304,320 字节（约 5.3 MB）。
  • 40,000 个空闲 Agent：4,348,772,352 字节（约 4.35 GB）。
  • 80,000 个空闲 Agent：8,406,446,080 字节（约 8.41 GB）。
  • 线性斜率折算：约 102 KiB / Agent。

按这个斜率外推，8 GB 内存的树莓派确实能装下约 75,000 个各带 20 轮对话历史的空闲 Agent。不过必须把口径看清：这 102 KiB 几乎全是 20 轮历史字符串本身在 InMemoryConversationStore 里的存储体积，之所以没有额外膨胀，是因为本地路由器 route_loop 直接把每个线程驱动放进 FuturesUnordered，线程一旦空闲就立刻退出并释放整个 drive_thread future 与 HistoryManager 缓存。如果换成真正驻留的大内存工具进程，或者成千上万个线程同时处于模型流式推理中，峰值内存会取决于同时活跃的切片数，而不是总注册 Agent 数。

同步工具的例外：为什么要允许切片内回环#

并非所有工具都适合发出去然后结束切片。以内置的 spawn_thread 为例，它在 ConversationStore 里写几条元数据、往队列丢一条子线程启动消息，几微秒就能完成。如果让它也走异步让出，不仅白白多出一次存储重载和切片调度，还会引出一个隐蔽竞态：父线程刚派发 spawn_thread 就退出了切片，紧接着一条无关的并发事件抢在 spawn_thread 的结果之前抵达父线程，父线程就会以为 spawn_thread 被中断了，可实际上子线程早就已经启动并在后台跑起来了。

因此 Tool trait 在 crates/infinity-agent-core/src/tools/mod.rs 里特意留了 supports_sync() 和 execute_synchronous() 两个钩子。当 run_completion 在流里碰到同步工具调用，或者碰到模型幻觉出来的未知工具名时，运行时不会结束切片，而是当场内联执行（或注入错误结果），把结果塞回当前内存历史，在同一个切片里直接发起下一轮模型推理。只有真正跨进程或跨网络的异步工具才会触发落盘屏障与切片让出。

这种切分把状态变更极快、怕竞态的元操作留在切片内部当场完成，把一切耗时不可控的外部调用隔离在队列边界之外。

02

21 个 Crate 的分层版图与类型化 ID 体系

打开一个近六万行 Rust 代码的多 crate 仓库，最容易迷失在交叉依赖里：本地守护进程、AWS Lambda、CLI 终端、Slack 机器人、MCP 桥接和 Jujutsu 沙箱全挤在同一个 Cargo.toml 下面，它们之间到底谁依赖谁，共享了哪些契约，又在哪里画出了硬隔离边界？

把 crates/ 目录下的 21 个成员按依赖方向自顶向下摊开，整座系统其实只有五层，而且上下层之间的耦合压得很低。

五层 Crate 拓扑与各自职责#

最底层是线缆协议与模型供应层，包含 5 个 crate，定义了跨进程和跨网络的稳定数据结构，不依赖核心状态机。rap-protocol（392 行）只放 RAP 协议消息、基础类型化 ID 和 CallbackClient trait；infinity-protocol（613 行）定义客户端和守护进程之间的 ClientMessage/DaemonMessage 以及 ThreadRef；infinity-provider-protocol（1,280 行）抽离出 ModelProvider trait、StreamChunk、ErrorClass 和 Unix Socket 跨进程协议，让 infinity-provider-bedrock（1,445 行）与 infinity-provider-rig（504 行）既可以直接链接进进程，也可以作为独立子进程被守护进程托管。

往上一层是堆叠沙箱子系统，由 3 个 crate 组成。sandbox-core（3,902 行）实现了整套 Axum HTTP RAP 沙箱服务、SandboxBackend 与 ModeProvider 两个核心 trait、流式命令执行以及 git bundle 迁移导入导出；sandbox-local（4,911 行，含大量集成测试）在其上实现本地 jj/git 工作区管理和 macOS sandbox-exec / Linux bwrap 写隔离；sandbox-remote（534 行）则实现面向 AWS Lambda 的 EFS 裸仓镜像后端。

第三层是工具桥接与标准 RAP 服务层，包含 6 个 crate。rap-client（515 行）封装 HTTP 客户端、工具清单加载缓存、本地回调监听和 RapNotifier 生命周期通知；infinity-rap-bridge（704 行）提供守护进程与 AWS rap-receiver 共用的 prepare_callback 转换器，避免本地和云端在回调解析上漂移；infinity-mcp-bridge（797 行）负责把 Stdio 和 Streamable HTTP 两类 MCP 服务适配成 Infinity 工具；rap-steering-server（348 行）与 rap-github-event-poller（715 行）是两个开箱即用的真实 RAP 服务；rap-test-servers（246 行）供集成测试使用。

第四层是整座仓库的心脏，核心切片运行时。infinity-agent-core 独占 15,372 行代码（占全仓四分之一以上），内部包含 event_processor.rs（切片三阶段逻辑与 HistoryManager，单文件 5,209 行含测试）、system/（AgentSystemBuilder、Thread、本地单线程路由器与驱动、DeferQueue）、tools/（spawn_thread、report_to_parent、close_thread、send_message_to_child、cancel_subscription、sleep 家族与 RapTool）和 stores.rs（内存版默认存储）。旁边的 infinity-mdtests（100 行）负责把 docs/docs/infinity-runtime/**/*.md 里的 44 段代码示例自动编进 Rust 测试，确保文档示例不会和主干 API 脱节。

最顶层是交互前端与部署外壳，共 5 个 Rust crate 外加 3 个 TypeScript 目录。infinity-daemon（9,215 行）是本地常驻守护进程，把 infinity-agent-core、本地 JSON 持久化、SSH 远程代理、热迁移编排和 WebSocket 前端打包在一起；infinity-agent-cli（10,294 行）实现内联终端 TUI、无头命令和 infinity acp 编辑器协议服务；infinity-agent-lambda（1,894 行）提供云端 SQS 消费 Lambda 与 rap-receiver Function URL 两个二进制入口；infinity-slack-bot（2,371 行）与 infinity-slack-dataflow（1,817 行）把守护进程接到 Slack，其中后者直接用 Hydro 团队自研的 hydro_lang 编写分阶段数据流。仓库根目录下的 agent/（AWS CDK）、infinity-ui/（共享 React 组件）和 infinity-web/（Vite 桌面端）则补齐了云端基础设施和图形界面。

工作区纪律：把 Bug 拦在编译期#

翻看根目录 Cargo.toml 里的 [workspace.lints] 和 AGENTS.md，能看出团队对运行时健壮性的几条硬规矩。workspace clippy 显式开启了 unwrap_used = "warn"、unused_async = "warn"、allow_attributes_without_reason = "warn"，以及 missing_unsafe_on_extern = "deny"。AGENTS.md 要求代码中不得悄悄吞掉 Result::Err，需要断言不变量时必须写 .expect("bug: ...")，把逻辑缺陷和外部运行时错误清楚分开。这些规矩和下面要讲的强类型 ID 体系一脉相承。

为什么花四个阶段消灭裸 String ID#

在多租户、多线程、多主机代理的 Agent 运行时里，字符串 ID 串台是一类极其隐蔽的故障：把父线程 ID 传进需要 tool_call_id 的存储接口，或者把带远程前缀的 "devbox/uuid" 直接当成本地 ThreadId 去查文件，编译器不会报任何错，直到线上热迁移或回调匹配时才静默丢消息。

从变更记录 0.2.0（PR #115 与 #116）和源码可以看到，Hydro 团队分四阶段完成了从裸 String 到 strkind 强类型 ID 的全仓迁移，同时把 JSON 线缆格式保持为透明字符串（零序列化开销）。

// crates/rap-protocol/src/lib.rs
strkind::strkind! {
    pub ThreadId;
    pub ToolCallId;
    pub ProviderCallId;
}

pub type ChoiceId<T = String> = ToolCallId<T>;

rap-protocol 定义了最基础的四个标识：

类型 线缆字段名 来源与含义
ThreadId group_id 会话线程标识。本地守护进程生成 UUID，Lambda 侧由调用方指定并复用为 SQS FIFO MessageGroupId
ToolCallId id 单次工具调用标识，由模型供应器生成（如 Bedrock 的 tooluse_...）或运行时为合成事件生成 UUID
ProviderCallId call_id 部分模型供应器附带的第二调用标识，工具回包时必须原样回显
ChoiceId id / choice_id 挂起人工选择项的标识，目前是 ToolCallId 的类型别名，因为选择弹窗绑定到发起它的工具调用

注意 ToolCallId 和 ProviderCallId 被刻意拆成两个不兼容类型。不同大模型 API 对工具调用 ID 的约定不一致（有的只用一个 ID，有的需要把 call_id 原样带回），过去用两个 String 参数传给 Tool::execute 极易传反，现在编译期就能拦住。转换只发生在最外层边界，比如与 rig-core 结构体对接或写入 DSQL/DynamoDB 字符串列时。

会话即根线程与 ThreadRef#

在守护进程和客户端协议层（crates/infinity-protocol/src/lib.rs），团队做了另一项很干净的概念收敛：取消独立的 session_id，承认一个会话就是它的根线程（root_thread_id）。

过去协议里同时存在 session_id 和 thread_id，连 SwitchModel 里原本针对单线程的字段都被误标成了 session_id，而远程会话又靠手工拼接和 split_once('/') 在字符串 "devbox/uuid" 上做手术。引入 RemoteName 和 ThreadRef 后，这套字符串手术全部被替换成类型方法：

// crates/infinity-protocol/src/lib.rs
#[derive(Debug, Clone, PartialEq, Eq, Hash, PartialOrd, Ord)]
pub struct ThreadRef {
    pub remote: Option<RemoteName>,
    pub id: ThreadId,
}

ThreadRef 在几个细节上考虑得很周全：

  • 线缆兼容：Serialize 与 Deserialize 仍然走 "{remote}/{id}"（远程）或 "{id}"（本地）的复合字符串形式，前端 TypeScript 照旧按普通字符串收发；解析器 FromStr 会显式拒绝空远程名、空 ID 以及包含两个及以上 / 的非法串。
  • 边界分离：面向客户端的 ClientMessage（如 Connect、UserInput、SwitchModel、RequestMigrate）一律使用 ThreadRef，明确表达目标所在主机；而守护进程之间点对点通信的迁移指令（Emigrate、EmigrateDone、ImportSession）使用纯 ThreadId，因为已经落在目标主机本地。
  • 代理改写与排序：ThreadRef::prefixed(&remote) 和 ThreadRef::strip(&remote) 替代了原本分散在 client_handler.rs 和 migrate.rs 里的字符串拆拼；派生 Ord 遵循 (remote, id)，让 None（本地线程）天然排在所有 Some(remote) 之前，不会像字典序字符串那样把本地 UUID 和远程主机名混插在一起。

把 21 个 crate 的分层边界和这套强类型 ID 记在心里，接下来就能直接钻进 infinity-agent-core，拆解一次执行切片内部最核心的三阶段状态机。

03

切片执行循环与三阶段 HistoryManager

试想一个线上常见的死锁事故：用户随手往对话框里粘贴了一段 80 万字的日志，或者某个 grep 工具一不小心扫出几十兆构建产物。传统 Agent 框架收到消息后，顺手把这条输入追加进了持久化对话表，再打包发给大模型。模型立刻返回上下文超窗报错；用户重试或者刷新页面重新加载会话，运行时又把刚才那条已经落盘的巨型消息原封不动地读出来发给模型，模型继续报错。一条超长输入，就能把整条会话线程永久卡死在毒消息（poison message）上。

再想另一个并发故障：模型决定调用一个修改数据库的远程工具，运行时先发了 HTTP 请求，再去把这次工具调用写进数据库。如果恰好在发出 HTTP 之后、落盘完成之前进程崩了，或者对方工具回包极快（比如 5 毫秒内就把回调推回了队列），下一轮切片在历史表里根本找不到对应的 ToolCall，只能把真实的执行结果当成幽灵消息丢弃。

crates/infinity-agent-core/src/event_processor.rs 用一套严谨的三阶段 HistoryManager 和落盘屏障，把这两类问题一起挡在了核心层。

一次切片的三段流水线#

任何平台宿主（无论是本地常驻驱动还是 AWS Lambda 的单次调用）驱动一次切片，底层组合的都是 event_processor 暴露的三个函数：prepare_input、run_completion 与 execute_action。在 crates/infinity-agent-core/src/system/thread.rs 的 Thread::step_no_defer 里，它们的执行顺序是写死的：

  1. 准备阶段（prepare_input）：逐条吸收本批次的 InputMessage。过滤已关闭线程，拦截重复投递，处理压缩触发与压缩完成消息，分流订阅事件，把 OAuth 与 UserChoice 直接返回给上层前端，只把真正需要模型响应的新内容塞进 HistoryManager。如果整批消息没有任何一条返回 PrepareResult::Ready，本轮直接跳过模型调用，零成本结束切片。
  2. 补全阶段（run_completion）：把内存历史和工具定义发给 ModelProvider，以流的形式接收文本、推理块和工具调用。遇到同步工具（如 spawn_thread）或未知工具名，在当前循环内直接执行并把结果注回历史，继续发起下一次补全；遇到异步工具调用或普通结束信号，产出终端动作 CompletionAction 后跳出流。
  3. 落盘屏障与派发阶段（sync() -> execute_action）：先调用 self.history.sync().await? 把本轮所有已知安全的消息持久化，确认落盘成功之后，才调用 execute_action_with_error_result 向外部 RAP 服务发出 HTTP POST。

这里有一条不能违背的铁律：sync() 必须在 execute_action 之前完成。哪怕进程在派发瞬间崩溃，持久化存储里也已经记下了那条待应答的 ToolCall；而如果派发本身因为网络错误失败，execute_action_with_error_result 会立即把一条错误 ToolResult 塞回输入队列，让模型在下一轮感知失败并自行恢复，而不会永远干等一个永远不会来的回调。

三阶段未落盘状态与轮次缓冲#

为了解决开头提到的毒消息卡死和流式中断脏写问题，HistoryManager 在已持久化的 ConversationStore 之上，把内存里尚未落盘的内容拆成了三层（对应 event_processor.rs 第 150 至 174 行的注释与字段）：

第一层是 unvalidated_items。所有刚通过 handle_content 进入内存的新输入（用户文本、工具结果、内联合成事件）都先躺在这里。它们已经加入内存的 history 向量，所以紧接着发起的模型请求能看到它们；但 sync() 会刻意跳过这批项，一字节都不往存储里写。原因很直接：模型还没见过它们，谁也不知道里面有没有一条会撑爆上下文窗口的毒消息。

第二层是 pending_items（已知安全队列）。只要模型针对这次请求流式吐出了任意有效输出，就证明整个输入上下文没有超窗，运行时立刻调用 mark_inputs_model_validated()，把 unvalidated_items 整体晋升到 pending_items。模型自己产出的内容则在轮次提交时通过 append_known_safe 直接进入 pending_items。append_known_safe 内部有一条硬断言：如果此时 unvalidated_items 非空直接 panic，从代码逻辑上杜绝先持久化模型回答、漏掉对应输入的乱序可能。

第三层是 turn_buffer（流式轮次缓冲）。模型流式吐出的每个 StreamChunk 都先攒在这里，不污染 history。handle_completion 还会通过 try_merge_buffer_text 把连续的 StreamChunk::Text 片段合并成单条助手消息，避免把一句话按 token 切成几百行写进数据库把磁盘撑爆。流式过程若中途断连需要重试，调用 discard_turn() 一键清空 turn_buffer，下一轮重试直接从干净的已提交历史重建请求；流式正常结束时，调用 flush_turn() 或 flush_turn_trimming_reasoning()（剔除末尾孤立的推理块与空白文本，确保已提交历史不以半截 thinking 结尾）把内容刷进 history 和 pending_items。

这套分层顺带给前端重放提供了很大便利：current_turn_view() 把 history 和 turn_buffer 拼起来返回，于是用户在模型输出到一半时新开一个浏览器标签页附着上来，也能通过 ReplaySnapshot 立刻看到正在生成的那半段回复。

上下文溢出恢复：精确止损，绝不静默丢掉用户的原话#

当模型供应器明确回报 ErrorClass::ContextOverflow 时，三阶段设计的价值就全体现出来了。因为引发溢出的新输入还留在 unvalidated_items 里，根本没进数据库，recover_from_overflow（event_processor.rs 第 1444 行）可以按两种情况精准处理：

  • 单一可替换元凶：如果 unvalidated_items 里恰好只有 1 条记录，且它是工具结果或订阅事件，那超窗的罪魁祸首毫无歧义。运行时调用 replace_unvalidated_tool_results 把它的正文替换成固定占位符 TOOL_RESULT_TOO_LARGE_PLACEHOLDER（"[tool result omitted: it was too large for the model's remaining context window]"），清除附带的 display_segments，然后立刻重试补全。替换函数会跳过正文已经等于占位符的条目，因此万一换完占位符仍然超窗，第二次不会陷入死循环，而是自动落入下面的丢弃分支。
  • 含用户输入或多条混合：只要 unvalidated_items 里混进了用户文本，或者同时有多条输入无法判断谁超了限，或者重试后再次溢出，运行时把其中的可替换工具结果统一结算为 TOOL_CALL_INTERRUPTED_TEXT（"Tool call interrupted by user"），调用 drop_unvalidated_user_inputs 把未验证的用户输入从内存历史末尾截掉并从 processed_message_ids 中移除其去重 ID，然后直接终止本轮并向上报错，绝不静默重试。

源码注释把这里两个很细的判断写透了：第一，如果删掉了用户的原话还悄悄拿旧历史再跑一轮推理，模型会按过时指令乱动作，所以丢弃用户输入后必须停下来等用户重新发话；第二，此时被一起结算的挂起工具结果不能填成结果过大的提示，否则模型下一轮可能会误以为应该重新跑一遍工具，填成和用户打断一致的 "Tool call interrupted by user" 才准确。同时，因为被丢弃的用户输入在 StateStore 里从未落盘，且内存里的去重 ID 也被遗忘，这条线程在下一条正常消息到来时立刻恢复健康，彻底告别毒消息锁死。

双重去重策略：谁该写去重表，谁靠尾扫就行#

在至少一次投递的队列上，消息重投是常态。如果把每一条工具结果、每一条助手回复的 ID 全塞进 StateStore 的去重集合，长会话的状态记录会越滚越大。

HistoryManager::sync()（第 649 至 669 行）做了一次非常克制的拆分：只有天然不幂等的输入才会把 message_id 持久化到 StateStore，也就是 InfinityMessage::User 和 InfinityMessage::SubscriptionEvent。订阅事件如果不记 ID，重投一次就会再生成一条新的合成调用注入历史，造成重复响应。

而普通 ToolResult 完全不写持久化去重表。handle_content 收到工具结果时，调用 match_tool_result 从 history 末尾逆向扫描：

// crates/infinity-agent-core/src/event_processor.rs
fn match_tool_result(&self, result_id: &str) -> ToolResultMatch {
    for msg in self.history.borrow().iter().rev() {
        match msg {
            InfinityMessage::ToolCall { call, .. } => {
                if call.id == result_id {
                    return ToolResultMatch::Unanswered;
                }
            }
            InfinityMessage::ToolResult { result, .. } => {
                if result.id == result_id {
                    return ToolResultMatch::AlreadyAnswered;
                }
            }
            _ => return ToolResultMatch::NoPendingCall,
        }
    }
    ToolResultMatch::NoPendingCall
}

这个逆向扫描只跨越连续的 ToolCall 和 ToolResult（顺手兼容了未来并行多个工具调用形成 tc tc tr tr 尾部的场景）；一旦遇到任何用户文本、助手文本或订阅事件，说明碰到了上一轮边界，直接判定 NoPendingCall 丢弃过时回包。如果逆向先撞到同 ID 的 ToolResult，说明已经应答过，判定 AlreadyAnswered 跳过；先撞到同 ID 的 ToolCall，才判定 Unanswered 放行。

当非工具结果消息（如用户突然打断）到达，且历史最后一条正好是未应答的 ToolCall 时，interrupt_pending_tool_call 会往 interrupted_tool_calls 里登记该调用 ID，并自动补一条内容为 "Tool call interrupted by user" 的合成 ToolResult 保持对话结构合法，随后由上层 Thread::step_no_defer 通过 RapNotifier 尽力向工具服务器发取消通知。即便远端工具没来得及停下、过几分钟仍把真实结果推了回来，尾扫也会因为历史里已经跨过了新的轮次边界而干净利落地把它挡在门外。

04

响应式工具协议 RAP：断连回调、订阅与 MCP 桥接

用过 MCP（Model Context Protocol）写长耗时工具的工程师都遇到过同样的别扭事：MCP 天生是面向持久会话的请求响应协议，无论是本地 stdio 子进程管道，还是远程 Streamable HTTP 会话，Agent 运行时都得一直挂着连接等回包。查个天气、读个文件自然够用；一旦要触发二十分钟的编译测试、订阅某个 GitHub 仓库持续一周的 PR 事件，或者中途弹出人工审批等待两小时，连接一旦断开或容器被回收，上下文就全散了。于是每个团队只能各自在业务代码里拼凑轮询循环、Webhook 胶水和状态表。

Infinity 给出的解法是把工具协议本身翻转过来，定义了 RAP（Reactive Agent Protocol）。核心代码分散在 rap-protocol、rap-client、infinity-rap-bridge 和 infinity-mcp-bridge 四个 crate 中。

清单发现与即发即忘调用#

一个标准 RAP 服务本质上就是一个普通的无状态 HTTP 服务，它完全不知道调用方背后跑的是什么大模型，也不保存对话历史。

接入从工具清单发现开始。运行时向工具服务的 GET /.well-known/rap-toolset 发请求，拿到 ToolsetManifest（crates/rap-protocol/src/lib.rs 第 212 行）：

pub struct ToolsetManifest {
    pub name: String,
    pub description: Option<String>,
    pub endpoint: String,
    pub tools: Vec<ToolDef>,
    #[serde(default, rename = "needsMigration")]
    pub needs_migration: bool,
}

清单里有两个很有工程味的字段。一个是 needsMigration，布尔值，向守护进程声明这个工具服务在本地持有不可丢弃的外部状态（比如 sandbox-local 里的 Jujutsu 书签和工作区），跨主机热迁移会话时必须先通知它搬家。另一个在每条 ToolDef 上，叫 displayScript，允许工具作者附带一段简短的 Rhai 脚本。核心运行时里的 eval_display_script（crates/infinity-agent-core/src/tools/mod.rs 第 117 行）会把模型传入的参数灌进 args 变量里求值，生成人类易读的工具调用摘要（例如 sleep 工具自带脚本把秒数和原因拼成 "Sleeping 30s: wait for CI"），而不用在前端硬编码每种工具的渲染逻辑。

模型决定调用工具时，核心层经由 invoke_rap_tool（crates/infinity-agent-core/src/tools/rap_tool.rs 第 72 行）向清单里的 endpoint（通常是 /invoke）发一次 HTTP POST，正文是 RapInvocation：

  • operation 与 arguments，工具名与 JSON 参数。
  • id: ToolCallId 与 call_id: Option<ProviderCallId>，工具回包时原样带回。
  • group_id: ThreadId 与 thread_ancestors: Option<Vec<ThreadId>>，标明当前线程以及从根到父线程的完整祖先链（沙箱服务正是靠 thread_ancestors 继承父线程的写权限授权）。
  • callback_url，异步结果该往哪里投递。
  • user_id，可选用户身份。

错误处理策略在本地和云端完全一致：如果 HTTP POST 遇到网络层传输失败，invoke_rap_tool 返回 Err，由运行时兜底回注一条通用失败结果；如果服务端可达但返回了非 2xx 状态码，说明服务端拒绝了调用、绝不会有后续回调，函数直接合成一条包含操作名、URL 和状态码的错误 ToolResult 投回输入队列并返回 Ok(())，让模型马上知情并调整策略，绝不会把线程挂死在永久等待上。只要收到 2xx，调用立刻返回，切片结束，运行时可以安心休眠。

五类回调与统一转换入口#

几百毫秒或几天之后，工具干完活，把一个带 type 标签的 JSON 对象 RapCallback POST 到 callback_url。rap-protocol 定义了五种回调变体：

变体 (type) 携带核心字段 运行时处理去向
tool_result id, call_id, text 或多模态 content, display_as, subscription 转为 InputMessage 入队；若 subscription: true 则在 StateStore 登记活跃订阅
subscription_event tool_call_id, text, associative, final 默认派生隔离事件子线程；associative: true 时内联注入；final: true 清理订阅追踪
oauth id, call_id, auth_url 经 PrepareResult::OAuthRequired 透传给前端引导授权，不进模型历史
user_choice id: ChoiceId, prompt, choices, default, response_url 写入 StateStore 挂起列表并透传前端弹窗，用户选完后由客户端 POST 回 response_url
view_update group_id, view_type, content 旁路展示通道（如沙箱实时 Diff 视图），守护进程透传给 UI，Lambda 接收后直接返回 200 丢弃

注意 tool_result 里模型视角与人类视角的分离设计：模型看到的是 content（支持文本与 Base64 图像块 RapToolResultContent::Image；如果当前模型不支持图像输入，HistoryManager::get_history 会在发出请求前自动替换成 IMAGE_OMITTED_PLACEHOLDER）或纯 text；而人类在 TUI/Web 上看到的是 display_as 里的结构化 DisplaySegment（支持 Text、Diff、Image），build_display_segments 会把工具提供的美化片段排在前面、原始文本兜底挂在末尾。

为了防止本地守护进程和云端 AWS Lambda 在回调转换上出现行为漂移，所有平台都强制共用 crates/infinity-rap-bridge/src/callback.rs 里的 prepare_callback（底层调用 convert_callback）。守护进程的本地回调监听器和 infinity-agent-lambda 的 rap-receiver 二进制都只做网络收发，消息语义转换全收口在这一处。

生命周期通知：关闭、取消与迁移#

异步协议一旦放手让工具独立运行，就必须处理三件善后事：线程关了怎么回收外部资源，用户按 Ctrl+S 打断时怎么停掉正在跑的构建，会话搬家到另一台机器时怎么把外部状态一起搬走。

crates/rap-client/src/notifier.rs 的 RapNotifier 封装了这三条尽力而为（best-effort）的 HTTP POST 端点：

  • POST /close_thread，携带 { "thread_id": ... }，在 CloseThreadTool 关闭子线程后广播，比如通知 sandbox-local 执行 jj workspace forget 并删掉缓存目录。
  • POST /cancel_tool_call，携带 { "thread_id": ..., "tool_call_id": ... }，当用户文本打断挂起工具调用后触发，比如通知 sandbox-core 给正在运行的子进程组发 SIGTERM。
  • POST /migrate，携带 { "session_id": ..., "destination_url": ... }，由热迁移编排器定向发给声明了 needsMigration: true 的服务，触发状态打包传输。

前两条通知故意设计成 best-effort，即便某个外部工具服务已经离线或没实现该路由，也只记警告日志，不阻断线程关闭或用户打断。

仓库内置的两个真实 RAP 服务#

光看协议定义容易抽象，仓库里自带了两个很紧凑的参考实现：

  1. rap-steering-server（348 行），暴露两个操作：扫描项目根目录和家目录里的规则约定文件（INFINITY.md、CLAUDE.md、AGENTS.md、.cursorrules、.claude/skills 等目录）并按规范路径去重符号链接，以及带路径穿越校验的安全读取。
  2. rap-github-event-poller（715 行），展示了标准 RAP 订阅服务的写法。收到订阅调用后，它先登记 (owner/repo, tool_call_id, filters, callback_url) 并立即回传带 subscription: true 的 tool_result；后台轮询任务按仓库共享一个 ETag 和 GitHub 响应头里的 X-Poll-Interval（默认 60 秒），首次轮询只记录 last_seen_id 跳过历史旧事件，此后每出现匹配过滤条件的新事件就通过 send_subscription_event 推送回 Agent 的 callback_url。没有活跃订阅时后台轮询任务靠 tokio::sync::Notify 挂起零开销，线程关闭或取消订阅时移除条目。

兼容现有 MCP 工具：infinity-mcp-bridge 如何桥接#

协议再先进，如果不能直接复用现有的 MCP 服务器，落地成本也会太高。crates/infinity-mcp-bridge/src/lib.rs（797 行）在客户端侧做了一层干净的适配。

它定义了 McpTransport trait，并内置了两种传输实现：StdioMcpTransport 启动本地子进程（带 kill_on_drop(true) 防止孤儿进程），按换行分隔的 JSON-RPC 2.0 读写；HttpMcpTransport 对接 Streamable HTTP MCP 服务，自动处理 initialize + notifications/initialized 握手、维护 mcp-session-id 请求头，并能同时解析普通 JSON 响应与 text/event-stream SSE 响应。

顶层的 McpToolSet 通过 McpTransportFactory 延迟建立连接，把 MCP 服务器暴露出的每个工具包装成核心运行时认识的标准 Tool 实现。调用发生时，桥接层在后台任务里等待 JSON-RPC 返回，再把结果转换成 InputMessage 投回运行时输入队列。对于本地常驻模式，这意味着任何现有 MCP 工具零改动就能并入 Infinity 的并发线程与统一展示链路；而在无服务器 Lambda 模式下，仓库的 agent/ 目录则允许把 MCP 服务包在独立的远程代理层之后，对外呈现为标准无状态 RAP 端点。

协议层的收发机制清楚了，但还有一个关键问题悬着：当订阅事件不断涌入、或者父 Agent 一口气派生五个子 Agent 并行干活时，上下文不会乱套吗？下一章进入线程树与位置索引压缩。

05

线程树、上下文继承与位置索引压缩

让一个主 Agent 拆出三个子 Agent 并行审查三份代码文件，看起来只是多开几个异步循环。真跑到生产环境，立刻会冒出四类头疼的上下文事故：第一，子线程继承了父线程准备派生三个子线程的思考过程，刚启动就误以为自己是父线程，接着把同样的三个子线程又派生了一遍，引发指数级套娃；第二，父线程派完子线程后继续聊了几十轮、触发了上下文压缩，把当初那条 spawn_thread 调用折进了摘要里，等子线程干完活回来交差，父线程翻遍当前上下文却找不到当初派活的调用 ID，结果直接把子线程的成果丢弃；第三，某个 GitHub 订阅每分钟推十条无关 PR 事件进来，如果全塞进主线程上下文，半小时就能把主线程窗口填满；第四，压缩历史时如果直接删旧行，压缩前就已经派出去、还没读完父历史的子线程，继承到的索引瞬间全部错位。

infinity-agent-core 用一套紧凑的线程树模型和位置索引压缩机制，把这四个坑逐一填平了。

同步派生与 child_of 线程栈校验#

内置的线程控制由四个工具组成，全部定义在 crates/infinity-agent-core/src/tools/thread.rs：spawn_thread、report_to_parent、close_thread 和 send_message_to_child。

其中 spawn_thread 专门实现了 supports_sync() == true 和 execute_synchronous。前文提到过，把派生做成切片内同步执行有两个好处：一是省掉一次存储重载，二是彻底避免刚派发出去就被并发事件误判中断的竞态。

为了挡住上面说的子线程身份错乱重复派生事故，spawn_thread 强制要求模型传入 child_of 参数，内容必须是从根线程到当前线程的完整路径栈（例如根线程传 ["R"]，一级子线程传 ["R", "A"]）。execute_synchronous 第一步就把模型传进来的 child_of 和运行时掌握的真实 context.thread_stack 做精确比对：

// crates/infinity-agent-core/src/tools/thread.rs
if child_of != context.thread_stack {
    return Some(ToolResult {
        id: id.as_str().to_owned(),
        call_id: call_id.map(|c| c.as_str().to_owned()),
        content: vec![ToolResultContent::Text(Text {
            text: format!(
                "Error: child_of {:?} does not match the actual thread stack {:?}. \
                 You may be confused and think you are in the parent thread, \
                 but you are not. You are in thread {}. Do NOT spawn threads — \
                 focus on your assigned task.",
                child_of, context.thread_stack, context.group_id
            ),
        })],
    });
}

这条校验非常管用。如果一个子线程读了继承下来的父线程计划，顺手照抄了父线程的 child_of: ["R"]，运行时会当场把这次调用打回，并把真实的线程栈提醒给它，把它拉回自己的子任务轨道上。

继承边界、Fresh 子代理与自身副本播种#

派生新线程时，调用方可以在两种继承语义里二选一（crates/infinity-agent-core/src/traits.rs 的 SpawnContext）：

  • SpawnContext::InheritUpTo(safe_point)（默认），子线程继承父线程（及所有更早祖先）直到 safe_point 为止的对话历史，但看不到父线程在派生之后新增的任何消息。safe_point 由 HistoryManager::safe_spawn_point() 计算，它会刻意截断在两类内容之前：一是尾部所有尚未收到结果的 ToolCall（防止子线程继承到悬空调用），二是所有还在内存里、尚未持久化到 ConversationStore 的 unvalidated_items（因为子线程是从持久化存储加载祖先历史的）。
  • SpawnContext::Fresh（通过参数 fresh_context: true 开启），子线程以完全空白的历史启动，只看到本次派发给它的自包含指令。源码里把新鲜边界做成可传递的线程属性：ConversationStore::load_history_with_ancestors 从叶节点向根回溯祖先链时，一旦遇到某个标记为 is_fresh_context_thread 的节点，就会把该节点之上所有更早祖先的切片全部裁掉，确保新鲜子代理再派生孙线程时也不会意外泄漏更早的背景噪声。

这里藏着一个极其讲究的实现细节：哪怕在默认继承模式下，spawn_thread 也会把继承截断点落在本次 spawn_thread 调用之前，然后把本次 spawn_thread 调用（保留原始 id、call_id 和参数）单独复制一份写进子线程自己的存储行里，再把子线程任务说明作为对应的 ToolResult 投进子线程队列。

为什么要多此一举自己种一份副本？原因就在父线程压缩。因为父线程随后可能触发上下文压缩，把父线程里的那条 spawn_thread 折进摘要；如果子线程只能通过继承切片看到它，那么当父线程发来 send_message_to_child 消息时，子线程将无法在自身历史里解析原始调用。如今子线程在自己的存储里拥有一份独立副本，配合下面提到的穿透查找，父线程怎么压缩都不影响子线程后续通信。

合成工具调用与双向通信#

大模型 API 通常只认识用户消息、助手消息以及成对出现的工具调用与工具结果，并不理解后台子线程突然发来异步报告这种概念。如果硬把报告伪装成一条普通用户消息塞进去，模型很容易把子代理的汇报错当成人类用户的最新指令。

Infinity 的统一包装手法是合成工具调用（synthetic tool call）。无论是子线程调 report_to_parent 发送中间进度、调 close_thread 汇报最终结论并永久关闭自己，还是父线程调 send_message_to_child 向运行中的子线程追加指示，底层的 prepare_input 都会根据 SyntheticKind（ThreadReport、ParentMessage 或 SubscriptionEvent）先反查出最初的那条调用记录，再往目标线程历史里注入一对结构合法的 receive_event__injected 工具调用与结果：

  • 合成调用参数包含 original_tool_name、original_tool_call_id 和 original_args，模型一眼就能对齐这是哪次 spawn_thread 或哪次订阅带来的异步消息。
  • 在持久化结构 InfinityMessage::SubscriptionEvent 中，这对合成调用与结果作为一个变体保存（payload 用 Box 包裹，避免拉大整个 InfinityMessage 枚举体积）。发给模型时 into_messages() 把它展开成两条标准消息；前端重放历史时则直接渲染成干净的订阅或子线程汇报卡片，不会把内部的 receive_event__injected 脏细节暴露给用户。

那么如果当初父线程的那条 spawn_thread 已经被压缩进了摘要，怎么反查？HistoryManager::find_tool_call（event_processor.rs 第 779 行）先在内存中的当前视图逆向查找；一旦未命中，立刻回退调用 conversation_store.load_history_up_to(&self.thread_id, None, None)，穿透压缩视图直接翻查本线程在持久化存储里的全部原始行。因为压缩只折叠加载出来的视图、从不删除底层原始记录，所以即使父线程休眠并压缩了好几轮，子线程迟到半天的关闭报告依然能精准挂接回原始 spawn_thread 调用。

订阅事件分流：隔离事件子线程 vs associative 内联#

同样的线程树原语，顺手解决了外部事件流的上下文污染问题。

当一条来自 RAP 服务的 subscription_event 到达父线程时，prepare_input 会查看事件上的 associative 标志：

  • 默认模式（associative == false）：父线程自己不消费原始事件，也不把它写入父历史。prepare_input 直接计算父线程当前的 safe_spawn_point()，自动派生一个临时的事件处理子线程（标记 is_subscription_event = true），往子线程存储里种好合成的 spawn_thread 和 receive_event__injected 引导上下文，再把原始事件正文投进子线程的输入队列。子线程独立分析事件（例如拉取 PR diff 检查改动），觉得重要就调 report_to_parent 或带报告调用 close_thread；如果事件毫无价值，子线程直接空报告关闭，父线程上下文里连一丝痕迹都不会留下。短时间内涌入十条事件，就会派生十个子线程并行消化。
  • 内联模式（associative == true）：适用于每一条输出都必须按序进入当前线程自身历史的流式场景（例如 sandbox-core 跑长命令时实时推送的构建日志行）。这类事件跳过派生子线程，直接以 receive_event__injected 注入订阅线程自身历史。

无论走哪条路，只要事件携带了 final: true，prepare_input 就会同步调用 current_history.remove_subscription，把该订阅从 StateStore 的活跃集合里摘除。

位置索引压缩：不删旧行，按游标折叠#

长对话总有一天会撞上模型上下文窗口。本地驱动 drive_thread 在 handle_step_result（crates/infinity-agent-core/src/system/local/driver.rs 第 384 行）里监控每次补全返回的 usage.total_tokens（刻意用 total_tokens 而不是 input_tokens，避免启用 Prompt Caching 时少算缓存命中部分）。一旦满足：

total_tokens as usize > context_window * 3 / 4

本地驱动就自动向自己塞入一条 TaggedSyntheticKind::Compaction 合成消息（同时置位 compaction_triggered = true 防止重复触发，直到收到 CompactionComplete 后复位）。

有趣的是，上下文压缩本身也是用子线程机制实现的。prepare_input 收到压缩触发消息后，取当前 safe_spawn_point() 派生一个标记为 is_compaction = true 的子线程，种入名为 __harness_begin_compaction__ 的引导调用，要求该子线程把继承到的全部历史总结成摘要，再以摘要作为 report_to_parent 调用 close_thread。

压缩子线程调用 close_thread 时，CloseThreadTool 识别出 is_compaction == true，不走普通父子汇报流程，而是读取子线程派生时记录的 spawn_order（记作 up_to_order），调用 conversation_store.save_compaction_summary(&parent_id, report_text, up_to_order) 单独存入摘要表，随后向父线程投递一条 TaggedSyntheticKind::CompactionComplete 消息。

父线程收到通知后调用 HistoryManager::apply_compaction()，核心只是一段精准的相对坐标换算：

// crates/infinity-agent-core/src/event_processor.rs
let offset = self
    .compacted_up_to
    .borrow()
    .map_or(0, |prev| prev as usize - 1);
let up_to =
    (up_to_order as usize).saturating_sub(offset) + self.ancestor_prefix_len.get();

这段算式把两个边界条件交代得清清楚楚：如果当前线程之前已经压缩过一次，那么旧摘要本身占住了内存历史的槽位 0，所以偏移量要减 1；如果当前线程是个子线程且之前还没压缩过，内存历史最前面还拼着 ancestor_prefix_len 条不属于自己存储表的祖先消息，切分位置必须加上这部分前缀，并在压缩完成后把 ancestor_prefix_len 归零（因为祖先内容已经被吞进新摘要里了）。

把摘要按 up_to_order 单独建表而不删改原始消息行，带来的直接收益就是历史视图的时序一致性。一个在索引 10 处被派生出来的子线程，哪怕父线程后来在索引 40 处做了压缩，load_history_with_ancestors 为该子线程查父摘要时传入的是 up_to_order <= 10，自然会跳过索引 40 的摘要，照旧精确还原出 0 到 10 的原始父历史；而在索引 50 处派生的新子线程，则会直接拿到索引 40 的摘要加上 40 到 50 的增量行，省下全部重复 token。

线程树和压缩机制把状态结构理顺了，但在本地单机跑几十个并发线程时，消息什么时候该批处理、什么时候该延迟、什么时候该立刻抢占打断？下一章拆解本地单线程路由器与延迟队列。

06

单线程本地调度器、延迟队列与抢占打断

在云端 AWS Lambda 上，每个活跃线程的切片由 SQS FIFO 自动串行调度，跑完进程就销毁，不存在长期驻留的调度器。但把同一套 infinity-agent-core 搬回开发者本机守护进程或者嵌入式应用时，立刻会碰到四个本地运行特有的竞态难题：

  1. 几万个历史线程如果每个都在后台养一个常驻 tokio::spawn 任务，光任务结构体和通道缓存就会吃掉可观内存。
  2. 父线程刚刚派发了一个耗时十秒的 execute_command，跑了一半时另一个子线程发回一条 report_to_parent。如果父线程立刻处理这条汇报，就会因为历史末尾还有未应答的工具调用，被迫给 execute_command 注入一条中断结果，把本来好端端在跑的构建平白无故杀掉。
  3. 用户正在看模型流式吐字，突然发现方向错了，直接敲下一句新指令回车。运行时必须立刻停掉当前流式生成、保存已经吐出来的半截内容，还得确保不能把模型还没响应过的未验证输入提前写坏。
  4. 某个线程刚准备空闲退出，就在释放通道前的一微秒，一条新消息或一个新前端订阅请求撞了进来，怎么保证不丢消息、也不把同一个线程同时拉起两个驱动？

crates/infinity-agent-core/src/system/local/ 里的 router.rs、driver.rs 加上 system/defer.rs 与 system/thread.rs，用单线程协作式调度和极克制的状态机把这四件事全部收敛清楚了。

为什么选择单线程 LocalSet 加 FuturesUnordered#

翻开 crates/infinity-agent-core/src/system/local/router.rs，整个本地 Actor 系统刻意运行在单线程的 tokio::task::LocalSet 上，而不是多线程工作窃取池。驱动内部大量使用了轻量的 Rc、RefCell 和 Cell（HistoryManager 和 Thread 都不需要 Arc<Mutex<...>> 锁竞争）。更重要的是，单线程 LocalSet 带来了确定性的协作切换点：只要一段函数里没有 .await，路由器 route_loop 和各线程驱动 drive_thread 之间就不会互相抢占，这正是后面无竞态原子退出检查的前提。

另一个省内存的关键手笔在 route_loop（第 256 至 261 行）：路由器没有用 tokio::spawn 给每个线程建独立任务，而是用一个 FuturesUnordered 直接持有所有活跃线程的 drive_thread future，再配一张 workers: HashMap<ThreadId, WorkerChannels> 路由表。

当某个线程空闲返回时，它的 future 从 FuturesUnordered 中产出 ThreadId，整个驱动状态机连同 HistoryManager 的内存立刻彻底释放，路由器紧接着把 workers 里对应通道已关闭的条目删掉（代码特意检查 w.input_tx.is_closed()，防止误删同一瞬间刚重新拉起的新驱动条目）。为了让单个线程的意外 bug 不至于拖垮整台守护进程，每个驱动 future 外层都包了 rap_protocol::log_panic("thread_driver", driver)，用 AssertUnwindSafe(...).catch_unwind() 捕获 panic 并记日志，其余线程照常运转。

准入策略：绝不为幽灵或已停线程唤醒驱动#

外部 RAP 服务随时可能迟到几小时推回来一条过期回调，或者针对一个已经被用户手工停止的会话发来订阅事件。如果路由器照单全收、见消息就拉起驱动，就会平白创建出幽灵线程记录，或者把已经停止的代理偷偷叫醒。

route_loop（第 310 至 356 行）在拉起新驱动之前加了一道准入门禁：

  • 普通用户文本直接放行（is_user_text_input 为真），因为发新文本正是用户创建新线程和唤醒已停止线程的合法入口。
  • 订阅客户端请求直接放行，允许 UI 在线程第一条消息到来之前提前挂载监听。
  • 其余一切事件型输入（工具结果、订阅事件、子线程回报、OAuth、用户选择）必须过两关：先查 conversation_store.thread_exists(&thread_id)，不存在则直接丢弃并记日志；再查 state_store.is_thread_stopped(&thread_id)，已停止则直接丢弃。两关遇到存储短暂报错时都采用 fail-open 策略（记录警告并放行），宁可让驱动醒来走一遍 prepare_input 吸收脏消息，也不因存储抖动误丢真实的工具回调。

DeferQueue 与 is_passive：什么时候该等，什么时候能打断#

再看前面提到的第二个难题：子线程回报撞上正在执行的工具调用。

crates/infinity-agent-core/src/system/defer.rs 定义了 DeferQueue trait，只有 push 和 drain 两个方法，提供两种内置实现：本地常驻模式用 InMemoryDeferQueue 暂存在内存向量里；无服务器 Lambda 模式用 NoDeferral（push 永远返回 Ok(false)），因为 Lambda 没有驻留进程可存内存，除非调用方自己实现基于 SQS 延迟重投的传输层队列，否则直接接受打断语义。

真正决定一条事件该不该被延迟的逻辑，在 Thread::pending_active_tool_call 和 Thread::filter_deferrable（crates/infinity-agent-core/src/system/thread.rs 第 216 至 291 行）里，依赖 Tool::is_passive() 这个精细的布尔标记：

尾部挂起的工具状态 到来的新消息类型 filter_deferrable 处理动作
无未应答工具，或挂起的是被动工具（如 sleep / sleep_until / sleep_until_event_or_input） 任何消息 立即放行，并排空此前积压的延迟队列一起拼进本批；若原工具在休眠，则按正常中断逻辑唤醒
挂起的是活跃工具（is_passive() == false，如 execute_command） 恰好是该工具的 ToolResult，或普通用户文本 立即放行，并将延迟队列排空追加在后面（保持本批先结算挂起调用、再处理延迟事件的顺序）
挂起的是活跃工具（is_passive() == false） 可延迟合成事件（SubscriptionEvent、ThreadReport、ParentMessage） 压入 DeferQueue 暂存，不打断正在运行的工具调用

这条规则把语义分得极细：sleep 家族工具虽然也在等结果，但它们代表原地待命，标记为 is_passive() == true，允许外部订阅事件或子线程回报随时叫醒；真正在跑构建、改文件的工具属于活跃任务，无关合成事件乖乖在 InMemoryDeferQueue 里排队，等构建结果一到（或者用户主动发话打断）再按顺序接上。

流式抢占打断与优雅关闭#

本地驱动 drive_thread（crates/infinity-agent-core/src/system/local/driver.rs）用 InFlightStep 把正在执行的 step_no_defer future 和它的 oneshot::Sender<()> 取消句柄绑在同一个结构体里。这样做的好处是所有权天然同步：取消步骤会消费掉整个 InFlightStep，哪怕驱动因为外层关闭被直接 drop，cancel_tx 也会随之释放，内层的 run_completion 立刻收到取消信号。

当一个步骤正在流式推理中，drive_thread 在 tokio::select! { biased; ... } 里同时监听步骤完成、新输入通道 rx 和新订阅通道 subscribe_rx：

  • 如果 rx 收到的批次里包含用户文本，驱动立即调用 in_flight.take().cancel().await 中断当前补全流。如果此时模型已经吐出部分文本，取消路径会把已生成的半截内容正常 flush_turn 并 sync() 落盘，不会丢掉用户刚才在屏幕上看到的话；如果模型还没吐出第一个字节就取消了，本轮输入留在内存的 unvalidated_items 里不落盘，下一轮连同新的打断消息一起发给模型。接着驱动把批次拆成用户文本和非用户消息两部分，给第一条用户文本加上 <interrupt> 前缀（前端回显 input_event 时会剥掉这个前缀，模型则能明确感知自己被用户中途打断），非用户消息放进 pending_batch 留待后续处理。
  • 如果 rx 收到的批次里全是异步事件（没有用户文本），驱动不打断当前推理，只是顺手塞进 pending_batch，等当前步骤自然跑完再接手。
  • 如果 rx 关闭（代表整个 RunningSystem::shutdown() 被触发），驱动同样显式 cancel().await 等待当前步骤把已验证历史刷盘完毕再退出。路由器侧也会 drop(workers) 后把 drivers 排空，绝不在持久化中途把进程掀翻。

同步原子退出与订阅安装 ACK#

最后看本地驱动最容易出并发 Bug 的两个边角：空闲退出与中途订阅。

当 pending_batch、rx 和 defer 队列都为空时，drive_thread 调用一个完全同步、不含任何 .await 的函数 check_before_idle（driver.rs 第 331 行）：先排空 subscribe_rx 处理所有刚到的订阅请求，再 try_recv() 确认 rx 确实空了；接着检查 thread.awaiting_tool_result()（即历史最后一条是不是除 close_thread 之外的未应答工具调用）。如果是，返回 IdleDecision::AwaitInput，驱动继续挂在 select! 上等工具回包；如果不是（即便线程还挂着活跃订阅，也不必常驻驱动，事件来了路由器会再拉起它），立刻返回 IdleDecision::Exit 退出驱动。

因为 check_before_idle 里没有让出点，且与 route_loop 共享同一个单线程 LocalSet，所以新消息要么在检查前就已经躺进了 rx 被它当场捞走，要么一定发生在驱动退出、接收端关闭之后，被路由器检测到 is_closed() 并拉起新驱动，绝不存在消息掉进两头裂缝的可能。驱动退出时，DriverGuard::drop 在同一临界区里移除 active_threads 集合成员并向 lifecycle_tx 发出 ThreadLifecycleState::Idle，让外部宿主（例如守护进程）据此精准回收该会话关联的附加资源。

前端订阅也用同样的严谨手法消除了竞态：SubscribeHandle::subscribe 带一个 oneshot::Sender<()>，直到目标线程驱动把 thread.replay_snapshot() 交给了 observer.on_subscribe 并真正把监听者注册完成，才会发回 ACK。调用方只要 await 完 subscribe() 再发 send_user_text()，就能百分之百保证不会漏收第一批流式事件。

把本地调度器拆透后，再往下看一个经常被低估的边界：核心运行时是怎么在不认识任何一家大模型 SDK、也不解析一句报错文本的前提下，处理五花八门的限流、超窗、断流和跨进程模型供应的？下一章拆解模型供应协议。

07

模型供应协议、跨进程隔离与错误分类契约

做过多模型接入的团队大多写过这种越改越脏的代码：核心 Agent 循环里嵌着一大段 if err.contains("Throttling") || err.contains("429") || err.contains("too many requests")，旁边又叠着一个 120 秒的流式空闲超时定时器。结果一换模型供应商，报错措辞变了，限流被当成致命错误直接放弃；一碰上推理模型思考两分半钟不吐字，核心层的空闲超时把好好的流强行掐断，触发毫无意义的重试，既烧双倍 token 又让用户干等。

Infinity 在 0.2.0（PR #121）里把这套脆弱的耦合彻底拆干净了。整个模型供应子系统由三个 crate 组成：infinity-provider-protocol（1,280 行）定义协议与跨进程传输，infinity-provider-bedrock（1,445 行）对接 AWS Bedrock ConverseStream，infinity-provider-rig（504 行）基于 rig-core 对接 OpenAI 兼容服务。

ErrorClass 契约：供应器分类，核心层只看枚举#

翻开 crates/infinity-provider-protocol/src/completion.rs，核心运行时对模型失败的所有认知，全部收敛在四个枚举变体里：

pub enum ErrorClass {
    Transient,       // 瞬时故障：断流、后端抖动、建连超时，可短退避重试
    Throttled,       // 限流配额不足：需要更长退避后重试
    ContextOverflow, // 上下文超窗：原样重试必败，必须收缩输入或压缩
    Fatal,           // 永久错误：非法请求、未知模型、无权限，立刻放弃
}

CompletionError::class() 把四类包装错误也归口到这四个值：RequestError 和 JsonError 属于本地构造或解析出错，归为 Fatal；ResponseError 属于读取流时的传输帧故障，归为 Transient；ProviderError { message, class } 直接携带供应器自己填好的 ErrorClass。

这样一来，infinity-agent-core 里的 run_completion 彻底不再做任何字符串匹配，也删掉了原本硬编码的 60 秒建连超时和 120 秒流中途停顿定时器。它的重试状态机变得极度干净（event_processor.rs 第 1404 至 1599 行）：

  • 收到 ErrorClass::Throttled 且未超过 MAX_COMPLETION_RETRIES（10 次）：休眠 THROTTLED_RETRY_DELAY（30 秒，休眠期间仍响应用户 cancel_rx 中断）后重试。
  • 收到 ErrorClass::Transient 且未超过 10 次：休眠 TRANSIENT_RETRY_DELAY（5 秒，可取消）后重试；若中途已经吐过部分块，先调用 history.discard_turn() 扔掉脏缓冲，再从干净历史重发。
  • 收到 ErrorClass::ContextOverflow：不走普通退避，直接转交第 3 章拆解过的 recover_from_overflow。
  • 收到 ErrorClass::Fatal：直接报错退出，一次都不重试。

超时策略也同步下放给供应器自己决定。核心层自己零超时，理由很务实：不同后端的延迟特征天差地别，核心层根本猜不准一次深度推理要思考多久。

Bedrock 供应器的真实工程细节#

crates/infinity-provider-bedrock/src/lib.rs 浓缩了不少对接真实生产云服务踩出来的坑，读它的注释比读官方文档还解渴：

  1. 只卡建连，绝不掐活流，Bedrock 偶尔会出现请求黑洞（发出去既不返回也不报错），因此 BedrockProvider 在 ConverseStream 请求发起阶段加了 60 秒的 REQUEST_INITIATION_TIMEOUT，超时后显式包装成 ErrorClass::Transient 交给核心层重试。一旦流式响应建立，代码里刻意不设任何中途停顿或读取超时，宁可相信底层连接与模型思考，也绝不人为掐断正常长推理。
  2. 细粒度工具流 Beta 绕开服务端看门狗，Bedrock 上调用 Anthropic 模型吐出一个很大的 edit_file 或 create_file 工具参数时，默认情况下后端会在服务端把整段工具输入缓冲校验完才开始下发。这中间长达数十秒的静默空档经常触发 Bedrock 自己的流看门狗，直接报 ModelTimeoutException。因此供应器主动附带了 fine-grained-tool-streaming-2025-05-14 Beta 请求头，让工具参数碎片边生成边下发、流永不静默。源码同时坦诚写明了代价：服务端不再替客户端预校验工具 JSON，碎片拼完后可能解析失败，这部分交由 stream.rs 里的 finish_tool_call 单独分类处理。此外还启用了 context-1m-2025-08-07 百万上下文 Beta 标志，并自动在每次请求的最后一条消息末尾追加 Prompt Caching 缓存点。
  3. 集中式错误映射，classify_bedrock_error 根据 AWS SDK 错误码和消息启发式完成映射：ThrottlingException / ServiceQuotaExceededException 归 Throttled；包含 "too long"、"too large"、"input length" 或同时含 "exceed" 与 "context" 的 ValidationException 归 ContextOverflow；InternalServerException、ServiceUnavailableException、ModelTimeoutException、ModelNotReadyException、ModelStreamErrorException、ModelErrorException 以及 "unexpected end of stream" 归 Transient；其余默认 Fatal。infinity-provider-rig 则在自己 crate 里维护针对 OpenAI 兼容接口的同类映射。
  4. 反套娃的真实集成测试，除了常规单测，infinity-provider-bedrock 还准备了非默认特性 live-tests（tests/live.rs），直接用本地 AWS 凭证打真实 Bedrock 端点验证超窗分类、未知模型致命错误和正常流式路径。变更记录里特意提到，正是跑真实测试才抓出了开发期一个算错的 token 估算问题，而光靠写死的单元测试字符串对照表永远测不出真实服务改文案。

插件化架构：通过 Unix Socket 跨进程运行供应器#

在 Lambda 部署里，模型供应器直接作为 Rust 库静态链接进二进制即可。但在本地产品 Infinity Code 里，用户希望像装插件一样执行 infinity provider install bedrock --crate infinity-provider-bedrock，随时安装、升级、混用多个不同供应器（比如同时装 Bedrock 和 OpenAI 兼容供应器，在不同线程间实时 /model 切换），而不必把所有云厂商的庞大 SDK 全编进主二进制 infinity-daemon。

crates/infinity-provider-protocol/src/remote.rs 用不到五百行代码搭出了一套极其清爽的跨进程供应器协议：

  • 启动与发现：每个独立供应器二进制启动后调用 serve_provider(Arc<dyn ModelProvider>)，在系统临时目录生成一个短路径 Unix Domain Socket（格式 inf-provider-<12位hex>.sock，特意压短路径长度以避开 macOS 上约 104 字节的 Unix Socket 路径上限），把 socket 路径打印到 stdout 交给守护进程读取，然后进入监听循环。
  • 并发连接模型：协议使用 LinesCodec 承载换行分隔的 JSON（JSON Lines），每次请求新建一条独立的 Unix Socket 连接。这个朴素的选择省掉了在单连接上写多路复用帧 ID、反压和队头阻塞的整套复杂性：十个线程同时推理，就是十条并行的本地 socket 连接，各自独立读写互不干扰。
  • 两种请求与流式帧：ProviderRequest::ListModels 返回单行 Models(Vec<ModelEntry>) 或 Error(WireError)；ProviderRequest::InvokeModel 返回 InvokeStarted，随后逐行流式推送 Chunk(Result<StreamChunk, WireError>)，最后以 StreamEnd 收尾。注意流中途的错误也能作为 Chunk(Err(WireError)) 沿流透传，与进程内流行为保持完全同构。
  • 跨进程保留错误分类：错误在 socket 上包装成 WireError { message, class }，反序列化时如果对方是老版本供应器漏掉了 class 字段，默认兜底为安全的 ErrorClass::Fatal（不盲目重试）。于是 ErrorClass 跨越了进程边界，客户端侧的 RemoteModelProvider 对 infinity-agent-core 呈现出与进程内供应器一模一样的 ModelProvider trait。

到这里，Agent 怎么运行切片、怎么管历史、怎么调异步工具、怎么分线程、怎么调度本地并发以及怎么连大模型，全都拼装完整了。但对于一个 Coding Agent 来说，最要命的现场还没解决：当三个并发线程同时改写同一个代码仓库时，怎么不把代码改烂，又不让模型一条 rm -rf 误伤开发者的宿主目录？下一章拆解堆叠沙箱子系统。

08

堆叠沙箱：Jujutsu 工作区、Git Worktree 与 OS 写隔离

让两个并行的编码 Agent 在同一个项目目录里干活，一个负责补单元测试，另一个负责重写 README 并顺手跑 cargo fmt，不出十秒就会撞出经典灾难：文件互相覆盖，未暂存的 git diff 混成一锅粥，开发者的工作树被改得面目全非，甚至模型在子目录里敲了一条不小心的清理命令，顺手把宿主目录里的未提交代码删光了。

Infinity Code 把代码编辑与命令执行全部做成了一个独立的 RAP 工具服务，由 sandbox-core（3,902 行）、sandbox-local（4,911 行）和 sandbox-remote（534 行）三个 crate 组成。它的核心思路很干净：宿主的真实工作目录永远只读不动，每个 Agent 线程都分配一块隔离的独立工作区，父子线程之间以堆叠方式共享基线、干完再合并，同时在操作系统层用内核沙箱把写权限死死框在沙箱目录内。

SandboxBackend 与 ModeProvider：把 VCS 策略抽离出核心服务#

打开 crates/sandbox-core/src/sandbox.rs，沙箱层没有把 Jujutsu 或 Git 逻辑硬编码进 HTTP 路由，而是拆出了两层 trait：SandboxBackend 负责底层环境差异（本地目录加 OS 写隔离 vs 云端 AWS EFS 镜像），ModeProvider 负责具体版本控制系统的工作区生命周期（detect、create_sandbox、refresh_sandbox、describe、detect_external_change、push_sandbox、squash、diff_files、cleanup 以及供 Drop 使用的同步 cleanup_blocking）。

在 crates/sandbox-local/src/backend.rs 里，LocalBackend::new 默认注册了两个对称的内置提供器：LocalJjProvider 在前，LocalGitProvider 垫底（调用方也可以通过 with_provider 往前插自定义提供器）。每次收到 clone_repo 调用时，后端先从请求路径向上回溯找到真实仓库根（哪怕 cwd 落在嵌套子目录也能准确识别），再按注册顺序询问提供器：

  • Jujutsu 模式（SandboxMode::Jj，推荐），检测到 .jj 目录即接管。LocalJjProvider 在 {repo}/.infinity/.sandboxes/ 下建临时目录，执行 jj workspace add -r root()，配置工作区级 user.name/user.email，检出或新建名为 sandbox-{thread_id} 的书签。每次复用缓存工作区前自动跑 jj workspace update-stale；每次写操作完成后调用 jj bookmark set sandbox-{thread_id} -B 推进书签，若是 colocated 仓库还会执行 jj --ignore-working-copy git export 让底层 Git 引用保持同步；每次操作前还会通过 jj_detect_external_bookmark_move 检查书签是不是被用户在外部挪过位置，如果有偏移就在工具结果里附带醒目警告。
  • Git 模式（SandboxMode::Git，兜底），纯 Git 仓库下自动启用。LocalGitProvider 通过 git worktree add 在 {repo}/.infinity/.sandboxes/ 下拉出独立 worktree 并绑定同名分支 sandbox-{thread_id}，每次修改后用 git_amend_all 把改动收拢到分支顶端，销毁时用 git worktree remove 清理，如果顶端提交为空还会顺手删掉空分支。
  • 直接模式（SandboxMode::Direct），通过 open_sandbox_direct 打开原始目录，跳过 ModeProvider。注意直接模式下 sandbox_writable 默认设为 false，命令和文件工具只读不能直接改写原目录，真正要写必须走下面的人工审批流程。

堆叠与合并：父子并行线程怎么无冲突汇流#

当根线程启动后，它拿到的工作区挂在书签 sandbox-{root} 上。此时它通过 spawn_thread 派生出两个子线程分别改单测和文档，每个子线程初始化沙箱时传入 base_thread_id = root，于是 CloneContext::base_bookmark 指向 sandbox-{root}。

这样就形成了堆叠沙箱（stacked sandboxes）：子线程 A 拿到 sandbox-{c1}，子线程 B 拿到 sandbox-{c2}，两者的基线都站在父线程的最新改动之上，但各自在独立的目录里修改、编译和跑测试，彼此完全看不见对方的半成品。等子线程 A 报告完成，父线程调用 squash_sandbox（底层在 jj 模式调 jj::squash_from，在 git 模式调 git::squash_from）把 sandbox-{c1} 压缩并回 sandbox-{root}；子线程 B 完成后如法炮制。整个过程中开发者自己的工作副本丝毫未动，最后只需要审一次 sandbox-{root} 的统一 Diff，满意了执行一条 jj squash --from sandbox-{root} 或 git merge sandbox-{root} 即可。子线程关闭时，RapNotifier 发出的 /close_thread 通知会触发 cleanup_sandbox_permanently，自动清理已合并的子工作区与空书签。

OS 级写隔离：macOS sandbox-exec 与 Linux Bubblewrap#

光靠把子进程 current_dir 设在沙箱目录里防不住模型越界写文件，一条带相对路径 ../../../foo 或绝对路径的 Shell 命令就能改穿宿主仓库。因此 sandbox-local/src/backend.rs 在 spawn_command 里（第 307 至 426 行）引入了操作系统原生的写权限隔离：

  • macOS (sandbox-exec)，动态拼出 SBPL 策略：默认 (allow default) 放行读与常规系统调用，紧接着 (deny file-write*) 封死全盘写权限，然后只用 (allow file-write* (subpath ...)) 白名单放行当前沙箱目录（Direct 模式除外）、该沙箱专属的持久化 TMPDIR、sccache 缓存目录、额外授权路径，以及字符设备 /dev/null。
  • Linux (bwrap / Bubblewrap)，用命名空间挂载构造同样的写边界：--ro-bind / / 把整棵根文件系统只读挂载进来，再用 --bind 单独把沙箱目录、TMPDIR、sccache 缓存和额外授权路径绑定为可写，并挂载独立 --dev /dev 与 --proc /proc。

源码里还有三个很老道的工程细节值得记下来：

  1. 防止 Git 越界向上爬目录，因为沙箱建在 {repo}/.infinity/.sandboxes/ 内部，如果不加干预，在沙箱里跑 git status 或 git rev-parse 可能会一路向上穿透识别到外层宿主仓库。spawn_command 统一给子进程注入环境变量 GIT_CEILING_DIRECTORIES，把天花板钉在沙箱父目录上（sandbox-local/tests/jj_colocated.rs 专门有测试守住这条底线）。
  2. sccache 外部保活，如果让 cargo build 在沙箱里自己拉起 sccache 守护进程，它会被框在沙箱写权限里。LocalBackend 在每次起沙箱命令前，先在沙箱外调用 ensure_sccache_server() 跑一次 sccache --start-server，同时把 SCCACHE_DIR 加进可写白名单，既保住增量编译缓存又不破坏写隔离。
  3. Linux 构建前置条件（commit e1a3e4b / PR #188），翻开 crates/sandbox-local/build.rs，在 Linux 上编译 sandbox-local 时，构建脚本会先探测系统里有没有 bwrap --version；如果没有，就执行 scripts/install-bwrap.sh 试图从源码现场编译 Bubblewrap，而源码编译需要 git、C 编译器（gcc / build-essential）和 libcap 开发头文件（libcap-dev / libcap-devel）。最新快照 e1a3e4b 正是在文档里把 Debian/Ubuntu 与 Fedora/AL2023 的预装包命令补清楚了。

越权审批与流式命令执行#

如果模型确实需要改写沙箱外的文件（比如执行 git push 或修改用户指定的原仓库路径），execute_command 的参数支持声明 additional_permissions，接受 "write-orig" 或 "write:/path"。

sandbox-core/src/server.rs 的 handle_execute_command_streaming_inner（第 845 至 930 行）会沿着 RapInvocation.thread_ancestors 拼出完整线程链，逐级检查元数据里是不是已经有过授权。如果没有，沙箱服务会挂起当前任务、通过 RAP 的 send_user_choice 往前端弹一个多选项确认框：既可以选择永久授权给根线程或当前子线程（授权会沿祖先链自动向下继承），也可以选 "Yes once" 单次放行，或者 "No" 拒绝。

命令真正跑起来后，流式执行还有两处关键防护：第一，invoke_handler 在 tokio::spawn 后台任务之前就同步把取消通道 oneshot::Sender 登记进 InFlightMap，彻底消灭任务刚启动就收到 /cancel_tool_call 却找不到取消句柄的时间窗口；第二，子进程创建时调用 .process_group(0) 自成进程组，收到取消信号后 kill_process 向负 PID（-pgid）发 SIGTERM，一次清理整棵子进程树（例如 cargo test 派生出的所有编译和测试子进程），同时通过 ViewUpdate 回调把最新文件改动实时推给前端 Diff 面板。

云端镜像：sandbox-remote 的 EFS 后端#

当沙箱部署在无服务器 AWS Lambda 上时，没有常驻本地磁盘可以缓存工作区。crates/sandbox-remote/src/backend.rs 实现了另一套 SandboxBackend，叫 EfsBackend：

  • 共享的 AWS EFS 挂载点（如 /mnt/efs/sandbox-repos）按归一化后的远端 Git URI 存放一份裸 Jujutsu 仓库镜像（jj git clone --no-colocate），多个操作同一仓库的线程共用这份底仓，每次初始化顺手 jj git fetch 同步上游。
  • 每次工具调用在 Lambda 的瞬时 /tmp 目录里基于 EFS 底仓拉出临时沙箱工作区，改完代码后通过 jj_push_working_copy 把 sandbox-{thread_id} 书签推回 EFS 裸仓，调用结束立刻删除 /tmp 目录。
  • 回调通道换成了 SigV4CallbackClient（sandbox-remote/src/sigv4_client.rs），给发往 rap-receiver Function URL 的请求自动签发 AWS SigV4 签名。

不管是本地 LocalBackend 还是云端 EfsBackend，上层 sandbox-core 的路由和核心运行时完全感知不到差异。下一章我们往上走一层，看看本地守护进程怎么把这些沙箱、模型供应器、远程 SSH 开发机和跨主机热迁移统统串起来。

09

本地守护进程、SSH 远程代理与跨主机热迁移

写代码时经常会遇到两种场景：第一种，在笔记本终端里让 Agent 跑一轮大重构，跑了一半想合上终端窗口切去干别的，甚至改用浏览器里的桌面 UI 查看 Diff，回来再接着聊，不能一关终端就把 Agent 和后台构建全杀掉；第二种，起初在笔记本本地开了个会话分析了半天需求，真到要编译庞大 Rust 工作区或者跑 GPU 测试时发现本机算力吃紧，想把整个活生生的会话连同对话历史树、子线程和沙箱里改到一半的代码，原封不动搬到云端那台 64 核开发机上继续跑。

crates/infinity-daemon/（9,215 行）就是为这两个场景设计的控制枢纽。CLI 终端、桌面 Web 界面、Zed 编辑器（ACP）和 Slack 机器人，本质上都是连向同一个守护进程的客户端。

常驻守护进程与 256 MiB 帧边界#

守护进程在首次运行 infinity 时自动拉起，把全部本地状态收纳在 ~/.infinity/ 下：

路径 职责
~/.infinity/daemon.sock 客户端与守护进程通信的 Unix Domain Socket
~/.infinity/daemon.pid 守护进程 PID 文件
~/.infinity/providers.json 已安装的外部模型供应器二进制注册表
~/.infinity/remotes.json 配置好的 SSH 远程守护进程列表
~/.infinity/sessions.json 会话索引元数据（工作目录、关闭与归档状态）
~/.infinity/.../{thread_id}*.json 按线程拆分的懒加载历史、元数据与视图快照

这里有一个很容易被忽略的传输层细节（crates/infinity-protocol/src/lib.rs 第 175 至 190 行）：tokio 默认的 LengthDelimitedCodec 单帧上限只有 8 MiB。但在 Coding Agent 场景里，一次重放长对话历史或者回传大文件 Diff 很容易冲破 8 MiB，导致客户端莫名断连。infinity-protocol 统一提供了 length_delimited_codec() 工厂函数，把 MAX_FRAME_LENGTH 调到 256 MiB，客户端和守护进程两端强制复用，保证帧长上限不会漂移。

面向浏览器桌面端（infinity-web + infinity-ui），守护进程通过 ws_handler.rs 暴露 WebSocket 接口，默认监听 127.0.0.1:8080（可通过 INFINITY_WS_BIND 与 INFINITY_WS_PORT 调整）；如果编译 CLI 时启用了 --features bundled-web，web_assets.rs 会把静态构建产物直接打包进二进制，开箱即访问，和终端 TUI 共享同一批在线会话。

懒加载 JSON 持久化与历史格式兼容#

crates/infinity-daemon/src/memory_store.rs 的 PersistentConversationStore 展示了非常克制的组合设计：它内部直接包着核心库的 InMemoryConversationStore，把所有复杂的祖先链、派生截断、压缩游标逻辑全部委托给核心实现，自己在外面只叠了一层按线程懒加载的 JSON 文件持久化。

每个线程在磁盘上拆成三份文件：{thread_id}.json 存消息列表与压缩摘要，{thread_id}.meta.json 存核心 ThreadInfo 与守护进程专用的 ThreadExtras（标题、子线程列表、累计 token、最后更新时间以及该线程独立选中的 selected_model），{thread_id}.views.json 存前端旁路视图（例如沙箱实时推送的 Diff 面板内容）。两张内存标记集合 loaded 和 metadata_loaded 保证打开会话列表时只读轻量的 .meta.json，真正点进某条会话才把完整消息读进内存。

源码里还保留了干净的向后兼容层：反序列化 ThreadSnapshot 时先尝试新格式（带展示元数据的 InfinityMessage），失败则回退解析旧版的 OldThreadSnapshot（裸 Message 加独立的 display_as 旁路表）并在内存里无损升级；如果老元数据里没有按线程记录的 selected_model，加载时自动用哨兵值识别并回填全局默认模型。

SSH 远程代理：透明拼装 ThreadRef#

开发者在 ~/.infinity/remotes.json 里登记远程开发机（或者执行 infinity remote add devbox -- ssh -J bastion devbox）。守护进程启动时，crates/infinity-daemon/src/remote.rs 读取 ssh_args，为每台远端建立一条直连远端 ~/.infinity/daemon.sock 的 SSH 转发隧道，并在断线时每隔 5 秒自动重连，同时把 connecting / connected / disconnected 状态实时广播给前端 UI。

多主机代理最巧妙的地方在于客户端几乎零感知：

  • 远端会话在列表里通过 ThreadRef::prefixed(&remote) 染上前缀（如 devbox/a1b2c3d4），本地会话保持裸 UUID。
  • 客户端发来针对 devbox/a1b2c3d4 的 Connect、UserInput 或 SwitchModel 时，本地守护进程识别出 remote == Some("devbox")，调用 strip(&remote) 剥掉前缀，原样沿 SSH 隧道转发给远端守护进程。
  • 远端返回的事件流再经由本地守护进程重新打上 devbox/ 前缀推回前端。整个过程不需要在远端开放任何公网 HTTP 端口，完全复用开发者已有的 ~/.ssh/config、跳板机与密钥认证体系。

跨主机热迁移：把活会话与沙箱一起搬走#

热迁移是 infinity-daemon 里最见分布式系统功底的一块代码，编排逻辑集中在 crates/infinity-daemon/src/migrate.rs（428 行），配合 sandbox-core/src/server.rs（第 1994 至 2250 行）的 /migrate 与 /migrate/import 两个接口完成。

无论用户是把本地会话搬到远端 devbox、把远端 devbox 搬回本地，还是把一台远端 devbox 直接搬到另一台远端 gpu-server，永远由本地守护进程充当总编排器。整个搬迁严格按六个阶段推进：

  1. 停机定格源会话，先在源主机调用 cleanup_session 停掉正在跑的 Agent 驱动和原会话附属的 RAP 服务，确保对话历史与沙箱文件在打包期间不再发生变化。
  2. 拉起目标端迁移 RAP 服务并打通 SSH 隧道，boot_dest_and_tunnel 在目标主机的 dest_cwd 下拉起那些在清单里声明了 needsMigration: true 的 RAP 服务（主要是 sandbox-local），拿到监听端口后按源与目标的拓扑动态建转发隧道：
    • 本地搬到远端：通过 ssh_forward_port 把远端目标端口正向转发到本机。
    • 远端搬到本地：通过 ssh_reverse_forward_port 把本机目标端口反向转发到源远端。
    • 远端 A 搬到远端 B：本地编排器充当中继，先把远端 B 的端口正向转到本机，再从本机反向转到远端 A，形成一条无需 A/B 互通直连的级联隧道。
  3. 沙箱打包与 multipart 传输，源端拉起临时迁移 RAP 服务，通过 RapNotifier::request_migration 通知源端 sandbox-local 向目标 URL 迁移。sandbox-core 的 migrate_inner 收集属于该 root_thread_id 的所有线程沙箱状态：如果是 Jujutsu 仓库，先确保所有工作区都已加载并跑一次 jj git export 把书签全部导出到 Git 引用里；接着调用 git bundle create 把该会话全部线程的 sandbox-{thread_id} 书签打成一个自包含的二进制 bundle 文件；最后连同序列化后的元数据 JSON 通过 HTTP multipart POST 发往目标端的 /migrate/import（目标端路由特意加了 DefaultBodyLimit::disable() 放开请求体限制，源端遇到连接拒绝最多间隔 5 秒重试 5 次）。目标端收到后解包 bundle、还原书签并改写 remote_uri 指向目标仓库路径。
  4. 序列化迁移对话树，沙箱搬迁成功后，源端调用 serialize_session（远端则通过点对点 ClientMessage::Emigrate 指令）把根线程及所有子线程的完整消息、压缩摘要和元数据打包传回编排器。
  5. 目标端导入并清理临时服务，销毁刚才拉起的临时目标 RAP 服务，在目标端调用 import_session（或发 ClientMessage::ImportSession）把整棵对话树导入存储，并在 SessionStore 中建好记录、标记为已停机等待下次唤醒。
  6. 归档源会话并拆除隧道，源端把旧会话标记为已归档（远端通过 EmigrateDone 通知），离开函数作用域时 _tunnel_guards 自动 drop，所有临时 SSH 端口转发全部干净回收，前端收到 DaemonMessage::MigrateComplete { root_thread_id, new_root_thread_id } 切到新坐标。

这套流程对失败边界也守得很严：migrate_inner 开头就会直接拒绝迁移 SandboxMode::Direct、SandboxMode::Custom 以及横跨多个不同 Git 仓库的会话，避免搬到一半留下残缺状态。

到这里，本地与跨机私有开发机的完整运行体系已经拆解完毕。下一章把视角切到公有云，看同一份 infinity-agent-core 在完全没有常驻进程、没有本地磁盘、也没有 SSH 隧道的 AWS 无服务器平台上怎么落地。

零闲置云端部署：SQS FIFO、Lambda、Aurora DSQL 与持久定时器

把一个本地能跑的 Agent 搬上无服务器平台（Serverless），通常要大动干戈重写一遍状态机：本地内存通道没了，本地文件没了，tokio::time::sleep 超过十五分钟直接被 Lambda 强杀，多个并发回调同时撞进来还会把数据库写花。

Infinity 最具辨识度的架构验证，就落在 crates/infinity-agent-lambda/（1,894 行）和根目录的 agent/（AWS CDK 栈，1,200 行 TypeScript）里。它没有为云端另写一套执行引擎，而是把同一个 infinity-agent-core 的 AgentSystemBuilder 换上四块云端存储与传输适配器，直接跑在按次计费、空闲缩零的 AWS Lambda 上。

无锁并发：用 SQS FIFO 替代分布式锁#

云端架构的入口只有两条：所有外部事件（用户输入、RAP 工具回调、定时器唤醒、子线程报告）全部汇入同一条 SQS FIFO 输入队列；外部工具服务的异步回包则 POST 到一个极薄的 RAP Receiver Lambda Function URL（crates/infinity-agent-lambda/src/bin/rap-receiver.rs，仅 136 行）。

rap-receiver 的代码干净得像一段胶水：解开可选的 Base64 请求体，解析 RapCallback，调用与本地守护进程完全共享的 infinity_rap_bridge::prepare_callback。如果是 ViewUpdate（旁路展示通道，无服务器环境没有常驻前端），直接返回 200 {"ok":true} 丢弃；其余四类回调则直接调用 sqs_client.send_message() 投进输入队列：

// crates/infinity-agent-lambda/src/bin/rap-receiver.rs
sqs_client
    .send_message()
    .queue_url(input_queue_url)
    .message_body(enqueue.message_body)
    .message_group_id(enqueue.group_id.into_inner())
    .message_deduplication_id(enqueue.dedup_id)
    .send()
    .await

这两行队列参数承载了整个云端并发控制的核心保证：

  • message_group_id 设为 ThreadId，SQS FIFO 保证同一个 MessageGroupId 在同一时刻最多只会被一个 Lambda 实例拉取消费，彻底串行化单线程的读写切片；而一千个不同的 ThreadId 属于一千个不同的消息组，Lambda 会自动并行拉起多个实例水平扩展。核心运行时不需要引入 Redis 锁或数据库悲观锁。
  • message_deduplication_id 设为 dedup_id，先在队列入口挡掉 5 分钟窗口内的重复投递；超过窗口的重投则由第 3 章的 StateStore 去重集合和历史尾扫兜底。

当 SQS 触发主 Agent Lambda（crates/infinity-agent-lambda/src/event_handler.rs）时，处理函数把收到的 SqsEvent 记录解析成 (InputMessage, message_id) 批次，交给 AgentSystem::step。即便把 SQS batchSize 调大到一次拉多条横跨不同消息组的记录，step 内部也会按 group_id 自动分组并并发推进各线程切片，完事把最终输出发往 OUTPUT_QUEUE_URL，随后进程退出，等待期间零算力账单。

双存储分工：Aurora DSQL 存历史树，DynamoDB 存状态与缓存#

无服务器切片每次唤醒都要从零重建 HistoryManager，因此云端实现了 ConversationStore 和 StateStore 的持久化版本，刻意拆给两套特征互补的 AWS 存储服务：

抽象 Trait AWS 实现 数据结构与表设计 选用考量

另外，traits.rs 里关于 load_history_up_to 的一段注释解释了一个容易踩坑的边界对齐问题：本地 InMemoryConversationStore 内部用 0-based 数组下标（左闭右开 [a, b)），而 DsqlConversationStore 的 message_order 是 1-based 行号（SQL 条件 message_order > $start AND message_order <= $up_to）。为了不让 spawn_message_order 和压缩 up_to_order 在两种存储间差一位，trait 契约统一规定所有边界参数一律按前导消息条数（leading-row count）解释，于是无论 0-based 还是 1-based，(Some(a), Some(b)) 取出的都是逻辑上的第 a 到 b-1 条消息。

持久定时器：900 秒为界的双轨休眠#

本地驱动里的 TokioSleepTool 和 TokioSleepUntilTool 只要 tokio::spawn 一个内存定时器就行，但在 Lambda 上进程两秒后就退出了，内存定时器根本活不到唤醒时刻。

crates/infinity-agent-lambda/src/tools/sleep.rs 用 WakeupScheduler 实现了完全无状态的持久定时器（durable timers），以 SQS 的最大原生延迟 900 秒（15 分钟） 为分水岭切出两条路径：

  • 延迟 <= 0 秒（或目标时间已过）：直接调用 send_to_input_queue 立即投回主输入队列唤醒。
  • 延迟 1 ..= 900 秒：把唤醒消息包进信封发往一条独立的延迟中继队列 delay_queue_url，设置 SQS 原生的 delay_seconds。到期后中继队列触发极轻量的 delay-relay Lambda，把里面的 InputMessage 按原 group_id 和 dedup_id 转发回主 FIFO 输入队列。
  • 延迟 > 900 秒：调用 AWS EventBridge Scheduler 的 create_schedule，用 at(YYYY-MM-DDTHH:MM:SS) 创建一个精确触发（FlexibleTimeWindowMode::Off）的一次性调度计划，目标直接指向 input_queue_arn 并附带 SqsParameters { message_group_id }。哪怕 Agent 决定睡到下周一早上九点纽约时间，这期间整个 AWS 账号里没有任何运行中的计算实例。

而且这两条路径和本地一样完全可打断：SleepTool 和 SleepUntilTool 都标记了 is_passive() == true。如果在休眠期间用户提前发了新消息，切片立刻醒来、给休眠调用注入中断结果继续干活；等几小时后 EventBridge 真的把迟到的唤醒消息投进来时，HistoryManager::match_tool_result 逆向尾扫发现早就跨过了轮次边界，直接当作过期消息静默丢弃，不会惊扰正在进行的新对话。

云端适配里的显式取舍#

对比 infinity-agent-lambda 和 infinity-daemon，也能清楚看到无服务器部署为了换取缩容到零而主动接受的几条限制：

  • event_handler.rs 传入的是 NoDeferral，这意味着如果某个活跃远程 RAP 工具正在执行时恰好有另一条订阅事件或子线程报告到达主输入队列，Lambda 切片无法在内存里暂存它，会直接按中断处理（除非自行实现传输层延迟重投的 DeferQueue）。
  • 发起外部 RAP 请求使用 RapHttpClient 自动附带 SigV4 签名，免去在工具函数 URL 上维护静态共享密钥。
  • event_handler.rs 第 35 行目前把云端模型 ID 硬编码为 global.anthropic.claude-sonnet-4-6（源码注释明确写着 "hardcoded for now"），且不携带本地 drive_thread 里的 75% 自动压缩逻辑。这些现状我们在第 12 章还会集中复盘。

多端接入：终端 TUI、ACP 编辑器协议与 Hydro 数据流 Slack 机器人

infinity-agent-cli：内联视口、无头派活与插件管理#

crates/infinity-agent-cli/（10,294 行）是本地开发者的主入口，同时承担了三类工作：

  3. 自举插件管理（install.rs），infinity provider install、infinity rap install 和 infinity update 默认从 crates.io（也支持 --git 与 --path）拉取编译外部供应器和 RAP 服务，并自动维护 ~/.infinity/providers.json 与 RAP 服务配置表。

infinity acp：把守护进程会话接进 Zed 等编辑器#

现代编辑器正在向 ACP（Agent Client Protocol） 收敛，让编辑器侧栏的 Agent 面板可以通过标准 stdio JSON-RPC 接入任意后端代理。执行 infinity acp 启动的就是 crates/infinity-agent-cli/src/acp_server.rs。

acp_server.rs 的架构定位很纯粹：它自己不跑大模型，也不管沙箱，只做 ACP stdio 协议与 infinity-daemon Unix Socket 协议之间的无状态翻译桥。编辑器发来列会话、加载历史、新建会话、发提示词、切模型等指令，桥接层转成对应的 ClientMessage 发给本地守护进程，再把守护进程推回来的流式文本、思考过程、工具调用和 Diff 视图实时映射成 ACP 更新帧送回编辑器面板。

这里有一条和第 2 章呼应的边界纪律：在 0.2.0 的类型化 ID 重构中，团队特意把外部 ACP 协议侧的会话 ID 保留为原生 String（且保持 acp-sessions.json 持久化格式不变），只在 acp_server.rs 边界处与内部的 ThreadRef 互相转换，不让外部协议的弱类型侵入守护进程内部。

用 Hydro 数据流写 Slack 机器人：infinity-slack-dataflow#

仓库里最能体现 UC Berkeley Hydro 团队技术底色的两个 crate，是 infinity-slack-bot（2,371 行）和 infinity-slack-dataflow（1,817 行）。

Slack 机器人的状态同步一向容易写得支离破碎：一边要消费 Slack Socket Mode 的消息、斜杠命令、按钮点击和 App Home 打开事件，另一边要同时监听守护进程发来的流式分片、人工选择弹窗和会话断开通知；用户点下一个确认按钮时，既要把按钮消息更新成已选状态、停掉旧的流式输出，又要向守护进程发送 AnswerChoice，还得防止随后守护进程回传 UserChoiceComplete 时重复改写同一条 Slack 消息。

团队没有用一堆互相嵌套的 tokio::select! 和共享通道回调去硬凑，而是直接用自家研发的 Rust 分布式数据流框架 hydro_lang，把整个 Slack 机器人的核心逻辑写成了一个纯粹的、可离线模拟测试的数据流图（crates/infinity-slack-dataflow/src/flow.rs）：

// crates/infinity-slack-dataflow/src/flow.rs
pub fn slack_dataflow<'a, P: 'a>(
    slack_events: Stream<SlackEvent, Process<'a, P>, Unbounded>,
    daemon_events: Stream<DaemonEvent, Process<'a, P>, Unbounded>,
) -> (
    Stream<SlackAction, Process<'a, P>, Unbounded>,
    Stream<DaemonCommand, Process<'a, P>, Unbounded>,
)

整套业务逻辑就是从两个输入流 (slack_events, daemon_events) 到两个输出流 (slack_actions, daemon_commands) 的声明式变换管线：

  • 入口过滤与分叉，先用 filter 过滤机器人自身回声与未授权用户，再通过 partition 逐层把事件无拷贝地拆成四条互斥支路：交互按钮点击、斜杠命令（如 /model 弹 Slack Modal 选择器或纯文本列表）、App Home 首次打开（每用户只钉一次推荐提示词），以及常规聊天消息。
  • 按钮点击的三路扇出，一条 button_clicks 流同时派生出三条动作流：button_stop_actions 立刻结束当前活跃流式输出（让模型接下来的新回复落在新消息里），button_update_actions 把原按钮块改写成带勾选标记的确认文本，button_commands 解析 action_id（格式 choice_{choice_id}_{selected_index}），先从共享状态中摘除 choice_messages 防止重复更新，再发出 DaemonCommand::AnswerChoice。
  • 离线模拟测试，核心编排完全与真实 Slack HTTP/WebSocket 和守护进程 Socket I/O 解耦（真实网络壳子留在 infinity-slack-bot 里的 slack_io.rs 和 daemon_io.rs），crates/infinity-slack-dataflow/tests/dataflow_sim.rs 可以直接在进程内喂入模拟事件流、断言输出动作流，把整套复杂的多步 Slack 交互逻辑用确定性单元测试覆盖干净。

为什么多套前端能共用同一条总线#

把 CLI TUI、桌面 Web、ACP 编辑器和 Slack 机器人横向摆在一起，会发现它们共享了同一组极简契约：

  • 所有前端都不直接操作 ConversationStore，只通过 ClientMessage/DaemonMessage（或 WebSocket 同构 JSON）与守护进程对话。
  • 所有人机交互中断点（OAuthRequired、UserChoiceRequired、UserChoiceDismissed）都是运行时和 RAP 协议的一等消息，因此 TUI 渲染成方向键选择器、Web 渲染成 ChoicePicker.tsx 卡片、Slack 渲染成 Block Kit 按钮，底层沙箱的 write-orig 审批逻辑一行代码都不用改。
  • DisplaySegment（Text、Diff、Image）和 ViewUpdate 把模型消费的原始文本与前端展示的富媒体视图分开传输，客户端按自身渲染能力降级即可（例如终端渲染不出图片就自动跳过 Image 片段回退到后续 Text 片段）。

一路看下来，Infinity 的设计非常连贯，但它绝不是没有边界和短板的银弹。下一章我们专门翻出源码里的 TODO、显式拒绝分支、安全边界与架构代价，做一次冷静的工程复盘。

失败模式、安全边界与架构取舍

任何一套架构选型都是在用一种约束换另一种自由。只看设计文档很容易觉得无阻塞切片加堆叠沙箱无懈可击，但把源码里的防御断言、降级路径和作者亲手写下的 TODO 翻出来对照，才能看清它真正守住了什么、故意放弃了什么，以及哪些坑还没有填平。

安全边界：本地沙箱防的是误写，不是恶意代码#

把 sandbox-local/src/backend.rs 里的 macOS sandbox-exec 配置和 Linux bwrap 参数摊开看，有一条边界必须先亮明：

  • 只限写，不限读：Linux 端是 --ro-bind / /，macOS 端是 (allow default) 再接 (deny file-write*)。沙箱里的子进程能正常读取整台机器上当前用户有权限读的任何文件，包括 ~/.ssh/、~/.aws/、.env 和其他项目代码。
  • 不限网络：bwrap 没有加 --unshare-net，sandbox-exec 也没有屏蔽网络外连。构建工具下载依赖顺畅无阻，代价是如果模型被提示词注入跑了一段恶意脚本，依然可以把本地凭据外传出去。
  • 不支持平台的静默降级：在 macOS 和 Linux 之外的平台（!platform_sandbox_available()），LocalBackend::new 只打印一条 tracing::warn! 后直接裸跑命令。

sandbox-local 解决的工程问题是防止可信开发场景下的并发文件踩踏和误删宿主工作树，它不能替代 Firecracker 微虚拟机或无网隔离容器去运行不可信的第三方代码。如果要在多租户云端跑不受信仓库的任意脚本，必须在 sandbox-remote 之外叠加容器级或微虚机级的网络与读隔离。

溢出恢复的已知盲区：已提交历史本身逼近上限#

第 3 章拆解过 HistoryManager 的三阶段溢出恢复：只要超窗元凶在刚进来的 unvalidated_items 里，就能干净地替换占位符或丢弃未验证用户输入。

但 crates/infinity-agent-core/src/event_processor.rs 第 1439 至 1443 行坦诚留了一段 TODO(deferral)：如果已经提交落盘的历史本身就非常接近模型上下文上限（比如本地 75% 自动压缩还没来得及跑完，或者在没有自动压缩的 Lambda 路径上持续累加），此时哪怕进来一条很短的正常消息也会触发 ContextOverflow。recover_from_overflow 只能丢掉刚进来的新输入，根本缩不动已提交历史。理想的修复是派发一个更低阈值的压缩子线程并让当前线程进入延迟等待，等压缩完成后再重放当前消息，但等待进行中的压缩子线程对应的延迟机制目前源码里尚未实现。

单线程 LocalSet 与工具侧的隐性限制#

本地调度器选了单线程 tokio::task::LocalSet 换取零锁状态机、极低内存占用和无竞态的同步 check_before_idle。这个取舍的背面是：所有在 LocalSet 上直接运行的同步代码都不能做重 CPU 计算或阻塞磁盘 I/O。

守护进程里的 PersistentConversationStore 目前用 std::sync::Mutex 和同步文件写入来落盘每线程 JSON；当单个线程的历史增长到几兆字节，或者几十个线程同时刷盘时，序列化 JSON 和同步 fs::write 会短暂卡住同一个线程里的所有其他活跃驱动。同样的，第 9 章看到的跨主机热迁移也明确划定了禁区：SandboxMode::Direct、SandboxMode::Custom 以及同一个会话里同时操作了两个以上不同 Git 仓库时，migrate_inner 会直接返回错误拒绝迁移。

何时该用这套架构，何时不必折腾#

回头对照全书拆过的机制，Infinity 的适用边界其实非常清楚：

  • 适合的场景：需要同时挂载大量长周期、事件驱动 Agent（CI/CD 盯盘、PR 审查、人工审批流、定时巡检）；需要按实际推理切片缩容到零以控制云账单；或者需要在一台开发机上同时开多条并行编码线程，既要互不干扰又要能随时把会话和代码整体迁往远程算力机。
  • 不必引入的场景：如果业务只是同步一问一答的短平快 RAG 机器人，所有工具调用都在几百毫秒内返回，既没有跨小时等待也没有多子线程并发编辑，直接用轻量单循环加标准 MCP 服务反而架构更薄、排障链路更短。

理解了取舍与边界之后，最好的巩固方式是亲手跑一遍核心状态机。下一章不依赖 Rust 工具链、也不依赖任何第三方 Python 包，直接用一份四百多行的标准库 Python 教学实现把 Infinity 的五项核心不变量完整跑通并验证。

核心代码走读#

挑三段最能体现 Infinity 架构精髓的逻辑来看。

1. 三阶段历史与溢出止损#

在 HistoryManager 里，append_known_safe 直接复现了 Rust 版的顺序性断言：在模型尚未验证当前新输入之前，绝不允许提交模型输出；而 sync() 只刷 pending_items，且只把天然不幂等的 user 与 subscription_event 写入持久化去重集：

def append_known_safe(self, message: InfinityMessage, message_id: str) -> None:
    assert not self.turn_buffer, "bug: append_known_safe with non-empty turn_buffer"
    assert not self.unvalidated_items, (
        "bug: committing model output while unvalidated inputs exist"
    )
    self.history.append(message)
    self.pending_items.append((message, message_id))

def recover_from_overflow(self) -> tuple[Literal["retry", "dropped"], int]:
    if len(self.unvalidated_items) == 1 and self.replace_unvalidated_tool_results(
        TOOL_RESULT_TOO_LARGE_PLACEHOLDER
    ):
        return ("retry", 0)
    self.replace_unvalidated_tool_results(TOOL_CALL_INTERRUPTED_TEXT)
    dropped = self.drop_unvalidated_user_inputs()
    return ("dropped", dropped)

注意 replace_unvalidated_tool_results 里对已经等于占位符的正文跳过不计的细节：这样如果单条超大工具结果换完占位符再试一次仍然触发溢出，第二次调用会自动落入 dropped 分支，不会无限重试。

2. 落盘屏障与同步回环#

在 MiniInfinityRuntime.process_one 里，同步工具（spawn_thread）在 while True 补全循环内部直接执行并把结果喂回同一轮切片，而异步工具则跳出循环、先执行 hm.sync()，再登记派发记录：

if pending_async_call is not None:
    self.dispatched_async_calls.append(
        (tid, pending_async_call.tool_call_id, pending_async_call.tool_name,
         pending_async_call.tool_args, persisted_len_before_dispatch)

测试用例 test_commit_barrier_persists_tool_call_before_async_dispatch 会断言派发发生那一刻 persisted_len_before_dispatch == 2（用户输入和工具调用均已持久化），直接把落盘屏障做成了可验证断言。

3. 堆叠沙箱与祖先链写授权#

StackedSandboxManager 用纯内存字典模拟文件系统快照，还原了两个关键约束：第一，父线程和两个并行子线程各自修改互不覆盖，子线程完成后通过 squash_sandbox 把差量合回父书签，宿主 host_files 全程保持原样；第二，check_write_allowed 检查目标路径时，落在自己沙箱内直接放行，落在宿主仓库根目录下则沿着 thread_chain 逐级向上检查是否已授予 write-orig，未授权时返回 needs_user_choice:write-orig 触发前端确认：
